# 本番環境・リリーススキル (minimal-web-kit-deploy)

このスキルは、個別のアプリの本番環境の手順書を作り、それに沿ってリリースするための手順です。一般的な手順の例は `docs/deploy.md` にあります。このスキルは、その例を実際の環境の手順書にする方法を扱います。

公開前の確認の項目は `minimal-web-kit-audit` の4節を併用します。

## 1. 作る物と置き場所
- 成果物は、アプリのリポジトリの手順書（例: `PRODUCTION.md`）と、設定の見本（systemdのユニット、環境変数の見本等）です。
- 手順書には、契約したサーバー、プラン、構成、バックアップの方針、セキュリティ上の判断が入ります。**公開リポジトリに置かない。** 作る前に公開範囲を確かめる（例: `gh repo view --json visibility`）。キット本体には書かない。
- 秘密の値（パスワード、トークン、鍵、クライアント秘密値）は、非公開のリポジトリにも書かない。手順書には、置き場所と作り方だけを書く。

## 2. 先に決めること
決まっていないことは推測で埋めず、利用者に聞く。次の表を手順書の「決めたこと」の節にする。

| 事項 | 決めること |
|---|---|
| 置き場所 | 常駐プロセスとSQLiteのファイルを置けるか（`docs/deploy.md` の1節）。OS、CPU（ビルドの `GOOS`・`GOARCH`） |
| 公開の経路 | HTTPSの終端（リバースプロキシかトンネルか）。待受は `127.0.0.1` のままにする |
| ドメイン | 公開するホスト名。`AUTH_RP_ID` は後から変えるとパスキーが使えなくなるので、最初に決める |
| 有効な機能 | `cmd/server/features.go` の登録。Siteだけなら静的ホスティングも選べる |
| 設定 | 環境変数の一覧。パスキーの種類（`AUTH_ALLOW_SYNCED_PASSKEYS`）、タイムゾーン（`TZ`） |
| データ | DBの置き場所と権限、バックアップの頻度・保存先・保持期間、取り寄せ、`verify-backup` の検査、戻す手順の試験の頻度 |
| 停止 | 配備で許す停止時間、書き込みを止める時点。バックアップより後の受付を、戻したときに失ってよいか |
| ログ | プロキシとシステムのログの保持期間。コードやstateを含むURLをクエリごと記録しないか |
| 前段のサービス | CDN等を通すなら、通信とアクセス記録の説明（`/privacy`）、中身を書き換える機能の扱い |
| 守らない範囲 | 大量のアクセスへの対策、契約とアカウントの守り等、アプリの外に任せるもの |

## 3. 承認が要ること
`AGENTS.md` の5項目を本番の文脈で確かめ、手順書の「承認が要る事項」に書く。

- 公開範囲: インターネットに公開すること自体が境界5に当たる。`127.0.0.1` 以外への束縛、セキュリティヘッダーの緩和も同じ。
- 外部通信: トンネルやCDN等の常時の通信は境界3に当たる。
- 保存データ: 有効にする機能が、承認済みの台帳どおりかを確かめる。
- 依存: 取り込むキットの変更で、直接依存が増えていないかを確かめる。
- CSS・JS: JSの読み込みやCSPの例外が広がっていないかを確かめる。

本番への配備は、毎回、利用者の明示の承認を取る。コミットの承認は配備の承認ではない。承認には、版、操作の対象、停止時間、戻したときに失うデータを含める。

AIが実行するのは、手元の検証と、外からの読み取りの確認までにする。本番のサーバーやダッシュボードの操作は、手順と確認の方法を示して利用者に頼む。利用者が対象と範囲を示して明示に頼んだときだけ、その範囲を実行する。

## 4. 手順書の構成
次の順で書く。不要な節は理由を書いて省く。

1. 目的と構成（通信の経路を図で）
2. 承認が要る事項
3. 決めたこと
4. 手順（手元、サーバー、前段のサービス、管理者の登録、定期の手入れ）
5. リリースの手順（6節）
6. 戻し方（7節）
7. 公開前の確認
8. 守らない範囲

## 5. 手順の書き方
- コピーして実行できる形で書く。置き換える値は `example.com` のように分かる形にする。
- 手順ごとに、誰が実行するか（手元、サーバー、ダッシュボード）と、成功をどう確かめるかを書く。
- 手順ごとに、利用者が操作するかAIが実行するかを3節の線引きで分ける。
- 複数のコマンドは、途中で失敗したら止まる形で書く（`sh -eu` 等）。データを消す操作の前に、前の手順の成功を確かめる。
- 順番の理由が分からないと壊れる所には、理由を書く（例: 再起動の前にバックアップを取る）。
- 手順を実行したら、実際の結果に合わせて手順書を直す。実行していない手順は「未検証」と書く。
- サービスの画面の案内は、変わることがあるので、公式の案内へのリンクを添える。

## 6. リリースの進め方
1. **版を決める**: 配備するコミットを1つ決める。キットの変更を取り込むアプリでは、取り込んだ範囲を確かめる。
2. **差分を読む**: 前回の配備からの差分で、次を確かめる。
   - DBの表の追加か、形の変更か（`migration.sql`、`migrate.go`、`docs/deploy.md` の9節）
   - 環境変数の追加、必須の設定の変更
   - Cookie・セッション・公開の経路の変更
   - 前の版が更新後のDBを読み書きできるか。起動だけでなく、主な読み書きをDBの複製で試し、結果で7節の戻し方を決める
   - 利用者が再ログインする必要があるか
3. **検証する**: `go test -race ./...`、`make verify`、必要なら `make test-ui`。
4. **ビルドする**: 対象の `GOOS`・`GOARCH` で `make build`。作業ツリーがきれいな状態から作り、`go version -m <ファイル>` の `vcs.revision` と `vcs.modified=false` を確かめる。
5. **承認を取る**: 版、差分の要点、停止時間、戻し方、失うデータを示す。
6. **配備する**（3節の線引きで）:
   - バックアップを取り、`verify-backup` で確かめる。
   - 今の実行ファイルと、環境ファイル・systemdの設定を戻せるように残す。
   - 実行ファイルを置き換えて再起動する。
7. **確かめる**: サービスの状態とログ、主な画面、今回の変更が本番で見えること。外から確かめられることはAIが確かめる。配備したファイルのハッシュと、ビルドしたファイルのハッシュが同じかも確かめる。CSSを変えたら `docs/deploy.md` の10節を見る。
8. **記録する**: 配備した版と日時、設定の変更、秘密の更新を、手順書か利用者の決めた場所に残す。秘密の値そのものは書かない。公開リポジトリには書かない。

共通認証を使うときの順序:
- 新しい機能を足す更新は、認証基盤を先に配備し、連携先を後にする。
- 秘密値は、認証基盤で発行し、連携先に置いて再起動し、ログインと照会を確かめる。通常の更新で旧値が使えるのは24時間で、それを過ぎると前の秘密値には戻せない。

## 7. 戻し方
判断の基準とコマンドは `docs/deploy.md` の9節「戻し方」と8節にある。手順書には、そのアプリの判断を書く。

- リリースごとに、前の版が更新後のDBを読み書きできるかの結果と、選ぶ戻し方を残す。
- DBを戻す前に、利用者に、失うデータを示して確認する。アカウントの停止等、バックアップより後の操作も戻ることを含める。
- 実行ファイルと一緒に、対応する環境ファイル・systemdの設定を戻す。漏洩した秘密の値には戻さない。
- 共通認証の提供機能でDBを戻すときは、**起動の前に** `oidc-revoke-all -yes` を実行する。
- 戻したら、6節の手順7の確認をもう一度行う。

## 8. やらないこと
- 本番のDBや設定を、確認なしで変更しない。
- 秘密の値を、会話、ログ、コミットに出さない。利用者に貼ってもらわない。
- 失敗した配備を、原因を確かめずにやり直さない。
- 手順書に無い操作を本番で試さない。先に手元で確かめ、手順書に足す。
