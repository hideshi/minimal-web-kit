# プライバシーポリシースキル (minimal-web-kit-privacy)

このスキルは、個別のアプリのプライバシーポリシーを、実際の構成に合わせて作るための手順です。ポリシーの内容は、有効な機能、保存データ、インフラ、外部サービス、運営者によって変わります。

**法的な助言ではありません。** 適法かどうかの判断は運営者が行います。判断が分かれる項目は、資料の根拠と未確認の点を示して運営者に渡し、必要なら専門家への相談を勧めます。「適法です」「問題ありません」「対象外です」と断定しません。資料を読めないときは、未確認と書き、番号だけを添えます。

## 1. 作る物と置き場所
- 成果物は、アプリの `/privacy` の文面と、機能が画面に載せる説明（`PrivacyFeature`）の見直しです。
- キットの `internal/web/views/privacy.html` と `PrivacyFeature` は配布用の雛形です。運営者ごとの内容は、アプリのリポジトリに書き、キット本体には書きません。
- 契約先やバックアップの詳細などの運用情報は、非公開の手順書（`minimal-web-kit-deploy` の成果物）に書きます。ポリシーには、利用者が知るべき範囲だけを書きます。秘密の値は書きません。
- 運営者が確かめる事項が残る文面は草案です。公開用の文面と、確認待ちの一覧を分けて渡します。

## 2. コードと文書から集める
推測で埋めず、**取得・送信・一時処理・保存**する情報と、その経路を表にします。DBに保存しない情報も対象です（CDNやトンネルを通る本文、Cookie、認証情報）。

| 調べる物 | 分かること |
|---|---|
| `cmd/server/features.go` | 有効な機能。無効でも、残っているデータ・Cookie・ログ・複製があれば説明する |
| `docs/data-inventory.md`（各機能の節）と各 `migration.sql` | 保存項目、目的、保持期間、削除の方法 |
| 各機能の `PrivacyNotices`、`docs/domain/<機能>.md` | 画面に自動で載る説明と、保持の条件 |
| `docs/data-inventory.md` の各 `Cookie:` 節と `internal/web/session.go` | Cookieの名前、目的、有効期限、公開ページで発行するか |
| ログ（`docs/deploy.md`、journald の保持、プロキシ） | 何を記録し、どれだけ残すか |
| バックアップ（`backup` コマンドの複製、`pre-migration-*.db`、送り先） | 保存先、暗号化、保持期間。削除したデータが複製に残る期間 |
| 環境変数（`CONTACT_RETENTION_DAYS` 等、配備の設定） | 保持期間の実際の値。既定値のまま書かない |
| 自作の機能、外部へ通信するコード | 追加の項目、外部へ送る情報 |
| アプリの外の取扱い | 外部フォームの回答、返信のメール、表計算、管理者の端末、書き出したファイル |

保持期間は、起算点、削除の処理の間隔、複製の世代と再複製を確かめてから計算します（例: 対応中のお問い合わせ365日＋手元の複製3か月）。上限の無いものは、最長の期間を未確定と示します。

個人データを持つかどうかは、キットのDBだけで判断しません。外部フォームやメールを含む運営者の取扱い全体で判断します。

## 3. 外部サービスを洗い出す
通信や保存を任せるサービスを全部挙げます。ホスティング、CDN、トンネル、バックアップの保存先、メール、外部フォーム、監視、アクセス解析、決済、埋め込みの地図や動画等です。公式の資料で次を確かめ、URLと確かめた日を残します。

| 確かめること | 例 |
|---|---|
| 事業者の名称と所在国。日本法人の有無と、国内での取扱い | 利用規約の末尾の所在地 |
| データの保存場所。保証があるか、希望だけか | ロケーションヒントは保証ではない |
| 契約上の立場と、取り扱わない旨の条項の有無 | 処理者（processor）か。DPAの締結の方法 |
| 通る情報 | 内容が事業者のところで平文になるか、送る前に暗号化しているか |
| 再委託先、削除の要求の反映 | サブプロセッサの一覧 |
| 事業者に残る記録 | アクセスの記録の項目と期間 |
| 判断待ちの事項 | 委託か第三者提供か、監督の方法、外国移転の根拠 |

通信を通すだけの事業者が内容を平文で処理する場合、それが「取扱い」に当たるかは、Q&Aに直接の記述を見つけられていません。運営者か専門家の判断に渡します。外部フォームは、入力項目、提供者側の保持、受け取った後の保管、削除の窓口も確かめます。

## 4. 個人情報保護法で確かめる点
個人情報保護委員会の資料の原文で確かめ、番号を添えて運営者に示します。資料は改定されるため、作るたびに読み直します。[Q&A](https://www.ppc.go.jp/personalinfo/faq/APPI_QA/)、[通則編](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)、[外国にある第三者への提供編](https://www.ppc.go.jp/personalinfo/legal/guidelines_offshore/)、[令和8年改正法](https://www.ppc.go.jp/personalinfo/legal/r8kaiseihogohou/)。

1. **対象か**: 個人情報データベース等を事業の用に供していれば、件数にかかわらず個人情報取扱事業者に当たる。任意団体や個人も含む（通則編 2-5）。
2. **取得するとき**: 利用目的を通知または公表する（法第21条第1項）。入力画面等で本人から直接取得するときは、あらかじめ利用目的を明示する（法第21条第2項、通則編 3-3-4）。ポリシーがあるだけで足りるとせず、各フォームの画面で確かめる。
3. **要配慮個人情報**: 自由記述に病歴等が書かれ得る。取得の予定と、混入したときの扱いを運営者に決めてもらう（法第20条第2項）。
4. **公表する事項**（法第32条、政令第10条、通則編 3-8-1）: 名称・住所・法人の代表者の氏名、全ての保有個人データの利用目的、利用目的の通知の求めと開示等の請求に応じる手続（手数料を定めたらその額）、安全管理のために講じた措置、苦情の申出先、認定個人情報保護団体の対象ならその名称と申出先。本人の求めに応じて遅滞なく回答する形でもよいが、「ガイドラインに沿っている」とだけ書くのは適切でない。
5. **外部サービスは提供か**: 判断の基準は、データが入っているかではなく、事業者が個人データを取り扱うことになっているか（Q7-53）。例として、契約で取り扱わない旨を定め、適切にアクセス制御している場合等が挙げられている（Q12-3）。送信前の暗号化はアクセス制御の材料になり得るが、それだけで「取り扱わない」と判断しない。契約条項、対象データ、サービスの処理の内容を確かめ、取り扱わない旨の条項が見つからなければ「取り扱わない」と書かず、根拠と未確認の点を添えて運営者に渡す。処理者という呼び方だけで日本法の分類も決めない。
6. **取り扱う場合**: 委託か第三者提供かの判断は運営者に渡し、次を確認項目として示す。委託なら委託先の監督（法第25条、通則編 3-4-4）。外国の事業者なら、サーバが国内でも外国にある第三者への提供になり得る（Q12-4）。国内で事業の用に供している場合の扱い（外国編 2-2）。法第28条の経路（本人の同意、指定された国、基準適合体制）と、それぞれで要る情報提供や継続的な確認（外国編 5・6）。
7. **取り扱わない場合でも**: 自ら安全管理措置を講じる（Q7-54）。外国の制度を把握し、事業者の国とサーバの国の名称、把握したうえで講じた措置を本人が知り得る状態に置く。サーバの国を特定できないときは、その旨、理由、参考になる情報を書く（Q10-25）。
8. **外国の制度**: 委員会の[調査](https://www.ppc.go.jp/personalinfo/legal/kaiseihogohou/#gaikoku)を読み、調査の時点を確かめる。補助的な資料で、確認の責任は事業者にある。
9. **漏えい**: 報告の要否と本人への通知は、運営者が通則編 3-5 で確かめる。一定の高度な暗号化は判断に関わるが（Q6-19）、暗号化だけで報告不要としない。鍵の喪失で復元できなくなれば「毀損」の事例に当たるが、同じ内容のデータが他にあれば当たらない（通則編 3-5-1-4）。事故の責任者と連絡経路は手順書で決める。
10. **子ども**: 未成年者が結果を判断できない場合は、親権者や法定代理人等の同意が要る（通則編 2-16）。令和8年改正法（令和8年7月17日公布）に16歳未満の者の取扱いの規定がある。施行の状況を確かめ、未施行なら予定として伝える。
11. **加工情報等**: 識別子やハッシュを、法定の仮名加工情報・匿名加工情報と書かない。Cookie等を第三者が個人データとして取得するなら、個人関連情報の規定（法第31条）を確かめる。

日本以外の法令（GDPR等）、電気通信事業法の外部送信規律は、このスキルの範囲外です。海外の利用者がいるときや、外部へ送る仕組み（解析、広告、埋め込み）を足すときは、適用の確認を運営者に頼みます。

## 5. 運営者に聞く
コードから分からない項目は、次をまとめて聞きます。分からない項目は空のままにせず、未確定と示します。

- 運営者の名称、住所、法人の代表者の氏名
- 問い合わせと苦情の窓口、開示等の請求の手続・本人確認・開示の方法、手数料の有無
- 認定個人情報保護団体の対象か
- 利用目的（機能の説明ではなく、運営者が何のために使うか）
- 対象の利用者（子どもが使うか、海外の利用者がいるか）
- 第三者への提供、共同利用の有無
- 組織の体制（担当者、従業者の範囲、社内の決まり、持ち出しの扱い）、中小規模事業者に当たるか
- 3節・4節で判断が要る事項、制定日、改定の知らせ方

## 6. 文面を作る
次の順で書きます。不要な節は省き、理由を運営者に伝えます。

1. 事業者の情報
2. 取得する情報と利用目的（有効な機能ごと。閲覧だけなら何を取らないか）
3. Cookie（発行者、目的、期限、無効にする方法と影響）
4. 保持期間と削除（最長の期間、複製に残る期間）
5. 外部サービスと外国での取扱い
6. 第三者への提供
7. 安全管理のために講じた措置
8. 開示等の請求の手続、苦情の申出先
9. 制定日、改定日、改定の知らせ方

書き方:
- コード、設定、契約資料、運営者が確かめた運用で裏づけられることだけを書く。「完全に」「絶対に」「一切」「漏洩しません」のような保証を書かない。
- 既定値は実際の設定値に置き換え、機能の説明と同じ数字にする（`PrivacyNotices` の値は設定から描かれる）。
- 確かめていないことを「確認した」と書かない。運営者が確かめた後に入れる文は、未確定として分けて渡す。
- 安全管理措置は概要にとどめる。アクセス制御の範囲や認証の手法等、書くと支障を及ぼすおそれがある具体は書かなくてよい（通則編 3-8-1、政令第10条第1号）。
- 利用者に読める言葉で書く。テーブル名やコードの名前を書かない。

## 7. 照合する
1. 2節の情報が全部ポリシーにあり、ポリシーの項目が実態にある。保存項目だけでなく、通過する情報も見る。
2. 雛形の固定文（閲覧、アクセスログ、外部フォーム、免責）を1文ずつ、2節・3節の事実と突き合わせ、合わない文を書き換える。例: 前段のCDNがIPアドレスを記録するなら、「記録しません」のままにしない。
3. 保持期間と最長の期間が、台帳、画面の説明、手順書と一致する。
4. 3節のサービスが全部載っている。保存場所の書き方が、資料の保証の範囲を超えていない。
5. 入力画面（外部フォームを含む）で、入力の前に利用目的を確かめられる。
6. 未確定が残っていれば一覧にして運営者に示す。残っている文面は公開しない。
7. 配備の後、本番の `/privacy` と、実際の問い合わせ先の説明を確かめる。
8. 確かめた資料のURL、日付、運営者が判断した事項を、非公開の手順書に残す。

## 8. 見直す時
次の変更では、このスキルをもう一度使います。

- 保存項目、Cookie、利用目的、保持期間の変更（`docs/data-inventory.md` の更新を伴う変更）
- 機能の有効・無効の変更
- 外部サービス、保存場所、バックアップの方法の変更
- 運営者や窓口の変更、法令やガイドラインの改定（令和8年改正法の施行を含む）
