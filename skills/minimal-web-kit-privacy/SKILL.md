# プライバシーポリシースキル (minimal-web-kit-privacy)

このスキルは、個別のアプリのプライバシーポリシーを、実際の構成に合わせて作るための手順です。ポリシーの内容は、有効な機能、保存データ、インフラ、外部サービス、運営者によって変わります。

**法的な助言ではありません。** 適法かどうかの判断は運営者が行います。判断が分かれる項目は、資料の根拠と未確認の点を示して運営者に渡し、必要なら専門家への相談を勧めます。「適法です」「問題ありません」と断定しません。

## 1. 作る物と置き場所
- 成果物は、アプリの `/privacy` の文面と、機能が画面に載せる説明（`PrivacyFeature`）の見直しです。
- キットの `internal/web/views/privacy.html` と `PrivacyFeature` は配布用の雛形です。運営者ごとの内容は、アプリのリポジトリに書き、キット本体には書きません。
- 契約先やバックアップの詳細などの運用情報は、非公開の手順書（`minimal-web-kit-deploy`）に書きます。ポリシーには、利用者が知るべき範囲だけを書きます。公開リポジトリか確かめるときは、`gh repo view <所有者>/<名前>` のように名指しする（`upstream` があると、名指ししないと別のリポジトリの結果が返ることがある）。
- 秘密の値は書きません。

## 2. コードと文書から集める
推測で埋めず、次から事実を集めて、表にします。

| 調べる物 | 分かること |
|---|---|
| `cmd/server/features.go` | 有効な機能。無効な機能の説明を書かない |
| `docs/data-inventory.md`（有効な機能の節）と各 `migration.sql` | 保存項目、目的、保持期間、削除の方法 |
| 各機能の `PrivacyNotices`、`docs/domain/<機能>.md` | 画面に自動で載る説明と、保持の条件 |
| Cookieの発行の経路（`internal/web/session.go`、`features/auth`） | Cookieの名前、目的、有効期限、公開ページで発行するか |
| ログ（`docs/deploy.md`、journald の保持、プロキシ） | 何を記録し、どれだけ残すか |
| バックアップ（手順書、`mwk-backup` 等） | 保存先、暗号化、保持期間。削除したデータが複製に残る期間 |
| 環境変数（`CONTACT_RETENTION_DAYS` 等、配備の設定） | 保持期間の実際の値。既定値のまま書かない |
| 自作の機能、外部へ通信するコード | 追加の項目、外部へ送る情報 |

最長の保持期間は、稼働データの期間と複製の期間を足して計算します（例: 対応中のお問い合わせ365日＋手元の複製3か月）。

## 3. 外部サービスを洗い出す
通信や保存を任せるサービスを全部挙げます。ホスティング、CDN、トンネル、バックアップの保存先、メール、外部フォーム、監視、アクセス解析、決済、埋め込みの地図や動画等です。

サービスごとに、公式の資料で次を確かめ、URLと確かめた日を残します。

| 確かめること | 例 |
|---|---|
| 事業者の名称と所在国 | 利用規約の末尾の所在地 |
| データの保存場所。保証があるか、希望だけか | ロケーションヒントは保証ではない |
| 契約上の立場 | 処理者（processor）か、データを取り扱わないと定めているか |
| 通る情報 | 内容が事業者のところで平文になるか、送る前に暗号化しているか |
| 事業者に残る記録 | アクセスの記録の項目と期間 |

## 4. 個人情報保護法で確かめる点
個人情報保護委員会の資料の原文で確かめ、番号を添えて運営者に示します。資料は改定されるため、作るたびに読み直します。[Q&A](https://www.ppc.go.jp/personalinfo/faq/APPI_QA/)、[通則編](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)、[外国にある第三者への提供編](https://www.ppc.go.jp/personalinfo/legal/guidelines_offshore/)。

1. **対象か**: 個人情報データベース等を事業の用に供していれば、件数にかかわらず個人情報取扱事業者に当たる（通則編 2-5）。
2. **公表する事項**（法第32条、政令第10条、通則編 3-8-1）: 名称・住所・法人の代表者の氏名、全ての保有個人データの利用目的、開示等の手続、安全管理のために講じた措置、苦情の申出先。本人の求めに応じて遅滞なく回答する形でもよいが、「ガイドラインに沿っている」とだけ書くのは適切でない。
3. **外部サービスは提供か**: 判断の基準は、データが入っているかではなく、事業者が個人データを取り扱うことになっているか（Q7-53）。「取り扱わないこととなっている」例は、契約で取り扱わない旨を定め、適切にアクセス制御している場合等（Q12-3）。**暗号化だけでは契約の条件は満たさない。契約が処理者と定めているなら、「取り扱わない」と書かず、運営者に判断を渡す。**
4. **外国の事業者**: 取り扱っているなら、サーバが国内でも外国にある第三者への提供になる（Q12-4）。国内で事業の用に供している場合等の例外と、法第28条の扱いは、運営者が確かめる。
5. **取り扱わない場合でも**: 外国の制度を把握して安全管理をし、事業者の国とサーバの国の名称、把握したうえで講じた措置を、本人が知り得る状態に置く。サーバの国を特定できないときは、その旨、理由、参考になる情報を書く（Q10-25）。
6. **外国の制度**: 委員会の[調査](https://www.ppc.go.jp/personalinfo/legal/kaiseihogohou/)を読み、調査の時点を確かめる。補助的な資料で、確認の責任は事業者にある。
7. **漏えい**: 暗号化と鍵の管理の条件（Q6-19）、鍵を失うと「毀損」に当たること（通則編 3-5-1-4）を、運用の判断に渡す。

個人データを持たない構成でも、Cookieや外部サービスの説明は書きます。EUの利用者等、日本以外の法令が関わるなら、このスキルの範囲外として運営者に伝えます。

## 5. 運営者に聞く
コードから分からない項目は、次をまとめて聞きます。分からない項目は空のままにせず、未確定と示します。

- 運営者の名称、住所、法人の代表者の氏名
- 問い合わせと苦情の窓口、開示等の請求の手続、手数料の有無
- 利用目的（機能の説明ではなく、運営者が何のために使うか）
- 対象の利用者（子どもが使うか、海外の利用者がいるか）
- 第三者への提供、共同利用の有無
- 組織の体制（担当者、従業者の範囲、社内の決まり、持ち出しの扱い）
- 3節で判断が要るサービスの扱い、制定日と改定の知らせ方

## 6. 文面を作る
次の順で書きます。不要な節は省き、理由を運営者に伝えます。

1. 事業者の情報
2. 取得する情報と利用目的（有効な機能ごと。閲覧だけなら何を取らないか）
3. Cookie
4. 保持期間と削除（最長の期間、複製に残る期間）
5. 外部サービスと外国での取扱い
6. 第三者への提供
7. 安全管理のために講じた措置
8. 開示等の請求の手続、苦情の申出先
9. 制定日、改定日

書き方:
- 実装で確かめられることだけを書く。「完全に」「絶対に」「一切」「漏洩しません」のような保証を書かない。
- 既定値は実際の設定値に置き換え、機能の説明と同じ数字にする（`PrivacyNotices` の値は設定から描かれる）。
- 確かめていないことを「確認した」と書かない。運営者が確かめた後に入れる文は、未確定として分けて渡す。
- 利用者に読める言葉で書く。テーブル名やコードの名前を書かない。

## 7. 照合する
1. 2節の保存項目が全部ポリシーにあり、ポリシーの項目が実装にある。
2. 保持期間と最長の期間が、台帳、画面の説明、手順書と一致する。
3. 3節のサービスが全部載っている。保存場所の書き方が、資料の保証の範囲を超えていない。
4. 5節の項目に未確定が残っていれば、一覧にして運営者に示す。
5. 配備の後、本番の `/privacy` と `/contact` の説明を確かめる。
6. 確かめた資料のURL、日付、運営者が判断した事項を、非公開の手順書に残す。

## 8. 見直す時
次の変更では、このスキルをもう一度使います。

- 保存項目、Cookie、利用目的、保持期間の変更（`docs/data-inventory.md` の更新を伴う変更）
- 機能の有効・無効の変更
- 外部サービス、保存場所、バックアップの方法の変更
- 運営者や窓口の変更、法令やガイドラインの改定
