# 計画・選定スキル (minimal-web-kit-design)

このスキルは、機能の追加や変更を始める前に、依存ライブラリやデータ取得を最小限に抑えるための判定を行います。

他の専門スキルと併用し、minimal-web-kit固有の判断・規約を補完します。一般的な開発手順を置き換えるものではありません。

## 1. 要件の確認（実装の前に）
変更の大きさごとの要否は `docs/README.md` の「変更の大きさと文書」で判断する。新しい文書を増やさず、次の差分だけを確かめる。
1. **目的**: 目的・アクター・人の判断が変わるなら、`docs/ui/use-cases.md` を実装の前に更新する。コードから推定した目的は、利用者か保守者に確かめる。
2. **ドメインモデル**: 用語・状態・不変条件・権限が変わる場合は、機能の `docs/domain/<機能>.md` を先に直す。不変条件には番号（例: `AUTH-INV-1`）を振り、使い回さない。計画書（`docs/*-plan.md`）は経緯の記録とし、今の仕様は `docs/domain/` に置く。
3. **業務フロー図**: 複数の役割が順に関わる、システムの外の手作業が挟まる、承認・差し戻し・例外・時間待ちが表だけでは分からない、のどれかに当たるときだけ、機能の `docs/domain/<機能>.md` にMermaidのフローチャートで描く。システム間の通信はシーケンス図で別に描く。キットには短い図だけを置き、実際の業務の図はキットから作るアプリに置く。
4. **画面設計書**: 既定で作らない。複数の役割が同じ画面を別の目的で使う、表示する情報が判断を左右する、分岐や復帰が複雑、標準の画面の型から外れる、のどれかに当たる画面だけ、固有の内容を `docs/ui/screens/` に書く。権限・入力規則・共通の配置は書き写さず、正本を参照する。

## 2. 人への確認が必須の5境界 (AGENTS.md)
以下のいずれかに該当する場合は、作業を自動で進めず、**必ず利用者に理由・代替案・影響を示して確認・承認を得てください**。
1. `go.mod` の変更（新規依存の追加・差し替え）
2. フォーム項目・Cookie・DB列の追加
3. 外部へのHTTP/ネットワーク通信
4. CSS/JSファイルの追加
5. 待受アドレスや公開範囲の変更

## 3. 依存ライブラリの選定チェックリスト
外部ライブラリを検討する際は、次の順序で判断します。
1. **`go.mod` のGoバージョンの標準機能で満たせないか**: `net/http`, `html/template`, `crypto/rand`, `crypto/sha256`, `log/slog` で十分か確認する。
2. **標準の組み合わせで代替できないか**: 数十行のGoコードで安全に書ける処理のためにライブラリを導入しない。
3. **外部ライブラリを採択する場合の条件**:
   - 複雑な暗号処理や標準仕様適合など、自作が明らかに危険な場合に限る。
   - ライセンス、推移的（間接）依存の数、CGOの有無、メンテナンス状況を確認する。
   - 採用時は利用者の承認を得て、`test/architecture_test.go` の許可リストを更新する。
4. **認証・暗号の検証を標準ライブラリで自前に組む場合**（例: WebAuthn）: 暗号処理そのものは自作せず、仕様の検証手順をテストで1つずつ固定する。計画の段階と、検証部分ができた段階で、外部のモデル等によるレビューを受ける。
5. **Coreの共通の経路を変える場合**（テンプレートの解析、配信、キャッシュ、セキュリティヘッダー、セッション）: すべての画面に効くため、計画の段階で外部のモデル等によるレビューを受ける。
6. **新しい公開経路、利用者の入力を構造に変える自前の読み取り（本文の記法等）、守りに触れる変更**: 計画の段階と、できた段階で外部のモデル等によるレビューを受ける。読み取りは、実装の前に読む規則（判定の順番の表と例）だけを短くレビューに出す。経路の衝突や、入力の長さに対して二次関数的に遅くなる形は、こうしたレビューで見つかった。

## 4. 個人データ・保存データの最小化チェックリスト
新しいデータを保存・取得する前に、次の問いを評価します。
1. **その情報がなくても目的を達成できないか**: 実名・メール・電話番号・生年月日は既定で取得しない。必要な場合は利用目的と取得範囲を説明し、承認を得る。
2. **粗い情報や一時利用で代替できないか**: 保存せずメモリ内でのみ処理できないか。
3. **保持期間と破棄手段はあるか**: 削除手段（ユーザー自身による削除・放置セッションGC）を同時に設計する。OwnerIDに紐づけたデータはセッション破棄と30日放置で消えるため、残すべきデータには別の持ち主と保持期間を定める。
4. **docs/data-inventory.md の更新**: 新規に列を追加する場合は、利用者の承認を得た上で `docs/data-inventory.md` に目的・保持期間を記録する。

5. **入力の検査を厳しくするとき**: 保存済みのデータが次の保存で弾かれないか（例: タイトルのタブ）、URLの応答が変わらないか（例: 400から404）を調べ、影響と利用者への説明を設計に書く。

## 5. 用途と公開時の約束を決める
- 公開ページはセッションなしを既定とし、状態保持が必要な操作だけで発行する。匿名のOwnerIDは管理者認証や業務権限の代わりにはならない。
- 内容を管理する機能・業務機能では、誰が何を閲覧・更新できるか、認証方法・権限・失効条件を先に決める。同梱機能の範囲は、各 `docs/domain/<機能>.md` の「守らない範囲」と README の各機能の節で確かめ、超える機能は設計し直して承認境界を確認する。管理画面を作るときは、管理者認証（`features/auth`）を使い、システム管理者だけに許す画面は `AdminPage`・`AdminForm` で守る。
- 最上位のパスを利用者が決める機能（例: 固定ページの `/{slug}`）は、`/{slug}` を経路に登録しない。登録すると `/privacy` 等が取られ、起動時のエラーにもならない。どの経路にも当たらなかったときの受け皿（`FallbackFeature`）で受け、使えない名前は一覧で持たずに、実際に経路に当てて確かめる。
- 同じ変更が2つ以上の機能（レイアウト・テンプレート等）に及ぶときは、Coreの部品に寄せる案と、機能ごとに直す案を並べて利用者に示す（`docs/components.md` の「部品を増やすとき」）。
- 個人情報を扱う場合は、フォーム・DB・Cookieだけでなく、外部フォーム、アクセスログ、バックアップへの流れも整理する。利用目的、保存先、保持期間、削除方法と窓口を定め、docs/data-inventory.mdと画面の説明を揃える。
- 外部フォームで運営者が受け取る情報も取得の対象として説明する。外部サービス側の処理と、サイトのセッション削除の対象外になることを区別する。
- 保存項目、Cookie、保持期間、外部サービスが変わる設計では、`minimal-web-kit-privacy` でプライバシーポリシーの見直しも計画に入れる。
- LP・READMEの約束を実装と検証方法に対応づける。「漏洩ゼロ」「完全適合」「配置だけで本番公開」「PRODUCTION READY」のような未検証の保証や、機能を有効にすると成り立たなくなる表現（例: お知らせ機能を有効にしたときの「完全セッションレス」）は避ける。バイナリサイズには測定環境を添える。
- 管理画面は、画面ごとに `docs/components.md` の「画面の型」（一覧・一覧＋追加・作成・編集・詳細・削除の確認）のどれにするかを決める。型に入らない画面は、理由を設計に残す。
- 動きのあるUIは、標準の要素 → htmx → 素のJSの順に検討し、どの段で作るかと理由を設計に残す（`docs/ui-guidelines.md`）。JSの追加・読み込む画面の拡大は承認境界4・5に当たる。
- 配布用のテンプレートと、運営者ごとの内容を分ける。プライバシーポリシー、免責事項、お問い合わせ窓口、宣伝の文言は運営者が書き換える前提の例として扱う。実際の運用サイトは別リポジトリにし、配布用を `upstream` として取り込む。
- 公開先（ホスティング、無料枠、CDN等）の仕様や条件は、公式の資料で確かめてから文書に書き、確かめたことと推測を分ける。配信サービス側に残るアクセスの記録も、プライバシーポリシーで説明する。
- Cookieも保存データも使わない構成（Siteのみ）なら、`export-static` で静的ホスティングに置く選択肢がある。サーバー・DBが要るかを、公開先を選ぶ前に整理する。
- データベースはSQLiteだけを対象にする（対象は小さな企業・団体の1台の構成）。MySQL・PostgreSQL・複数台の構成・自動の切り替えを前提にした設計はしない。障害への備えは、サーバーの外の複製と、そこから戻す手順（`docs/deploy.md` の8節）で守る。
- 表を作り直す移行は、`store.BackupBeforeMigration` で複製を作ってから、1つのトランザクションで行う。見本は `features/contact/migrate.go`。
