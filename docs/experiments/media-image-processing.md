# 画像の加工の測定（2026-11-01）

[画像機能の計画](../plans/media-plan.md) の13節の1の、途中の結果です。写真そのものは載せません。

## 条件

- 手元の Linux（Intel Core Ultra 5 115U）、Go 1.27.1。本番のVPSでは測っていない。
- 処理: `image` の標準ライブラリでデコード、EXIFの向きの適用、Lanczos3の縮小（自作の試作）、JPEG。
- 試作は素直な書き方で、全画素を `NRGBA` に写し、縮小の途中の結果を `float32` で持つ。メモリの値は実装の上限の目安で、最適化の後の値ではない。
- 写真はAndroidの2枚（どちらもJPEG、sRGB）。模擬画像はノイズから作った。

## 容量

長辺を変えたときの保存の容量（Pillow の Lanczos、JPEG）。

| 入力 | 長辺 | 品質75 | 品質80 | 品質85 |
|---|---|---|---|---|
| 写真A（4080×3072、4,133KB） | 1,800 | 479KB | 547KB | 640KB |
| | 1,600 | 388KB | 444KB | 520KB |
| | 1,400 | 305KB | 349KB | 410KB |
| | 1,200 | 229KB | 262KB | 309KB |
| 写真B（3072×3072、975KB） | 1,800 | 323KB | 378KB | 457KB |
| | 1,600 | 261KB | 304KB | 366KB |
| | 1,400 | 208KB | 240KB | 288KB |
| | 1,200 | 159KB | 183KB | 219KB |

写真の容量は、計画の見積もりの平均250KBより大きい。300MBに入る枚数は、平均550KB（1,800px・品質85）で約550枚、平均370KB（1,600px・品質80）で約800枚。

## 画質

長辺1,800pxの品質85と品質80を、無圧縮の縮小と原寸で並べて確かめた。毛並みと細い線で、品質85・80とも目立つ劣化やブロックは見えなかった。判定は目視で、撮影の条件は2枚だけ。1,600pxは容量だけを測り、画質は比べていない。

## メモリと時間

| 入力 | 処理全体 | 最大RSS | `GOGC=25` のRSS |
|---|---|---|---|
| 写真A（1,200万画素相当、通常のJPEG） | 1.3秒 | 220MB | 171MB |
| 写真B（940万画素、通常のJPEG） | 1.1秒 | 194MB | 未測定 |
| 模擬 2,400万画素、通常のJPEG | 1.9秒 | 368MB | 272MB |
| 模擬 2,400万画素、プログレッシブ（4:2:0） | 2.3秒 | 389MB | 未測定 |
| 模擬 2,400万画素、プログレッシブ（4:4:4） | 2.8秒 | 747MB | 381MB |
| 模擬 1,200万画素、プログレッシブ（4:4:4） | 1.8秒 | 399MB | 未測定 |
| 模擬 12000×2000（細長い） | 1.6秒 | 316MB | 未測定 |
| 模擬 600万画素、16ビットPNG | 0.7秒 | 125MB | 未測定 |
| 模擬 600万画素、透明のPNG | 1.6秒 | 143MB | 未測定 |

処理全体の時間には、4つの品質の符号化を含む。計画の模擬の値（61MB）より大きい。実装では `NRGBA` への写しをやめ、途中の結果を小さくして測り直す。

## 確かめたこと

- 位置情報を含む写真でも、出力にEXIFと位置情報が残らない。
- 出力に色プロファイルが残らない。sRGBの写真では問題にならない。

## 確かめていないこと

- iPhoneの写真とP3色域。手元に写真が無い。
- 図・スクリーンショットの実物のPNG。透明の模擬画像は2,914KBになり、PNGの出力は入力の形によって大きく残る。
- 向きの付いた写真（2枚とも向きの値は1か無し）。
- 本番のVPSでのメモリと時間。
