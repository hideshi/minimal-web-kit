# 共通認証の方式検証（2026-10-30）

対象: `docs/federated-auth-plan.md`。検証開始時の `origin/main` は `c9011a1`。

これはCookieの遷移と失効・障害時の契約を調べる小さな試作であり、OIDC提供機能の実装・適合試験ではない。既存の `features/auth` のコード・DB・Cookieは変更しない。実在するアカウント・ドメイン・本番への通信も使用しない。

## 確認結果

### Cookieの往復

Chromium 150.0.7871.181、Python 3.13.5。別プロセスのA・Bを127.0.0.1の異なるポートで起動し、自己署名証明書でHTTPSを使用した。ブラウザの検証専用プロファイルで証明書検証を無効化し、ホスト解決をループバックに固定した。本番のTLS設定の検証ではない。

- 別サイト: `a.test` と `b.test`。
- 同一サイト・別オリジン: `a.example.test` と `b.example.test`。

| 構成 | A到着時のStrict Cookie | Aの200継続ページからリンク操作後 | BのLax試行Cookie | Bのコールバックで発行したCookie |
|---|---|---|---|---|
| 別サイト・BはLax＋303 | 送られない | 送られる | 送られる | 303後も送られる |
| 別サイト・BはStrict＋303 | 送られない | 送られる | 送られる | 303後は送られない |
| 別サイト・BはStrict＋200とリンク操作 | 送られない | 送られる | 送られる | リンク操作後に送られる |
| 同一サイト・別オリジン（上記3方式） | 送られる | 送られる | 送られる | いずれも送られる |

結論: 推奨の「BはLax、AはStrictと利用者が操作する継続ページ」はこのブラウザで成立した。別サイトのStrict＋自動リダイレクトだけではBにログイン状態を渡せない対照例も得た。Cookie属性の検証であり、state・nonce・PKCE・実際のパスキー認証は組み込んでいない。Firefox・Safariは未検証。

### 停止・再開と競合

Python SQLite 3.46.1のファイルDB・WAL・別接続で次を確認した。

- 停止時に世代を進め、古いコードを削除すると、再開しても古いセッション・未交換コードを拒否できる。
- 利用許可にも世代を持たせると、取り消し・再付与後に古いセッションを拒否できる。
- 別利用者の有効性は変わらない。再ログインした新しい世代は使える。
- 停止とコード交換を同時に開始する競合を40回実行。交換が先に成功した場合も、停止後にその世代を使えない。

さらにGo 1.27.1、キットの `store.NewSQLiteStore` と既存のmoderncドライバで、ファイルDB・独立した接続・`BEGIN IMMEDIATE`を使って同じ主要契約を検査した。競合40回、古いセッション・未交換コードの拒否、別利用者の分離、再ログインとコード再利用の拒否が通った。

いずれも試作の表・SQLを検査している。既存authの停止・Recover・GC・世代更新を統合した実装の検査ではない。コードの期限、再利用時の発行済み連携の取り消し、署名済みのログイン結果との世代の結び付けは未検証。

### Aへの毎要求照会と障害

別プロセスのA・B、別DB、ループバックHTTPで、サーバー間照会の試作を検査した。検証用の固定クライアント資格情報を使用し、ブラウザCookieはBでハッシュ照合した。製品用の資格情報・CSRF・暗号化通信の実装ではない。

| 条件 | Bの結果 | Bセッション |
|---|---|---|
| 有効 | GET・POSTとも200、要求ごとにAへの照会回数が増える | 維持 |
| Aが401・500・タイムアウト・不正な本文・別subを返す | 503、操作しない | 維持し、回復後に再確認して200 |
| Aのプロセス停止 | 503、操作しない | 維持 |
| Aで停止 | 401、操作しない | 削除 |
| 停止中はBを開かず、再開後に古い世代でアクセス | 401、操作しない | 削除 |
| 再開後に新しい世代でログイン | 200 | 新規セッション |

拒否されたPOSTによる更新は0件。全ケース後も成功したPOST1件だけがDBに残ることを確認した。

このHTTP試作ではTLSエラー、照会同時数の制限、障害側の短期遮断、鍵更新・クライアント資格情報の更新は未検証。503の回復は一時障害を解除したケースで確認し、プロセス再起動による回復は対象外。

## 再実行

追加のPythonパッケージやnpmは不要。Python 3.13以降・Chromium・OpenSSLが必要。

```sh
python3 docs/experiments/federated-auth/transport_and_revocation.py
python3 docs/experiments/federated-auth/availability.py
go test -race -v ./docs/experiments/federated-auth
```

Pythonの試作は専用の一時ディレクトリを各スクリプトの隣に作り、DB・証明書・ブラウザプロファイルを終了時に削除する。サーバー・ブラウザも終了する。Goの試作は `t.TempDir()` を使う。ローカルのポートを利用するため、その利用が許可された環境で実行する。

`transport_and_revocation.py` は別サイトStrict＋303のCookie欠落も結果として出力する。この欠落自体は比較対象として期待する観察結果であり、推奨方式の成功とは区別する。

## 計画への反映と次の区切り

- Aのauth内部で原子的に失効させる方針、BのLax、Aの継続ページ、sub＋世代の照会を詳細設計の第一候補にする。承認済みの実装仕様とは扱わない。
- 実際のOIDCログインは、提供側・利用側の実装方式を選定してから検証する。[zitadel/oidc](https://github.com/zitadel/oidc)は提供側・利用側、[coreos/go-oidc](https://github.com/coreos/go-oidc)は利用側の比較候補。今回は依存を追加しておらず、ライセンス・推移依存・仕様対応を含む最終選定は未完了。
- 詳細設計ではデータ台帳・APIの拒否表・復旧・世代の原子的な更新対象を確定し、保存データ・通信・依存・Cookie等の変更をまとめて承認に出す。
- この検証の成功だけで、OIDC対応済み・本番利用可能とは判断しない。
