# デザイン改善計画（ナビとリンクの反応、サイトと管理画面の統一）

状態: 2026-10-30、3節と、9.3節の優先度「高」を実装した。外部のモデルのレビューの反映と残りは10節にある。9節に部品の差異の調査結果がある。

## 1. 目的と範囲

公開ページのリンクとメニューは、マウスを乗せたときの変化が小さく、今いるページも分からない。デジタル庁のサイトの作りを参考に、次の3点を直す。

1. ヘッダーのナビの見た目と、マウスを乗せたときの反応
2. 今いるページの表示
3. 本文などのリンクの、マウスを乗せたときの反応

作らないもの: ドロップダウンのメニュー、ナビの階層、JavaScriptでの開閉、外部のCSSフレームワーク、デジタル庁の配色やロゴの流用、カードやボタンの作り直し。

## 2. 今の作りと参考にしたサイトの違い

デジタル庁のトップページの配信中のHTML・CSSを、2026-10-30に読んで確かめた。見た目の値は将来変わることがある。キット側は `internal/web/static/css/style.css` と各レイアウトの現状。

| 場面 | デジタル庁の一番上のメニュー | キットの公開ナビ |
|---|---|---|
| ふだん | 下線なしの文字 | 下線つきの青いリンク |
| マウスを乗せたとき | 薄い灰色（`#f2f2f2`）の丸い背景と下線 | 文字の色が少し濃くなるだけ |
| クリックしている間 | 専用の指定なし | 専用の指定なし |
| キーボードで選んだとき | 黄色の背景と濃い色の枠 | 共通の `:focus-visible` の枠 |
| 今いるページ | 丸い枠線と太字（`is-active`） | 印なし |
| 押せる範囲 | 高さ2rem以上で、文字の周りに余白がある | 文字の部分だけ |

本文のリンクは、デジタル庁ではマウスを乗せると下線が3pxになり、キットでは色が少し濃くなるだけ。

## 3. 変更の案

### 3.1 ヘッダーのナビ

- 対象は `header nav a` にする。素の `nav` はページ送り（`.pagination`）にも当たるため、そこには手を入れない。公開の6レイアウトと管理画面のレイアウトのナビは、どれも `<header>` の中にある。
- ふだんは下線をなくし、余白を付けて、押せる範囲を広げる。
- マウスを乗せたら、灰色の丸い背景と下線を出す。`@media (hover: hover)` では囲まない。リンクは押すと別の画面へ移るためタッチの端末でも反応が残りにくく、囲むとヘッドレスのChromeで反応を確かめられないため。
- 背景の色は `#f2f2f2` にして、CSS変数を足す。リンクの色との対比は、`--color-primary`（`#004098`）で8.58:1、`--color-primary-hover`（`#002b66`）で12.2:1。どちらもWCAG 2.1 AAの4.5:1を超える。
- フォーカスの表示は、今の `:focus-visible` のまま変えない。背景の上でも枠が見えることを確かめる。

ナビから下線を外すと、ナビの中のリンクを色と位置で見分けることになる。ナビはリンクの集まりだと構造から分かるため、本文のリンクの下線は残したまま、ナビだけ外す。文字と背景の対比は、色だけで見分けていないことの証明ではないため、WCAGの適合を宣言するものではない。

状態の見分け方は、今いるページは枠線と太字、マウスを乗せると背景と下線、フォーカスは共通の黒と黄の枠とする。枠線は普段から透明で確保し、状態が変わっても大きさを変えない。ログアウトのボタンは `header nav a` に当たらないため、余白と行の高さをナビのリンクとそろえる。

### 3.2 今いるページの表示

`aria-current` の表示の指定は `style.css` にあるが、付けているのは管理画面のレイアウトだけで、公開のレイアウトには無い。

- 属性の値は、画面と一致するリンクには `aria-current="page"` を付ける。詳細ページ（`/news/3`）の親のリンク（`/news`）には `aria-current="true"` を付ける。
- `/#features` のようなページ内リンクには付けない。
- 見た目は、丸い枠線と太字にする。今の `nav a[aria-current="page"]` の下線3pxは、マウスを乗せたときの表示と区別するために置き換える。管理画面のナビにも効くから、管理画面の撮影でも確かめる。
- 公開キャッシュのある画面でも、印はURLごとに同じなので、利用者ごとの情報は入らない。Cookieも保存データも増えない。

判定に使う値は、描画のデータの `CanonicalPath` にする。トップ・プライバシーポリシー・お知らせ・カタログ・お問い合わせ・固定ページの公開画面は、この値を渡している（Baseのトップだけ渡していなかったため足した）。404とセッション破棄の確認には値が無く、印は出ない。値が無くても描画が失敗しないよう、関数の引数は `any` で受ける。

`Handler.Render` に値を足す形は取らない。各機能は `Render` を通らず、自分で `ExecuteTemplate` を呼ぶためである（2026-10-30にコードで確認）。判定の置き場所は2案ある。

| 案 | 内容 | よい点 | 弱い点 |
|---|---|---|---|
| A: Coreの関数に寄せる（採用） | `componentFuncs` にテンプレートの関数 `navCurrent` を足す。`{{with navCurrent $.CanonicalPath .Href}} aria-current="{{.}}"{{end}}` の形で、`page`・`true`・空を返す | 判定が1か所で済み、テストも1か所でよい。共通の解析の経路を通る全レイアウトと自作のレイアウトで使える。親のリンクの判定も書ける | Coreの関数が1つ増える。予約の関数名になる |
| B: 機能ごとに直す | 各レイアウトで `{{if eq .CanonicalPath "/news"}}` と比べる | Coreを変えない | 同じ判定が6レイアウトに並ぶ。テンプレートには前方一致の関数が無く、親のリンクの判定を書けない |

`navCurrent` の規則: 対象は単一の `/` で始まるサイト内のパスだけで、外部のURL・相対のURL・`?` や `#` を含むリンクには付けない。完全に一致すれば `page`、`/catalog` と `/catalog/3` のように `リンク + "/"` で始まれば `true` にする。`/` は完全一致だけにする。`/catalog-x` のような似た名前には当たらない。末尾の `/` は別の経路として扱う（`/about/` は固定ページでは404のため）。

管理画面は、機能が渡す `Current`（画面が属するナビのリンク）が要求のパスと一致すれば `page`、違えば `true` にする。入力の失敗で一覧の経路へPOSTした場合は、作成画面でも `page` になるが、許容する。

`navCurrent` の名前は、部品が使う関数名として利用側が上書きしない約束にとどめ、`static-head` のように解析で止める検査は作らない。

### 3.3 本文などのリンク

`a:hover` に `text-decoration-thickness: 3px` を足す。`a.btn` は下線が無いので影響しない。`:active` の指定は足さない。

## 4. 動きのあるUIの段

`docs/ui-guidelines.md` の1段目（標準のHTML・CSSとサーバー側の描画）だけで作る。JavaScriptは増やさない。ドロップダウンを作らないのは、今のナビに開く必要のある階層が無いため。

## 5. 承認境界と保存データ

5つの承認境界のどれにも当たらない。CSSは既存の `style.css` を直し、新しいファイルは作らない。フォーム項目・Cookie・DB列、外部通信、公開範囲、依存は変えない。

案Aは、解析や配信の流れを変えず、テンプレートの関数を1つ足すだけである。ただし、全画面のナビに効くため、実装の前に外部のモデルのレビューを1回受ける。

## 6. 検証

- テスト: 公開ページの描画で、一致するリンクにだけ `aria-current` が付くこと、ページ内リンクには付かないこと。案Aなら部品の単体テストと `docs/components.md` への追記も行う。
- 撮影: `make test-ui` の1100pxと360pxで、公開ナビの折り返しと、余白を足した後の高さを見る。リンクが多いサイトでは、ナビが複数行になる。
- ブラウザでの確認: マウスを乗せた状態とフォーカスの状態を撮る。Site有効・無効の両方と、管理画面を見る。
- 全体: `go test ./...` と `make verify`。

## 7. 利用者の決定（2026-10-30）

1. 判定の置き場所は案Aにする。
2. 詳細ページの親のリンクに印を付ける。値は `aria-current="true"` にする（`/catalog/3` を見ているときに「カタログ」が分かるため。管理画面は、すでに編集画面でも親のリンクに印が出る）。
3. 管理画面のナビは同じ見た目にそろえる。`header nav a` なら追加の作業は要らない。
4. 管理画面に、著作権表示だけのフッターを足す。
5. 予備の4レイアウトのナビに、ほかの機能へのリンクを足す修正は、別の作業にする（9.2節）。予備の4レイアウトのフッターは、4つとも同じ文言のため変えない。Siteと文言が違うのは、Siteの `/privacy` にだけ免責事項があり、紹介の文言も運営者の書き換えを前提にしているためで、そろえない。

## 8. 進め方

1. 外部のモデルのレビューを受ける。
2. 3.3節の本文のリンクと、3.1節のナビを1つ目のコミットにする。
3. 3.2節の今いるページの表示を2つ目のコミットにする。
4. 9.3節の優先度「高」を3つ目のコミットにする。「中」「低」は、高を直した後の画面を見て範囲を決める。
5. それぞれ6節の検証を通し、main へ早送りで取り込む。CSSの版はURLに付くので、配備の後は `docs/deploy.md` の10節に沿って確かめる。

## 9. サイトと管理画面の統一と、部品の差異

### 9.1 調べ方と範囲

2026-10-30に、`style.css`・`components.html`・各テンプレートを読み、`make test-ui` の撮影（1100px・360px）と、Site有効の配信中の詳細ページの撮影を見比べた。使われていないクラスは、テンプレートとCSSのクラス名を機械的に突き合わせた。

見ていないもの: ログイン画面、Site有効の状態での管理画面以外の全画面、マウスを乗せた状態。撮影の見本には、Site有効の公開ページ、お知らせとカタログの公開の詳細、ログイン画面が無い。9.3節の12で足す。

### 9.2 骨組みの差

| 箇所 | Site | 予備の4レイアウト | Baseのレイアウト | 管理画面 |
|---|---|---|---|---|
| ブランドの名前 | リンク | リンク | リンクなし | リンクなし。「サイトを表示」が別にある |
| サブタイトル | あり | なし | あり（Siteと文言が違う） | 「管理画面」 |
| ヘッダーの並び | `.site-header-inner` | `.site-header-inner` | 使っていない | `.site-header-inner` |

- ナビの見た目は、3.1節でそろう。ログアウトのボタンは、ナビのリンクと同じ高さにする。

- Baseのフッターは、`.footer-inner` の左右の並びにそろえる。文言はセッションの説明なので変えない。
- 予備の4レイアウトのナビはリンクが固定で、`.NavLinks` を受け取っていない。Siteを無効にしてお知らせとカタログを有効にすると、`/news` から `/catalog` へのナビのリンクが無い。直すには、各機能へナビのリンクを渡す口が要るため、今回の統一とは別に判断する。

### 9.4 残す差

- 管理画面の一覧は表、公開の一覧はカードのままにする。管理画面は列で見比べ、公開ページは読むためのもので、用途が違う。
- 管理画面の `noindex` と、ページのタイトルの「管理画面」の表記は残す。
- 公開ページだけの部品（ヒーロー、ステップ、FAQ）は、管理画面に持ち込まない。

### 9.5 Coreに寄せるか

差異の多くは `style.css` の1か所で直せるため、Coreの部品を増やさない。ヘッダーとフッターの部品化は、Baseへの一本化と同じくナビのデータの渡し方まで変わるため、今回は行わない。例外は、9.3節の5の任意の印で、`form.Field` と `field` の部品を変える。

### 9.6 再発を防ぐ検査

- 撮影に加えて、`test/template_test.go` に、公開の一覧のカードが共通のクラスを使うことと、`（任意）` をラベルの文字に直接書かないことの検査を足す。
- 文字色の直書きは、CSS変数にまとめた後に、変数の定義以外で禁止する検査を足す。

## 10. レビューの反映と実施状況（2026-10-30）

実装の前に、外部のモデル（Codex・gpt-6.1-sol）のレビューを受けた。指摘はコードで確かめ、次のとおり反映した。

| 指摘 | 対応 |
|---|---|
| Baseのトップに `CanonicalPath` が無く、値が無いと描画が失敗するおそれ | Baseのトップに足し、関数の引数を `any` にして、値の無い画面のテストを足した |
| リンクのURLの扱いが未定義 | 3.2節の規則にし、境界値のテストを足した |
| 管理画面の親のリンクが `page` のまま | 要求のパスで `page` と `true` を分けた |
| `main p` は部品の余白を上書きする | 詳細度0の `:where(main, article, section) > p` にした。カードの中の段落には効かせない |
| 表の最小の幅は列によって効き方が違う | `th, td` は5em、本文の表は6emのままにした。日時は `td time` で折らず、狭い画面では表を横に動かす |
| ログアウトの高さは別に指定が要る | `header nav .btn` で余白と行の高さをそろえた |
| 検証の範囲が足りない | Site有効の公開ページとログイン画面を3つの幅で撮り、320pxで横にはみ出さないこと、3つの状態が見分けられることを `test/browser/public_test.go` で確かめる |
| `.card > .btn` は意図より広い | `form.card > .btn` にした。その後、利用者の判断で、幅40rem未満ではフォームと `.action-bar` のボタンを全幅にし、40rem以上だけ文字の幅で左寄せにした（どちらの手でも押せるようにするため） |

実施したもの: 3節、9.2節、9.3節の1〜6と12。

見つけた課題: お問い合わせの一覧は、360pxで「内容」の列が狭く、行が高くなる。横に動かせば読めるため、残している。

確かめていないもの: 文字の200%拡大、文字間隔の変更、カタログのhtmxの履歴の復元、支援技術での読み上げ。

残り: 9.3節の7〜11と13〜18（12は実施済み）。予備の4レイアウトのナビは別の作業にする（7節）。
