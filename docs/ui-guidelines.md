# UIの作り方の方針 (ui-guidelines.md)

動きのあるUIを作るときの判断の順番と、使う技術ごとの決まりです。規約の要点は `AGENTS.md` の「コア原則 3」にあり、この文書はその詳細です。

## 1. 方針：3段で考える

| 段 | 使うもの | 対象 | 承認 |
|---|---|---|---|
| 1 | 標準のHTML・CSS（＋サーバー側の描画） | 開閉、モーダル、メニュー、ツールチップ、入力の検査、一覧・詳細・フォーム送信 | 不要 |
| 2 | htmx | サーバーとのやり取りを、ページを読み直さずに行いたい箇所（絞り込み検索、行の編集、送信後の一部差し替え等） | 必要（承認境界4・5） |
| 3 | Alpine.js 等 | 標準の要素で作れない部品（キーボード操作に対応したコンボボックス、並べ替え等） | 必要（承認境界4・5） |

- 上の段で作れるものを、下の段で作らない。迷ったら1段目で作り、使い勝手の問題が確認できてから次の段を検討する。
- 2段目のライブラリは htmx に決めておく。導入するときは、ライブラリの1ファイルをバージョンを固定してリポジトリに置き、`/static/` から配信する（npmは使わない）。更新時は差分と変更履歴を確認する。
- JavaScriptが動かない環境でも、重要な操作（送信、削除、ログイン以外の画面移動）は普通のリンクとフォームで行えるようにする。

## 2. 1段目：標準の要素でできること

ブラウザが、役割・開閉状態・キーボード操作・フォーカスの扱いを最初から持っているため、自分で作るよりアクセシビリティの面で確実です。

| 要素 | できること | 例 | 注意 |
|---|---|---|---|
| `<details>` / `<summary>` | クリック・Enter・Spaceで中身を開閉する。開閉状態は支援技術に伝わる | FAQ、補足説明、絞り込み条件の折りたたみ | 同じ `name` 属性を付けると、1つだけ開くアコーディオンになる（比較的新しい機能） |
| `<dialog>` | モーダル・非モーダルの画面を出す。モーダルでは背面が操作できなくなり、Escで閉じ、フォーカスが中に移る | 確認画面、入力フォームの小窓 | 開くには `command="show-modal"`（下記）かJSが要る。`<form method="dialog">` のボタンで閉じられる |
| `popover` 属性 | ボタンで要素を浮かせて表示する。外側のクリックやEscで閉じ、最前面に出る | メニュー、ヘルプの吹き出し、通知 | `popovertarget` 属性のボタンで、JSなしで開閉できる（2024年に主要ブラウザがそろった） |
| `command` / `commandfor` 属性 | ボタンから `<dialog>` や `popover` を、JSなしで開閉する | 「削除する」ボタンで確認の `<dialog>` を開く | Chrome・Edge 135、Firefox 144、Safari 26.2 以降（2025年12月にそろった）。古い端末では動かないため、重要な操作には別ページの確認等の代わりを残す |
| `:has()`・`:focus-within` 等のCSS | 子要素の状態に応じて見た目を変える | 入力エラーがある欄の枠を強調する | 見た目だけで、状態の伝達はHTML側で行う |
| 入力の属性（`required`・`pattern`・`type="email"`・`type="date"` 等） | 送信前の入力チェックと、日付等の入力部品 | 必須項目、日付の選択 | サーバー側の検証は必ず残す |

## 3. 2段目：htmxを入れる場合の決まり

- **CSP**: `script-src 'self'` のままにする。`new Function()` を使う機能（`hx-on`、イベントの絞り込み、`js:` で始まる値）は使わない。
- **スタイル**: インジケーター用のスタイルの差し込みを無効にし、見た目は `style.css` のクラスで作る（CSPが `<style>` の差し込みを許さないため）。
- **CSRF**: 状態を変える要求では、既存のCSRFトークンをヘッダーで送る。
- **変化の通知**: 差し替える領域に `aria-live` 等を付け、結果が支援技術に伝わるようにする。
- **フォーカス**: 差し替え後のフォーカスの移し先を決める（結果の見出し、エラーの欄等）。
- **URL**: URLを変える操作は、そのURLを直接開いたときにページ全体を返す。
- **エラー**: 通信失敗・セッション切れ・入力エラーの表示方法を決める（既定ではエラー応答を画面に反映しない）。
- **段階的な強化**: JSが動かなくても、元のリンクとフォームとして動くようにする。

## 4. htmxの限界

次のものが中心になるアプリでは、htmxでは作りにくい。別の構成を検討する。

- 一文字ごとの即時反応など、通信の遅れが目立つ操作
- 複数の部品にまたがるブラウザ側の状態、元に戻す操作、送信前の楽観的な表示
- ドラッグ＆ドロップ、リッチテキストの編集、グラフ、地図などの高度な部品
- オフラインでの利用、リアルタイムの共同編集

## 5. 3段目を使う条件

- WAI-ARIAの作成パターンに沿って、役割・状態の属性とキーボード操作を作り込む。
- 実機のキーボード操作と画面読み上げソフトで確認する。
- Alpine.js を使う場合は、`unsafe-eval` が要らないCSPビルドを使う（式の書き方に制限がある）。

## 6. カタログで承認済みの利用範囲

公開一覧のGET検索・ページ送りだけに、固定版htmxとcatalog.jsを使う。script-srcはこの画面だけself。設定はheadのmetaに置き、allowEval/allowScriptTags/includeIndicatorStylesはfalse、selfRequestsOnlyはtrue、historyCacheSizeは0。historyRestoreAsHxRequestはfalse、refreshOnHistoryMissはtrueとして、履歴復元はページ全体の取得に戻す。管理画面・詳細では読み込まない。
検索後はフォームにフォーカスを残し、ページ送り後は結果見出しへ移す。固定したrole=status領域を更新する。失敗時は元の結果を残し、通常GETでの再試行を提供する。新しい検索で古い要求を取り消す。管理操作は通常のフォームのcsrf_tokenを使う（Admin.Formは現状ヘッダーのトークンを検証しない）。
Alpine.jsはタグ選択の比較試作（`experiment/catalog-tags` ブランチ）でだけ評価しており、本体には採用していない。比較の内容と結果は [catalog-ui-comparison-plan.md](catalog-ui-comparison-plan.md) にある。
