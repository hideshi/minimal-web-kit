# お問い合わせの受信箱の強化 実装計画

状態: 2026-10-31、外部レビュー（Claude Fable 5.1）の指摘を反映した。実装は未着手。利用者が決めたのは、CRMの前にお問い合わせを強化する案と、対応中の延長（案B、4節）まで。10節の項目と、承認境界2（DB列の追加）の承認を得てから実装する。

## 1. 目的と範囲

受信箱を、内容を読むだけの場所から、対応の進み具合を管理できる場所にする。CRMを作る前に、顧客の台帳を持たずに、必要な対応を満たせるかを確かめる。

- 状態を、未読・対応中・完了・スパムの4つにする。
- 運営者のメモを1件に1つ書けるようにする。
- 一覧を、残っている仕事だけに絞れるようにする。
- 対応中のものは、更新を続ける間、削除を延ばす。上限を設ける。

作らないもの: メールの送信、返信の機能、担当者の割り当て、やり取りの履歴の積み上げ、顧客ごとのまとめ、受付から上限を超える保存、公開フォームの項目の追加、メモを書いた人と日時の記録。これらが必要になったら、CRMを別に設計する。

変えないもの: 公開フォームの項目と画面、受信箱を見られるのが管理者だけであること（CONTACT-INV-3）、スパム対策、受付上限（CONTACT-INV-5。未読だけを数え、1時間・1日の上限は受付日時で数えるため、影響しない）。

## 2. 状態

| 状態 | 値 | 今との対応 |
|---|---|---|
| 未読 | `unread` | 同じ |
| 対応中 | `active` | 新規 |
| 完了 | `done` | 新規。今の既読（`read`）の移行先は10節で決める |
| スパム | `spam` | 同じ |

状態の変更は、今までどおり詳細の画面のボタン（POST）で行い、開いただけでは変えない。どの状態からも、ほかの状態へ変えられる。同じ状態への変更のボタンは出さない。

## 3. メモ

- 列 `note`（TEXT NOT NULL、既定は空文字）。2,000文字以内で、`form.Text` で検査する。
- 詳細の画面に入力欄を置き、`POST /admin/contact/{id}/note` で保存する。`AdminForm` で守る。
- 入力欄の説明に、送った人の返信先以外の個人情報や、病歴など配慮が必要な情報を書かないよう注意書きを付ける。
- メモは送った人の情報を含みうるため、データ台帳とプライバシーポリシーの保存項目に「対応の記録（運営者のメモ）」を足す。
- ログに中身を出さない。`Message` の `LogValue` に含めず、ハンドラでも `r.PostForm` やエラーの文を出さない。入力の失敗で再描画する経路も含めて、カナリアで確かめる。
- 表示は `form.Paragraphs` で描く。
- 2人の管理者が同時に書くと、後の保存が勝つ。ドメインモデルの「守らない範囲」に書く。

## 4. 保持と削除

| 状態 | 削除の時期 |
|---|---|
| 未読 | 受付から保持期間（既定90日） |
| 対応中 | 最後の更新から保持期間。ただし受付から上限（既定365日） |
| 完了 | 受付から保持期間 |
| スパム | 受付から保持期間 |

- 列 `last_activity_at`（INTEGER NOT NULL、既定値なし）を足す。受付のときは `created_at` と同じ値にする。既定値を付けないのは、古い実行ファイルが行を足したときに、削除の時期が狂わないよう、失敗させるため。
- 更新として数えるのは、対応中のもののメモの保存と、対応中への状態の変更だけ。開いて読んだだけでは更新しない。未読・完了・スパムのものでメモを保存しても、削除の時期は変わらない。
- 上限の設定は `CONTACT_ACTIVE_MAX_DAYS`（既定365）。`CONTACT_RETENTION_DAYS` 以上、365以下で、範囲外は起動時にエラーにする。2つの値を読んだ後に比べ、エラーの文言に設定値を含めない。保持期間と同じ値にすると、延長は効かない。
- `Purge` は次の条件で消す。判定は1つのSQL文で行う。

```sql
DELETE FROM contact_messages
WHERE (status <> 'active' AND created_at <= :retention_limit)
   OR (status = 'active' AND (last_activity_at <= :retention_limit OR created_at <= :max_limit))
```

- 画面に出す削除の時期は、ストアの関数 `DeleteAt` を1か所にまとめる。`Purge` と同じ境界値で、「消える1秒前は残り、ちょうどで消える」ことを両方で確かめる。
- 対応中のものを、受付から保持期間を過ぎた後で別の状態（完了・未読・スパム）にすると、次の削除の処理（起動時と1時間ごと）で消える。受付から保持期間を過ぎた対応中のものの詳細の画面に、「対応中以外にすると、1時間以内に削除されます」と表示する。完了のボタンだけに付けない。

**キットの約束への影響**: 今の説明は「受付から90日で、状態に関係なく削除」である。対応中のものは最長1年残ることになるため、9節の文面をすべて直す。

## 5. 画面

| 画面 | 型 | 変更 |
|---|---|---|
| `/admin/contact` | 一覧 | 既定は未読と対応中だけ |
| `/admin/contact/all` | 一覧 | 全件。同じテンプレートで描く |
| `/admin/contact/{id}` | 詳細 | メモの欄、状態のボタン、削除の時期を足す |

- 絞り込みを `?view=all` にしないのは、部品 `pagination` が `Base` に `?page=` を付ける作りで、クエリを重ねられないため。
- 一覧の列は増やさない。削除まで7日以内のものは、状態の列に「対応中（あと3日）」のように添える。列を増やすと、横スクロールの目安（`docs/components.md` の3節）を外れる。
- 空のときの文は「〜はまだありません。」で終える（`test/admin_ui_test.go` の検査）。両方の一覧で必要になる。
- 完了の通知の鍵（`adminNotices`）は状態の値で引くため、`read` を外して `active`・`done` を足す。
- 動きのあるUIは足さない。`docs/ui-guidelines.md` の1段目で作る。JavaScript・CSSファイルは増やさない。

## 6. DBの移行

`status` の CHECK 制約に値を足すには、SQLiteでは表を作り直す必要がある。`ALTER TABLE ... ADD COLUMN` だけでは足りない。

- 旧形式の判定は、`PRAGMA table_info(contact_messages)` に `last_activity_at` が無いことで行う。表が無ければ新規として `migration.sql` だけを流す。
- 作業用の表 `contact_messages_legacy` が残っていたら、起動を止める（`features/news/news.go` の前例と同じ）。
- 新しい表の定義を Go に二重に持たない。1つのトランザクションで、次の順に行う。
  1. 旧表を `contact_messages_legacy` に改名し、旧表の索引を消す。
  2. `migration.sql` を流す（新しい表と索引ができる）。
  3. 行を写す。`read` は10節の移行先にし、`note` は空、`last_activity_at` は `created_at` にする。
  4. `sqlite_sequence` の旧表の値を、新しい表の名前へ写す。写した行の最大の `id` では足りない（最新の行を削除した後は、旧表の値の方が大きい）。旧表の値が無い場合も扱う。
  5. 旧表を消す。
- 移行で削除の時期を延ばさない。`last_activity_at` に移行の時刻を入れない。
- 2回起動しても壊れないこと、途中で失敗したら元のままであること、移行後の列が新規のDBと一致すること、最新の行を消してから移行しても次の `id` が巻き戻らないことを、テストで確かめる。
- `Init` は `Purge` と待受の前に直列で走るため、移行中に同時に動く処理は無い。ただし、移行中に手動のバックアップが重なると、起動に失敗することがある。
- 古い実行ファイルは新しい表を扱えない。戻すときは、更新の前のバックアップから戻す。

## 7. 承認境界と保存データ

- 承認境界2に当たる: 列 `note`・`last_activity_at` の追加。
- 利用目的: `note` は対応の引き継ぎ、`last_activity_at` は保持期間の計算。
- 保持と削除: 4節のとおり。お問い合わせと一緒に消える。スパムのまとめての削除でも消える。バックアップの複製には、その複製の保持期間のあいだ残る。
- ほかの境界（依存、外部通信、CSS・JSファイル、公開範囲）には当たらない。

## 8. 検証

- 不変条件: CONTACT-INV-2 の番号は使い回さない。定義とテストの参照を外し、次を足す。
  - CONTACT-INV-9: 対応中は最後の更新から保持期間、それ以外は受付から保持期間で削除し、どの状態も受付から上限を超えて残らない。
  - CONTACT-INV-10: 読むだけ、対応中以外のメモの保存では、削除の時期が延びない。
  - CONTACT-INV-11: 移行で削除の時期が延びず、`id` の採番が巻き戻らない。
  - CONTACT-INV-7 の文言を「GETは状態・メモ・最終更新を変えない」に改める。
- 単体: 状態ごとの削除の境界値（保持期間のちょうど・1秒前、上限のちょうど）、`DeleteAt` と `Purge` の一致、対応中から完了・未読・スパムにしたときの削除、対応中のメモの保存と対応中への変更で延びること、メモの上限、設定の範囲と相互の検査。
- HTTP: メンバーと未ログインの拒否、CSRF、GETで状態もメモも変わらないこと、全件の画面のページ送りと `?page=` の不正な値。
- 台帳: `docs/data-inventory.md` の7節と実スキーマの照合。
- 管理画面: `test/admin_ui_test.go` の見本に、全件の画面、対応中と完了の詳細、メモの入力の失敗を足す。
- 撮影: 受信箱と詳細を1100pxと360pxで見る。
- カナリア: メモの中身がログに出ないこと。
- 全体: `go test ./...`、`make verify`、`make test-ui`。

## 10. 利用者が決めること

1. 今の既読（`read`）の移行先を、対応中と完了のどちらにするか。推奨は完了。削除の時期はどちらでも同じで、既定の一覧に過去の既読が並ばない。
2. メモの上限は2,000文字でよいか。推奨はこの値。
3. 一覧の既定は、未読と対応中だけでよいか。推奨はこの形で、全件の画面へのリンクを置く。
4. 承認境界2: 列 `note`・`last_activity_at` の追加を承認するか。

## 11. 進め方

1. 10節を決める。
2. ドメインモデルと台帳を直す。
3. 表の移行、状態の改名、保持の処理を、1つ目のコミットにする。CHECK 制約から `read` が消えるため、状態を使う画面・通知・見本も同じコミットで直す。
4. メモと一覧の絞り込みを、2つ目のコミットにする。
5. 文書と文面を、3つ目のコミットにする。
6. それぞれ8節の検証を通し、main へ早送りで取り込む。

## 12. レビューの記録

2026-10-31、Claude Fable 5.1 のレビューを受けた（Codex・GPT 6.1 Sol は利用の上限で実行できなかった）。主な指摘はコードで確かめ、本文に反映した。

- 対応中から未読・スパムへ変えても消える経路（4節）
- `sqlite_sequence` の引き継ぎの順序と、表の定義の二重化（6節）
- CONTACT-INV-2 の番号の使い回し（8節）
- `docs/deploy.md` の記述との矛盾と、文面の直し漏れ（9節）
- 「対応中のものの状態の再設定」を更新から外したこと（4節）
- 「削除まで」の列をやめたこと（5節）

レビューで確かめられなかったこと: modernc.org/sqlite でDDLを含むトランザクションの取り消しが効くこと。実装の最初にテストで確かめる。`ServeMux` で `/admin/contact/all` が `{id}` より優先されることも、実装で確かめる。
