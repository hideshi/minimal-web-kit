# 固定ページ機能 実装計画

状態: 2026-10-30、利用者が10節の9項目と承認境界2（DBの表の追加）を承認した。外部レビュー（Fable）の指摘は本文に反映済み（11節）。本文の読む規則の正本は [richtext.md](../richtext.md)。8節の順に実装する。

## 1. 目的と範囲

管理画面で、`/about` のような1階層のURLのページを作り、下書き・公開できるようにする。本文には見出し・箇条書き・リンク・表を書ける。

- 新しい同梱機能 `pages`（`features/pages/`、`make add-pages`・`remove-pages`）。管理者認証を使う（有効な間は `remove-auth` を拒否する）。
- 本文の書き方（3節）はCoreの部品（`internal/web/richtext` パッケージと、`components.html` の描く部品）にする。後からお知らせ等でも使えるが、**今回はお知らせの本文は変えない**。
- 個人情報を載せる場所ではない（公開する文章）。閲覧者の情報は取得しない。
- 作らないもの: 画像・ファイルの添付、HTMLの直接入力、階層のあるURL（`/company/about`）、版の履歴、予約公開、ページごとのレイアウトの選択、JavaScriptでのプレビュー、スラッグを変えたときの旧URLからの転送、検索結果用の説明文の列（本文の冒頭から作る）。

## 2. 画面と経路

### 2.1 公開ページは「Coreの受け皿」で受ける

独立経路に `GET /{slug}` を登録すると、Coreの経路（`/privacy`・`/account/...`）より具体的と判定され、それらを取ってしまう（レビューで実際の構成を再現して確認）。そのため、固定ページは**どの経路にも当たらなかったときの受け皿**として、Coreに口を1つ足して受ける。

- Coreのルートの `/` のハンドラで、Coreの経路（`appMux`）に当たる経路があるかを `Handler(r)` で確かめ、無ければ受け皿の口（新しい任意のインターフェース。例: `FallbackFeature`）に渡す。当たる経路があれば、今までどおり処理する（405のときもパターンは空になるため、受け皿は「1階層の GET・HEAD」以外を今までの応答に戻す）。
- 固定ページは、1階層・書式どおりのスラッグ・公開中なら描き、それ以外は404を返す。404はSiteの404の画面を描く（配線で `NotFoundFeature` のハンドラを受け取る口 `SetNotFound` を足す。Siteが無ければ `http.NotFound`）。`/about/`・`/foo/bar` も同じ404になる。
- Coreの経路は何も取られず、公開ページはCookieを照合しない独立の処理のまま。スラッグの検査は復号後の値に当て、canonical は常に `/スラッグ` にする。
- 経路の受け皿はCoreの変更のため、固定ページとは別のコミットにし、`/privacy` と独立経路の既存のテストが通ることを先に確かめる。

### 2.2 スラッグ（URL）

- 英小文字・数字・ハイフン、2〜40文字、ハイフンで始まり・終わらない。DBでも長さを `CHECK` する。
- **登録済みの経路と同じスラッグは保存できない**。判定は、組み上がった経路に `GET /スラッグ` を作って当て、受け皿以外に当たれば使えない、とする（配線の最後にこの関数を固定ページに渡す。将来の機能にも追随する）。接頭辞だけの語（`static`・`admin`・`api` 等）は受け皿に落ちるため、固定の一覧でも拒否する。
- 同じスラッグの重複（UNIQUE違反）は、500ではなく欄のエラー（400）にする。
- 公開中のページのスラッグを変えると、旧URLは404になる。編集画面に注意を出す。

### 2.3 管理画面

| 経路 | 型 | 内容 |
|---|---|---|
| `GET /admin/pages` | 一覧 | タイトル・URL・状態・ナビの順・更新日時 |
| `GET /admin/pages/new`、`POST /admin/pages` | 作成・編集 | 作成 |
| `GET /admin/pages/{id}`、`POST /admin/pages/{id}` | 作成・編集 | 編集 |
| `POST /admin/pages/preview` | 作成・編集 | プレビュー（保存しない） |
| `POST /admin/pages/{id}/publish`・`unpublish` | — | 公開・下書きに戻す |
| `GET /admin/pages/{id}/delete`、`POST .../delete` | 削除の確認 | 削除 |

- 編集できるのは管理者とメンバー（カタログと同じ）。管理画面は `test/admin_ui_test.go` の見本の表（プレビューは成功で画面を返す送信、上限超えは失敗の見本）に足す。
- **プレビュー**: 作成・編集の両方の画面に「プレビュー」ボタンを置く（フォームの中で「保存」を先に置く。Enterキーは最初のボタンで送るため）。入力の検査を通し、誤りがあれば描かずに400で欄のエラーを返す。通れば、保存せずに、入力を残したフォームの上に描いた本文を出す。保存も公開状態の変更もしない。`docs/components.md` の「作成・編集」の型に「プレビューの節を持つ場合」の1行を足す。
- 管理画面に、書き方の早見表を `<details>` で出す。

## 3. 本文の書き方（Coreの部品 `richtext`）

書き方を絞ったMarkdownを、キットのコードで**構造（ブロックと文字の並び）に読み**、`html/template` の部品で描く。HTMLの文字列を組み立てず、`template.HTML` も使わない。

### 3.1 書ける要素

| 要素 | 書き方 | 出力 |
|---|---|---|
| 見出し | 行頭の `## `・`### ` | `h2`・`h3`（`h1` はページのタイトル） |
| 段落 | 空行で区切る。段落の中の改行はそのまま改行 | `p`（改行は `br`） |
| 箇条書き | 行頭の `- ` | `ul`（クラス付き） |
| 番号付き | 行頭の数字＋`. `（番号の値は無視） | `ol`（クラス付き） |
| 表 | `\| 列 \| 列 \|` の次の行が区切り行（`\|---\|---\|`）、続けて行。直前の行に `表: 説明` を書くと、それを `caption` にする | `table`（1行目は `th scope="col"`）。説明が無ければ `caption` は「表N（直前の見出し）」、見出しも無ければ「表N」。Nは文書の順 |
| リンク | `[文字](URL)` | `a`（同じタブで開く） |
| 強調 | `**文字**` | `strong` |

### 3.2 読む規則（正本は [richtext.md](../richtext.md)。2026-10-30にレビューを受けて固めた。以下は要約で、食い違うときは richtext.md を正とする）

本文は保存の前に `form.Text` を通す（CRLFをLFに揃え、改行・タブ以外の制御文字を拒否し、UTF-8を検証する）。読む処理はLFだけを前提にし、「文字」はruneで数える。

**行の種類を決める順番**（各行は生の行のまま判定する）:
1. 空行 → 今のブロックを閉じる。
2. 先頭が `## ` または `### ` → 見出し（今のブロックを閉じる）。段落の途中でも見出しにする。
3. `表: ` で始まり、次の行が表の開始 → 表の説明。
4. `|` で始まり、次の行が区切り行 → 表の開始。区切り行が無ければ段落の文字。表は、`|` で始まる行が続く間続く。
5. 先頭が `- ` → 箇条書きの項目。先頭が `数字. ` → 番号付きの項目。リストの途中で別の種類の行が来たら、リストを閉じる。
6. それ以外 → 段落の行。先頭に空白がある `  - x` も段落の文字。
- `\` は次の1文字を文字にする。行の種類の判定は `\` を見る前に行う（`\##` は段落）。表の列は、先に「`\` の付いていない `|`」で分け、各セルをその後で文字の並びとして読む（セルの中で `\|` を使える）。

**文字の並びの規則**（見出し・段落・項目・セルの中）:
- `**…**` → 強調。`[文字](URL)` → リンク。閉じない `**`・`[` は文字のまま。
- URLの中の `)` と空白は終端。強調の中のリンク、リンクの中の強調は扱わない（文字のまま）。

### 3.3 リンクのURLの許可

- 外部: `net/url` で解析し、スキームを小文字で比べて `https` だけ。ホストが空でなく、ユーザー情報（`user@`）が無いこと。
- サイト内: `/` で始まり、`//` と `/\` で始まらない。
- どちらも、空白・制御文字・`\` を含まないこと（`NavLinks` の検査と揃える）。
- 許可しないURL（`http://`・`mailto:`・`javascript:`・`data:` 等）のリンクは、書いた文字をそのまま出す。

### 3.4 上限とテスト

- 上限: 本文5万文字（rune）、表は20列・200行まで。超えたら欄のエラー。
- 表のテスト: 3.1〜3.3の各規則、組み合わせ、書けない記号、危ないURL（`javascript:`・`data:`・`//`・`/\`・大文字のスキーム・空白・制御文字・ユーザー情報）。
- ファズテスト（`testing.F`）の性質: 止まらない、出力の大きさが入力に比例する、`href` の値が全部 `https://` か `/` で始まる、描いた結果から既知のタグを取り除いた残りに `<` が無い。種に `[`・`**`・`|` を5万個並べた入力を入れ、遅さが二次関数的にならないことを確かめる。`go test` は種だけを回すため、部品のレビューの前に `-fuzz` を時間を決めて回し、記録を計画に残す。
- 描く部品は、管理画面の検査（素の `ul`・`ol` を出さない、表に `caption` と `th scope`）とテンプレートの検査（ファイルごとの `<table`・`<caption`、`<th`・`<th scope=` の数）を満たす形で、`components.html` に置く。見出し・表・リストの見た目は `style.css` にクラスを足す。

## 4. ナビゲーションとsitemap

- ページごとに「ナビに出す順」（空ならナビに出さない）を持つ。公開中で順のあるページだけを、Siteのヘッダーのナビに載せる。ナビの中では、固定のリンク（ホーム等）と他の機能のリンク（お知らせ等）の後に、順の小さい順に並べる。
- **スナップショット方式**: 固定ページは、公開中で順のあるページのリンクをメモリに持ち、起動時と、保存・公開・非公開・削除の後に作り直す。描画時にDBを読まない。
- 口の変更は2点だけ: (1) Coreと `NavLinkConsumer.SetNavLinks` を「リンクを返す関数」を受け取る形にする。(2) `Registry.NavLinks` を関数を返す形にする。お知らせ・お問い合わせ・カタログの `NavLinkFeature` は定数を返すまま変えない。Siteは `layoutData` と `handleSitemap` で関数を呼ぶ。起動時の書式検査は静的な機能の分だけ行い、固定ページの分はスラッグの書式が保証する。公開ナビでは `NavLink.AdminOnly` を使わない。
- DBを直接書き換えた場合はスナップショットが古くなる（再起動で直る）。
- 公開中のページは sitemap.xml に載せる（既存の `SitemapFeature`）。
- `/`・`/privacy`・`/news` は60秒の公開キャッシュがあるため、ナビの変化はそれらの画面では最大60秒遅れて見える。

## 5. データ（承認境界2）

```sql
CREATE TABLE IF NOT EXISTS pages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    slug TEXT NOT NULL UNIQUE CHECK (length(slug) BETWEEN 2 AND 40),
    title TEXT NOT NULL,
    body TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL DEFAULT 'draft' CHECK (status IN ('draft', 'published')),
    nav_order INTEGER CHECK (nav_order IS NULL OR nav_order >= 0),
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL
);
```

- 公開する文章で、個人情報は入れない運用（画面で案内する）。作者のアカウントは保存しない。明示削除まで保持する。`owners` に紐づけない。

## 9. 守らない範囲・残るリスク

- Markdownの方言との完全な互換は目指さない。書ける要素は3.1の表だけで、他は文字として出す。
- 外部のリンク先の内容と安全は確かめない。
- 版の履歴が無いため、上書きした本文は戻せない（バックアップから戻す）。
- スラッグを変えると旧URLは404になる（転送は作らない）。
- 固定ページを有効にすると、Siteだけの静的書き出し（`export-static`）は使えない。
- ナビの変化は、公開キャッシュのある画面では最大60秒遅れる。DBを直接書き換えたときは再起動まで反映されない。
