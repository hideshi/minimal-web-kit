# MCP対応の計画

状態: 計画のレビューを反映済み（2026-10-31）。実装の前。今の仕様ではない。

## 目的

AIエージェントが、MCPを通じて、お知らせ・カタログ・固定ページを読み、登録・編集できるようにする。読み取りは確認なしで行い、変更はクライアントの利用者の確認を経る。別の機能も同じ口で足せるようにし、機能ごとの有効・無効を管理者が決める。認証はキットの共通認証基盤を使う。

## 確定した判断

- 確認はクライアント側で利用者に求める。サーバーに承認待ちの表や承認画面は作らない。
- サーバーは、確認の手順を通らない書き込みを拒否する。人の操作かは証明できない。クライアントを自動応答に設定した場合は、その利用者の責任とする。
- 読み取りは確認なしで、下書きも読める。
- 初版に削除は入れない。公開と非公開は編集と別のツールにする。
- 境界2（設定とトークンの表）と境界5（`/mcp` と `.well-known` の公開経路）は承認済み。
- まずキットに入れる。紹介サイトへの適用は別に決める。

## 実測（Claude Code 2.1.316、手元の調査用サーバー）

| 確かめたこと | 結果 |
|---|---|
| 接続 | `MCP-Protocol-Version: 2026-07-28`、`server/discover`、`Mcp-Method`・`Mcp-Name`、応答はJSONで動く |
| 能力の宣言 | 要求の `_meta` の `clientCapabilities` に `elicitation` がある |
| `_meta["anthropic/requiresUserInteraction"]` | 非対話では許可の設定があってもサーバーに届かない。対話では確認が出る |
| `input_required` の `elicitation/create` | 対話では画面が出て、サーバーの文がそのまま表示され、`requestState` と `inputResponses` で送り直す |
| 応答 | 承諾は `accept` で実行。却下は `decline`、非対話は `cancel` で実行しない |
| 確認の回数 | 2回（許可の確認、elicitation） |
| 確認の形 | 必須の欄を置くと承諾だけで進めない。空の `properties` なら承諾・却下だけになる |

OAuthの実測（同じ版、事前登録の `clientId` と固定の `callbackPort`、JWTなしの不透明なトークン、リフレッシュなし）:

| 確かめたこと | 結果 |
|---|---|
| 発見 | 401の `WWW-Authenticate` から、保護リソースの情報と認可サーバーの情報を読む |
| 認可 | `/mcp` の操作でブラウザが開く。PKCE S256と `resource` が届く。`nonce` は使わない |
| 自動登録 | 動かない構成でも問題なし。`registration_endpoint` を出さなくても、事前登録のIDで進む |
| 交換 | 成功し、`server/discover`・`tools/list`・ツールの呼び出しが通る |
| 期限切れ | `expires_in` の後はトークンを送らず401になり、「sign in again」のエラーを返す。自動でブラウザは開かず、利用者が `/mcp` から再認可する。書き込みは実行されない |

期限切れでは、利用者が許可の確認に `Yes` と答えた後にエラーが出る。リフレッシュなしの8時間は、記事の作業には足りると判断して初版の方針にする。長時間の自動処理は対象にしない。

確かめていないこと: Claude Code以外のクライアント、再起動をまたいだトークンの保持、`bypassPermissions` やフックでの動き。

## 全体の形

| 部品 | 役割 |
|---|---|
| `internal/mcp` | JSON-RPC、ツールの一覧と呼び出し、確認の組み立てと検証。標準ライブラリのみ |
| `features.MCPFeature` | 機能がツールを申告する口 |
| `features/mcp` | 任意の機能。`/mcp`、保護リソースの情報、`/admin/mcp` の設定画面 |
| `features.TokenVerifier` | Bearerトークンの検証の口。`auth/oidcop` が実装し、後で `federatedauth` も実装できる |

```go
type MCPEffect int

const (
	MCPWrite MCPEffect = iota // ゼロ値は書き込み。宣言を省いても確認なしにしない
	MCPRead
)

type MCPTool struct {
	Name, Title, Description string
	InputSchema              json.RawMessage
	Effect                   MCPEffect
	Read                     func(ctx context.Context, p MCPPrincipal, in json.RawMessage) (MCPResult, error)
	Prepare                  func(ctx context.Context, p MCPPrincipal, in json.RawMessage) (MCPPlan, error) // 検査だけで、変更しない
	Apply                    func(ctx context.Context, p MCPPrincipal, in json.RawMessage, state string) (MCPResult, error)
}

type MCPFeature interface {
	Feature
	MCPTools() []MCPTool
}

// TokenVerifier は無効と確認不能を区別する。確認不能では実行しない。
type TokenVerifier interface {
	VerifyBearer(ctx context.Context, token, resource string) (MCPPrincipal, error)
}
```

- 起動時に検査する。読み取りは `Read` だけ、書き込みは `Prepare` と `Apply` だけを持つ。未知の `Effect`、名前の重複、検証の口の0件・複数件は起動を止める。
- 書き込みは1つの共通の処理からだけ呼ぶ。検証に失敗したら、別の経路で実行しない。
- 共有の型は標準ライブラリだけに依存する所に置く。`MCPPrincipal` はアカウント、クライアント、スコープ、認可の世代を持つ。業務の権限は要求ごとにアカウントから読む。

## 書き込みの流れ

1. トークンのスコープ `mcp:write`、機能の有効、引数を確かめる。
2. クライアントが `elicitation` のフォームを宣言していなければ、変更せずにツールのエラーを返す。空の `elicitation: {}` はフォームの宣言として扱う。
3. `Prepare` で検査し、対象の状態ハッシュと確認の文を作る。保存の関数を試しに呼ばない。
4. 確認の文と `requestState` を付けて `input_required` を返す。
5. 送り直しで `requestState` を検証する。応答はサーバーが発行したキーだけを読み、欠落・不正な型・未知の `action` では実行しない。
6. 番号を排他的に消費してから、結果を判定する。`accept` のときだけ先へ進む。`decline`・`cancel` でも消費する。
7. トークン、スコープ、認可の世代、機能の有効をもう一度確かめて、`Apply` を実行する。
8. `Apply` は、状態ハッシュの照合と保存を1つのトランザクションで行う。変わっていたら保存しない。

失敗したら、同じ確認を使い回さず、確認からやり直す。応答が届かなかった場合も再送は拒否する。実行は最大1回で、結果の到達は保証しない。

### requestState

- 用途の識別子、形式の版、アカウント、クライアント、認可の世代、ツール、必要なスコープ、引数のハッシュ、対象の状態ハッシュ、機能の設定の世代、発行日時、期限（10分）、番号を入れ、長さの上限を固定する。
- HMAC-SHA256で守る。鍵は起動ごとにメモリで作り、使用済みの番号もメモリに持つ。単一プロセスの前提で、再起動すると確認は無効になる。件数に上限を付け、超えたら新しい確認を断る。
- 機能を無効から有効に戻しても、古い確認は使えない（設定の世代が変わる）。

### 対象の版

新しい列は足さない。操作の意味に関わる保存状態（本文、公開状態、公開日時、スラッグ、ナビの順、分類）のハッシュを版にする。`updated_at` は秒単位なので使わない。変更して元に戻した場合は同じ版になるが、内容が確認時と同じなので許す。管理画面からの変更も、このハッシュの差で検出できる。

### 確認の文

- 固定の操作の説明と、入力に由来する引用を分ける。エージェントの説明は入れない。
- 対象、現在の公開状態、変更する項目、差分を見せる。公開中の内容が変わること、公開日時の変更で公開されること、URLの変更は強調する。
- 表示できる上限（初版は4000文字）を超える変更は、確認を出さずに拒否して、管理画面を案内する。省略した文で確認を通さない。
- `requiresUserInteraction` は書き込みのツールに付ける。確認は2回になるが、1回目は設定で飛ばしにくく、2回目は内容を見せられるため、両方残す。
- `annotations` はヒントとして付ける。守りの根拠にしない。

### 管理画面との共有

HTTPの解析と表示を、入力の検査、保存、コミット後の処理から分ける。MCPも同じ関数を通す。読んだ結果、お知らせとカタログのハンドラはストアを呼ぶだけで、コミット後の処理も無いため、切り出しが要るのは固定ページのナビの更新だけだった。

- 固定ページ: 正規化、経路の予約、重複の検査と、コミット後の `afterChange`（ナビの更新）。
- お知らせ: `admin_pages.go` の日時の解析、空欄で既存の日時を保つ処理、初回の公開日時。
- カタログ: タグの関連の張り直し。`NewTags` はツールの入力に含めず、未知の入力として拒否する。

省略、空、null、全置換の意味はツールごとに固定する。

## 初版のツール

| 機能 | 読み取り | 書き込み |
|---|---|---|
| お知らせ | 一覧、取得 | 作成、編集、公開、非公開 |
| カタログ | 一覧、取得、カテゴリとタグの一覧 | 作成、編集、公開、非公開 |
| 固定ページ | 一覧、取得 | 作成、編集、公開、非公開 |

カタログのカテゴリとタグの追加・編集は入れない。既存のIDの指定だけを受ける。

## 有効・無効

- 表 `mcp_feature_settings`（機能名、有効、世代、更新日時）。行が無ければ無効。
- `/admin/mcp` は管理者だけが変えられる（`AdminPage`・`AdminForm`）。画面の型は一覧。
- 無効の機能は `tools/list` に出さず、呼び出しも拒否する。確認の途中で無効にされたら実行しない。設定を変えるたびに世代を進める。
- `MCPFeature` を実装した機能が増えても、既定で無効のまま。

## 認証

MCPサーバーはリソースサーバーとして動く。アカウント、パスキー、連携先、利用許可、世代は共通認証基盤のものを使う。

既存のOIDCログインは変えない。今の `request` は `GetAudience()` がクライアントID、スコープが `openid` 固定で、`validAuthorizeQuery` は `nonce` を必須にし、`resource` を許さない。ここを広げると既存のログインを壊すおそれがあるため、**MCPの認可の経路を別に作る**。SDKの `Storage` は広げない。

| 項目 | 内容 |
|---|---|
| アクセストークン | 不透明な乱数。ハッシュをDBに保存し、要求ごとに引く。JWTは使わない |
| 束縛 | アカウント、クライアント、`resource`、スコープ（`mcp:read`・`mcp:write`）、3つの世代、発行日時、期限 |
| 要求ごとの検証 | ハッシュ、期限、`resource`、スコープ、固定した世代と今の世代の一致、アカウントの状態 |
| 期限 | 無操作で失効はさせず、発行から8時間で固定する |
| リフレッシュトークン | 初版は発行しない。期限が来たら再認可する |
| 認可の要求 | 認可と交換の両方で `resource` を検査し、保存した値と一致させる。PKCE S256必須、`nonce` 不要 |
| クライアントの種類 | 登録情報で公開か秘密かを明示する。要求に秘密が無いことを理由に公開として扱わない |
| ループバック | 登録したスキーム、IP、パスは固定で、ポートだけ可変にする |
| コードの再利用 | 公開クライアントでは、コード、保存した戻り先、PKCEの一致を必須にする。不一致では世代を進めない。AUTH-INV-18に公開クライアントの条件を足し、回帰テストを先に書く |
| 案内 | 保護リソースの情報（`resource`・`authorization_servers`）、認可サーバーの情報（`none`・S256等を実装どおりに）、401と403のBearerの応答 |
| 同意の画面 | クライアント名、リソース、読み取りと書き込みの別、戻り先を出し、認可要求に結びつける |
| 登録 | コマンドで事前に登録する。CIMDとDCRは初版に入れない |
| 破棄 | 期限切れのトークンは `PurgeFeature` で消す。ログアウトでは消さず、世代と明示の取り消しで止める |

認可の仕様と実装の対応表を作って、抜けを防ぐ。`federatedauth` の検証は初版では作らない。作るなら、認証基盤への問い合わせで検証する。

不透明なトークンにすると、署名の検証、JWTの種別の区別、SDKの変更が要らなくなる。要求ごとのDBの読み取りは増えるが、キットの対象は1台の構成なので問題にならない。

`internal/mcp` と `features/mcp` はOIDCのライブラリをimportしない。`TestArchitecture_FederationDependenciesStayOptional` の対象にMCPと3機能を足す。

## HTTPの守り

- `POST /mcp` だけ。GETとDELETEは405。応答はJSONのみで、SSEと `Mcp-Session-Id` は使わない。
- CookieもCSRFトークンも使わない独立経路。Bearerは必須。
- `guard.SameOrigin` は使わない（`Sec-Fetch-Site` 必須で、CLIを拒否し、`null` を許す）。設定した公開Originと比べる専用の検査を作る。`Origin` が無ければ通し、不一致、`null`、複数、不正な形は403にする。`Host` も固定で確かめ、プロキシのヘッダーは信じない。CORSは許可しない。
- `Mcp-Method`・`Mcp-Name` を本文と照合する。`MCP-Protocol-Version` と `_meta` の不一致は400（`HeaderMismatch`）、未対応の版は400（構造化エラー）。対応するのは `2026-07-28` だけで始める。
- 本文の大きさ、JSONの深さを固定で制限し、バッチは受け付けない。
- JSONは型付きで読む。重複キー、末尾の別のJSON、不正なUTF-8、範囲外の数値、未知の項目は拒否する。ハッシュの対象と実行の対象は、同じ解析の結果にする。汎用のJSON Schemaの検証器は作らない。
- 回数の制限はメモリで持つ。認証前の全体の上限と同時実行の上限、認証後のアカウントとクライアントごとの上限。超えたら429。件数の上限と破棄の条件を決める。
- 一覧の件数、応答の大きさ、DBの処理時間を制限する。
- ログは登録済みのツール名と固定の分類だけ。未知の名前は固定の分類にする。引数、本文、`requestState`、`inputResponses`、`Authorization`、OAuthの値、panic、生のエラーを出さない。カナリアで確かめる。

## 保存データ（境界2）

`mcp_feature_settings`、アクセストークンの表（ハッシュ、アカウント、クライアント、`resource`、スコープ、世代、発行日時、期限）、公開クライアントの列（種類、ループバック）、MCP用の認可コード。書き込みの引数は保存しない。保持と削除は `docs/data-inventory.md` に書き、プライバシーポリシーの見直しを `minimal-web-kit-privacy` で行う。

## 不変条件（案）

| 番号 | 条件 |
|---|---|
| MCP-INV-1 | `Effect` を省いたツールは書き込みとして扱い、未知の値や関数の混在は起動を止める |
| MCP-INV-2 | 書き込みは、検証済みの確認の `accept` が無ければ実行しない |
| MCP-INV-3 | 確認は、アカウント、クライアント、認可の世代、ツール、引数、対象の状態に結びつき、一度だけ使える。却下でも消費する |
| MCP-INV-4 | 確認の後に対象が変わっていたら保存しない。照合と保存は1つのトランザクションで行う |
| MCP-INV-5 | 無効の機能のツールは一覧に出ず、呼び出せず、確認の途中でも実行しない。有効に戻しても古い確認は使えない |
| MCP-INV-6 | 別のリソース向けのトークン、失効した世代、足りないスコープは拒否する。確認不能なら実行しない |
| MCP-INV-7 | 書き込みは管理画面と同じ検査、保存、コミット後の処理を通る |
| MCP-INV-8 | 引数・本文・`requestState`・トークンをログに出さない |
| MCP-INV-9 | 確認の文の枠はサーバーが作り、入力は引用として分ける。省略した内容で確認を通さない |

## 進める順番

2. MCPの認可の経路とトークンの検証。`docs/domain/auth.md`（AUTH-INV-18）をテストと同じコミットで更新する。
3. `internal/mcp`、有効・無効の設定、`features/mcp`。`docs/domain/mcp.md`、`docs/ui/use-cases.md`、`docs/data-inventory.md` を実装と同じコミットで更新する（不変条件の番号は対応するテストが要るため）。
4. 3機能のツール。
5. Claude Codeで通し、トップ・READMEと同梱機能のカードを更新し、完成のレビューを受ける。

## 残る論点

1. 確認の上限の4000文字が、実際の記事に足りるか。
2. 運用でリフレッシュなしの不便が大きければ、系列と再利用の検出を設計して足す。

## レビューの結果（Sol、2026-10-31）

- 採った: 版の照合と保存の原子性、番号の消費の定義、公開クライアントの条件、OIDCとの分離、ディスパッチの一本化、処理の切り出しの範囲、回数制限とJSONの解釈、専用のOrigin検査、確認の文の分離、ログの対象。
- 変えた: JWTとリフレッシュトークンを初版に入れる案をやめた。レビューが「削れる」とした点を採り、不透明なトークンにして、世代の扱いとSDKへの影響を小さくした。
- 採らなかった: 単調な改訂番号。新しい列が要り、内容が同じなら確認の意味は保たれるため。

## 試作品（everything-mcp）の扱い

コードは使わない。依存（Gin、GORM等）、APIの中継と多テナントの構成、`2025-03-26` の仕様がキットと合わない。承認の検査でエラーが起きると実行へ進む点は、まねをしない。

## 作らないもの

サーバー側の承認待ち、削除のツール、お問い合わせのツール、タグの新規作成、JWTのアクセストークン、リフレッシュトークン、`federatedauth` の検証、SSE、Tasks、CIMD、DCR、stdioの配布。
