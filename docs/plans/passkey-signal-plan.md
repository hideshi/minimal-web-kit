# パスキーの状態を端末へ知らせる（Signal API） 実装計画

状態: 2026-11-14、計画の案。外部レビュー（Fable）の前。
仕様の正本は [domain/auth.md](../domain/auth.md)。この計画書は経緯の記録とする。
きっかけ: GoogleChrome/modern-web-guidance のガイド `passkey-management`・`passkey-authentication`・`privacy` を読み、キットと突き合わせた。

## 1. 目的と範囲

サーバーでパスキーを消しても、端末のパスワード管理ソフト（Googleパスワードマネージャー等）には残る。ログインの選択肢に出続け、選ぶと「このパスキーではログインできません」になるだけで、どれが生きているか分からない。

特に大きいのは復旧で、`resetAccountKeys`（`auth-recover`、管理画面の登録URLの発行し直し）は、パスキーを全部消して `webauthn_user_id` も作り直す。古いパスキーが端末にまとめて残る。

WebAuthn の Signal API で、サーバーの状態を端末へ知らせ、使えないパスキーを片付けさせる。

- 対象: `features/auth/static/webauthn.js`、パスキー管理の画面、ログインの応答。
- 対象外: アカウントの呼び名を端末へ知らせる `signalCurrentUserDetails`（キットには呼び名を変える操作が無い）、ログインの欄の自動入力（conditional mediation。今のボタンの方式を変える理由が薄い）、AAGUIDで提供元を表示すること（外部の一覧を読み込むことになり、承認境界3に当たる）。

## 2. 呼ぶ場所

| 場所 | 呼ぶもの | 渡すもの | 効く場面 |
|---|---|---|---|
| パスキー管理の画面（`/admin/passkeys`）を開いたとき | `PublicKeyCredential.signalAllAcceptedCredentials` | `rpId`、本人の `webauthn_user_id`、本人の**有効な**パスキーのIDの一覧 | 自分で消したパスキー（削除の後はこの画面へ戻るため、削除の処理には手を足さない）。複製の疑いで無効になったパスキー |
| ログインの失敗の応答を受けたとき | `PublicKeyCredential.signalUnknownCredential` | `rpId`、ログインに使ったパスキーのID | 復旧の後に残った古いパスキー。ほかの管理者が消したパスキー。アカウントの削除の後に残ったパスキー |

- どちらも、関数があるかを確かめてから呼ぶ。無いブラウザでは何もしない。
- どちらも、失敗しても画面の動きを変えない（`try`/`catch` で握りつぶす。利用者への文言も出さない）。
- `rpId` は、`location.hostname` から作らず、サーバーが渡す（設定の RP ID と一致させるため）。

## 3. サーバーの変更

### 3.1 パスキー管理の画面

- 画面に、`rpId`・`webauthn_user_id`（base64url）・有効なパスキーのIDの一覧（base64url）を `data-` 属性で埋め込む。置き場所は、既にある `#passkey-add-form` か、表示の無い要素1つにする。インラインのスクリプトは使わない（CSPは変えない）。
- パスキーのIDは、今も削除・名前の変更のURLに出ている。新しく画面に出るのは `webauthn_user_id` だけで、これも登録の開始（`/admin/webauthn/register/begin`）の応答で本人に渡している値。
- 有効なパスキーが0件なら、一覧を埋め込まない（JS側も呼ばない）。`AUTH-INV-4` で0件にはならないはずだが、空の一覧は「全部消せ」と同じ意味になるため、二重に守る。
- この画面は `no-store` のまま。

### 3.2 ログインの応答

今は、どの理由で断っても 401 の `login_rejected` を返している。次の1つだけ、別の符号を返す。

| 場合 | 今 | 変更後 |
|---|---|---|
| パスキーが見つからない（`sql.ErrNoRows`）、または無効（`disabled_at` あり） | 401 `login_rejected` | 404 `credential_unknown`（文言は今の `login_rejected` と同じ） |
| 署名の検証の失敗、カウンタの後退、アカウントの停止、`userHandle` の不一致 | 401 `login_rejected` | 変えない |
| DBの失敗 | 503 か 500 | 変えない。**`credential_unknown` を返さない** |

- `getCredential` は、見つからない場合と無効の場合を、どちらも `ErrCredentialUnavailable` で返している。DBの失敗とは既に分かれているので、判定はそのまま使える。
- アカウントの停止は `credential_unknown` にしない。再開すれば同じパスキーが使えるため、端末から消させない。
- ログを分ける: `auth login rejected` の `reason` は今の `credential_unavailable` のまま。

### 3.3 新しい不変条件（案）

- `AUTH-INV-29`: ログインで `credential_unknown` を返すのは、パスキーが見つからないか無効のときだけ。DBの失敗、署名の失敗、アカウントの停止では返さない。
- `AUTH-INV-30`: パスキー管理の画面が端末へ渡す一覧は、本人の有効なパスキーだけで、空の一覧は渡さない。

## 4. 危険と守り

Signal API は「この一覧に無いものは消してよい」「このパスキーは無い」と端末に伝える。間違えると、正しいパスキーを端末から隠させ、ログインできなくなったように見せる。

| 危険 | 守り |
|---|---|
| 一覧の取り違え（他人のパスキー、空の一覧） | 本人の `account_id` で絞る（`AUTH-INV-3`）。空なら渡さない（`AUTH-INV-30`） |
| DBの一時的な失敗で「無い」と伝える | DBの失敗では `credential_unknown` を返さない（`AUTH-INV-29`） |
| **違うDBで起動した**（空のDB、パスキーを登録する前の複製から戻した、DBのパスを取り違えた） | 端末で古いパスキーを選んだ人は、全員 `credential_unknown` を受け取り、端末から消される。後で正しいDBに戻しても、端末の分は戻らない。守りの案は5節 |
| パスキーのIDを知っている人が、そのIDがまだ有効かを確かめられる | 判定は署名の検証の前に行う。IDは推測できない長さの乱数で、知っているのは持ち主の端末と、そのURLを見た人だけ。有効かどうかが分かっても、署名が無ければログインできない。受け入れる |
| 名前やIDの形の誤り | JS側で、base64url の形（`[A-Za-z0-9_-]`、余りの無い長さ）を確かめてから渡す |

## 5. 決めること（レビューで確かめたい点）

1. **違うDBで起動したときの守り**: 案は次のどれか。
   - (a) 何もしない。復旧の手順（`docs/deploy.md` の8節）に「パスキーの登録の後に取った複製から戻す」と書き、取り違えは運用で防ぐ。
   - (b) 有効なパスキーが1件も無いDBでは `credential_unknown` を返さない。空のDBは防げるが、古い複製は防げない。
   - (c) 環境変数で無効にできるようにする。既定は有効。
   僕の推しは (b) と (a) の併用。(c) は設定を増やすほどの効果が無いと見ている。
2. **端末側の扱い**: 外したパスキーを、端末が「隠す」のか「消す」のか、後で一覧に戻せば復活するのかを、各社の公式の資料で確かめてから文書に書く。確かめられないものは「確かめていない」と書く。
3. **承認境界**: JSのファイルは増えず、読み込む画面もCSPも変わらない。保存するデータも増えない。承認済みの例外 `webauthn.js` の処理が増えることが「例外の拡大」に当たるかは、利用者に確かめる（当たらないと見ている）。

## 6. ログアウトの `Clear-Site-Data` を採らない

modern-web-guidance の `privacy` は、ログアウトで `Clear-Site-Data` を送ることを勧めている。採らない。

- `"cookies"` は、応答のオリジンではなく**登録ドメイン全体**（サブドメインを含む）の Cookie を消す（MDN）。同じ登録ドメインの下に、キットから作った別のサイトを置くと、片方のログアウトでもう片方のログインも切れる。キットの使い方（共通認証で複数のサイトをつなぐ）と合わない。
- `"storage"` で消えるのは、アクセス解析の同意（`analytics.js` の localStorage）くらいで、ログアウトのたびに同意を聞き直すことになる。
- `"cache"`: 管理画面は既定の `no-store` で、キャッシュに残らない。
- ログアウトは、サーバーのセッションを消し、管理者の Cookie を消している。これで足りる。

決定は `docs/domain/auth.md` の「守らない範囲」に一文で残す。

## 8. テスト

- Go（`features/auth`）:
  - 見つからないパスキー・無効のパスキーで 404 `credential_unknown`（`AUTH-INV-29`）。
  - 署名の失敗、アカウントの停止、`userHandle` の不一致は 401 `login_rejected` のまま。
  - DBの失敗（閉じたDB等）で `credential_unknown` を返さない。
  - パスキー管理の画面に、本人の有効なパスキーだけが埋め込まれ、無効のもの・他人のものが入らない。0件なら埋め込まない（`AUTH-INV-30`）。
- ブラウザ（`test/browser`）: Chrome の仮想認証器（CDP の WebAuthn ドメイン）で登録・ログインし、`signalAllAcceptedCredentials`・`signalUnknownCredential` を記録用の関数に差し替えて、渡した値を確かめる。仮想認証器が使えない場合は、差し替えだけで画面の読み込み時の呼び出しを確かめる。
- 守りを外して落ちることを確かめる: DBの失敗で `credential_unknown` を返す、無効のパスキーを一覧に含める、空の一覧で呼ぶ。
- 実機: 手元の Chrome と Googleパスワードマネージャーで、消したパスキーが選択肢から消えることを見る（できた段階で）。
