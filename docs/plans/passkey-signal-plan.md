# パスキーの状態を端末へ知らせる（Signal API） 実装計画

状態: 2026-11-14、実装した。外部レビュー（Fable）の指摘（高3・中5・低4）を取り込み、Signal API の扱いを Chrome の公式の資料で確かめた（10節）。5節は利用者が3つとも推しのとおりに決めた。
仕様の正本は [domain/auth.md](../domain/auth.md)。この計画書は経緯の記録とする。
きっかけ: GoogleChrome/modern-web-guidance のガイド `passkey-management`・`passkey-authentication`・`privacy` を読み、キットと突き合わせた。

## 1. 目的と範囲

サーバーでパスキーを消しても、端末のパスワード管理ソフト（Googleパスワードマネージャー等）には残る。ログインの選択肢に出続け、選ぶと「このパスキーではログインできません」になるだけで、どれが生きているか分からない。

特に大きいのは復旧で、`resetAccountKeys`（`auth-recover`、管理画面の登録URLの発行し直し）は、パスキーを全部消して `webauthn_user_id` も作り直す。古いパスキーが端末にまとめて残る。

WebAuthn の Signal API で、サーバーの状態を端末へ知らせ、使えないパスキーを片付けさせる。

- 対象: `features/auth/static/webauthn.js`、パスキー管理の画面、ログインと登録の応答。
- 効く範囲（10節で確かめた）: 知らせをどう扱うかは、パスキーの提供者が決める。公式の資料が「反映できる」と書いているのは Googleパスワードマネージャーだけで、デスクトップの拡張機能の提供者は反映するかを自分で決め、Android 14 以降は端末で有効な提供者すべてに届く。セキュリティキー、Windows Hello、iCloudキーチェーンの扱いは、資料に書かれていない。ブラウザは Chrome・Edge 132 以降（Android の Chrome は 144 以降）、Safari 26 以降で、Firefox は未対応。そのため、ログインの片付けが確実に効くのは、`AUTH_ALLOW_SYNCED_PASSKEYS=true` のサイトで Googleパスワードマネージャーを使う場合で、既定（同期型を拒否）のサイトで効くのは、主に登録の失敗の片付け（2節の3行目）になる。
- 対象外: アカウントの呼び名を端末へ知らせる `signalCurrentUserDetails`（キットには呼び名を変える操作が無い）、ログインの欄の自動入力（conditional mediation。今のボタンの方式を変える理由が薄い）、AAGUIDで提供元を表示すること（外部の一覧を読み込むことになり、承認境界3に当たる）。

## 2. 呼ぶ場所

| 場所 | 呼ぶもの | 渡すもの | 効く場面 |
|---|---|---|---|
| パスキー管理の画面（`/admin/passkeys`）を開いたとき | `PublicKeyCredential.signalAllAcceptedCredentials` | `rpId`、本人の `webauthn_user_id`、本人の**有効な**パスキーのIDの一覧 | 自分で消したパスキー（削除の後はこの画面へ戻るため、削除の処理には手を足さない）。複製の疑いで無効になったパスキー（同期型ではカウンタが働かないので、ほぼ起きない） |
| ログインの応答が `credential_unknown` のとき | `PublicKeyCredential.signalUnknownCredential` | `rpId`、ログインに使ったパスキーのID | 復旧の後に残った古いパスキー。ほかの管理者が消したパスキー。アカウントの削除の後に残ったパスキー |
| 登録の完了の応答が `synced_credential` のとき | `PublicKeyCredential.signalUnknownCredential` | `rpId`、作られたパスキーのID | 同期型を拒否する設定で、同期型のパスキーを作ってしまった（端末にだけ残る） |

- 復旧の後の古いパスキーは、管理画面の一覧では片付かない。復旧で `webauthn_user_id` が変わり、`signalAllAcceptedCredentials` は渡した `userId` のパスキーにしか効かないため。片付くのは、そのパスキーでログインを試したときだけ。
- どれも、関数があるかを確かめてから呼ぶ。無いブラウザでは何もしない。
- どれも、失敗しても画面の動きを変えない（`try`/`catch` で握りつぶす。利用者への文言も出さない）。
- `rpId` は、`location.hostname` から作らず、サーバーが渡す。ログインは `login/begin` の応答の `rpId`、登録は `register/begin` の応答の `rp.id`、管理画面は埋め込んだ値を使う。
- 知らせる条件は、応答の本文の `error` の符号で判定する。状態コードの404だけでは判定しない（前段のプロキシや配備の途中の404で消させないため）。今の `post()` は失敗のとき `message` だけを持つ `Error` を投げるので、符号も載せるように直す。
- 登録の失敗で知らせるのは `synced_credential` だけ。`credential_exists`（同じ認証器が登録済み）では、本物を消させるので、決して呼ばない。ほかの登録の失敗（登録URLの期限切れ等）でも端末にパスキーが残るが、理由の判定を増やさず、今回は対象外とする。

## 3. サーバーの変更

### 3.1 パスキー管理の画面

- 画面に、`rpId`・`webauthn_user_id`（base64url）・有効なパスキーのIDの一覧（base64url）を `data-` 属性で埋め込む。置き場所は、既にある `#passkey-add-form` か、表示の無い要素1つにする。インラインのスクリプトは使わない（CSPは変えない）。
- パスキーのIDは、今も削除・名前の変更のURLに出ている。新しく画面に出るのは `webauthn_user_id` だけで、これも登録の開始の応答で本人に渡している値。画面は `no-store` のまま。
- 有効なパスキーが0件なら、一覧を埋め込まない（JS側も呼ばない）。`AUTH-INV-4` で0件にはならないはずだが、空の一覧は「全部消せ」と同じ意味になるため、二重に守る。
- 3.4節の条件を満たさないサイトでは、埋め込まない。

### 3.2 ログインの応答

今の `handleLoginFinish` は、`getCredential` のどのエラーでも 401 の `login_rejected` を返している（DBの失敗も含む）。次のように分ける。

| 場合 | 今 | 変更後 |
|---|---|---|
| パスキーが見つからない（`sql.ErrNoRows`）、または無効（`disabled_at` あり） | 401 `login_rejected` | 3.4節の条件を満たせば 404 `credential_unknown`（文言は `login_rejected` と同じ）。満たさなければ今のまま |
| 行の `sign_count` が範囲外（壊れた行） | 401 `login_rejected`（`ErrCredentialUnavailable`） | 別のエラーに分け、401 `login_rejected` のまま。「無い」とは伝えない |
| DBの失敗、要求の取り消し | 401 `login_rejected` | `writeStoreError`（競合は503、それ以外は500）。**`credential_unknown` を返さない**。今の挙動の変更になる |
| 署名の検証の失敗、カウンタの後退、アカウントの停止、`userHandle` の不一致 | 401 `login_rejected` | 変えない |

- アカウントの停止は `credential_unknown` にしない。再開すれば同じパスキーが使えるため。
- 判定は `errors.Is(err, ErrCredentialUnavailable)` のときだけにする。
- ログの理由: 見つからない・無効は今の `credential_unavailable`、壊れた行は新しい理由、DBの失敗は `writeStoreError` のイベント名に分ける。拒否のログの件名（`auth login rejected`）は変えないので、通知の「認証の拒否の連続」の数え方は変わらない。
- `errorMessages` に `credential_unknown` を足す。

### 3.3 登録の完了の応答

変えない。`synced_credential` は今も専用の符号で返っている。JS側でだけ知らせる。

### 3.4 知らせてよいサイトの条件

同じ RP ID を、別のDBを持つサイトや環境が使っていると、正しいパスキーを消させる。ログインは `allowCredentials` を空にしているので、端末は RP ID が合うパスキーを全部出す。たとえば `a.example.com` と `b.example.com` が、どちらも `AUTH_RP_ID=example.com` で別のDBを持つとき、Aのパスキーを選んでBにログインすると、Bは「無い」と答え、Aで有効なパスキーが端末から外れる。本番と検証環境、開発の `localhost` を使う複数のプロジェクトでも起きる。

`signalAllAcceptedCredentials` は渡した `userId` のパスキーにだけ効き、`webauthn_user_id` はDBごとの乱数なので、この危険は `signalUnknownCredential` だけにある。ただし、条件は3か所で揃える。

知らせるのは、次のすべてを満たすときだけ。

1. RP ID が `AUTH_ORIGIN` のホストと完全に一致する（上位ドメインを RP ID にしていない）。
2. RP ID が `localhost` でない。
3. 有効なパスキーが1件以上あるDBである（空のDB、全体の復旧から登録し直すまでの間は知らせない）。

1・2で防げない共有（同じホスト名を、別のDBの検証環境が使う等）は、文書で「同じ RP ID を別のDBで使うなら、この機能が正しいパスキーを消させる」と案内する。

## 4. 危険と守り

Signal API は「この一覧に無いものは消してよい」「このパスキーは無い」と端末に伝える。間違えると、正しいパスキーを端末から外させ、ログインできなくなったように見せる。

Googleパスワードマネージャーは、どちらの知らせでも、パスキーを消さずに「隠す」。隠したパスキーは、後の `signalAllAcceptedCredentials` の一覧にIDが入っていれば戻る（10節）。ほかの提供者の扱いは資料に無いので、設計は戻せない前提のままにする。

| 危険 | 守り |
|---|---|
| 一覧の取り違え（他人のパスキー、空の一覧） | 本人の `account_id` で絞る（`AUTH-INV-3`）。空なら渡さない（`AUTH-INV-30`） |
| DBの一時的な失敗で「無い」と伝える | DBの失敗では `credential_unknown` を返さない（`AUTH-INV-29`） |
| RP ID を別のDBと共有している | 3.4節の1・2の条件。残りは文書で案内 |
| 空のDBで起動した | 3.4節の3の条件 |
| **複製から戻した**（パスキーの登録より前の複製、DBのパスの取り違え） | 複製より後に登録したパスキーは、戻したDBに無い。そのパスキーでログインを試すと、端末から外される。後で正しいDBに戻したとき、Googleパスワードマネージャーなら、本人がパスキー管理の画面を開けば一覧に入って戻る（ただし、隠れたパスキーではログインできないので、別のパスキーでログインする必要がある）。ほかの提供者では戻るか分からない。`docs/deploy.md` の8節に、この向きを書く（今は「複製より後のパスキーの削除は戻る」だけ） |
| 画面を描いた後に一覧が古くなる（別の端末で同時にパスキーを足した、復元されたタブで再実行された） | 窓は狭い。受け入れる。開き直せば正しい一覧で知らせ直す |
| 認証なしで、パスキーのIDがまだ有効かを確かめられる | 見つからない場合は公開鍵が無いので、署名を確かめてから答えることはできない。IDは推測できない長さの乱数で、URLのIDは `Referrer-Policy: no-referrer` で外へ出ない。今も応答の時間差で区別できる。有効かが分かっても、署名が無ければログインできない。受け入れる |
| 値の形の誤り | JS側では、空でないことと、文字が `[A-Za-z0-9_-]` だけであることを確かめる。長さの検査はしない（パディング無しの base64url で `length % 4 === 0` を求めると、16バイトの `webauthn_user_id` の22文字が落ちる）。細かい形はブラウザが TypeError で断る |

## 5. 決めること（利用者に確かめる）

決定（2026-11-14、利用者）: 1は足さない。2は例外の拡大に当たらない。3は足す。

実装で計画から変えた点:
- 登録の同期型の知らせも3.4節の設定の条件（1・2）にそろえるため、`register/begin` の応答に `signalUnknown` を足した（3.3節は「変えない」としていた）。JSは `create` に渡す前に取り除く。DBの条件（3）は、作ったばかりのパスキーには関係しないので見ない。
- 知らせの完了は最大1秒だけ待ってから移動する（ブラウザの実装が待たせても、ログインを止めない）。
- RP ID が `*.localhost` のときも知らせない（できた段階のレビューの指摘）。
- ログインでパスキーを読めなかったとき、利用者の切断（`context.Canceled`）は障害のログに出さない。

1. **止める設定を持つか**: 3.4節の自動の条件だけにするか、環境変数で止められるようにもするか。設定が無いと、事故のときは配備し直して止めることになる。僕の推しは、設定を足さず、自動の条件と文書で守ること（設定の数を増やさないため。キットは配備し直しが数秒で済む）。
2. **承認境界**: JSのファイルは増えず、読み込む画面もCSPも変わらない。保存するデータも増えない。ただし `webauthn.js` の性格が、「結果をサーバーへ渡すだけ」から「端末のパスキーの状態を変える」に変わる。これが「例外の拡大」に当たるか（当たらないと見ている）。
3. **ログインの成功のときにも一覧を知らせるか**: Chrome の資料は、`signalAllAcceptedCredentials` をパスキーを消したときと**ログインのたび**に呼ぶよう勧めている。ログインのたびに呼べば、管理画面を開かなくても片付き、誤って隠したパスキー（Googleパスワードマネージャー）もログインのたびに戻る。そのためには、`login/finish` の成功の応答に `rpId`・`webauthn_user_id`・有効なパスキーの一覧を足し、JS が知らせてから移動する。応答を受け取るのは、署名を確かめた本人だけ。僕の推しは「足す」（管理画面と同じ値・同じ守りで、効く場面が増えるため）。

## 6. ログアウトの `Clear-Site-Data` を採らない

modern-web-guidance の `privacy` は、ログアウトで `Clear-Site-Data` を送ることを勧めている。採らない。

- `"cookies"` は、応答のオリジンではなく**登録ドメイン全体**（サブドメインを含む）の Cookie を消す（MDN の原文で確かめた）。同じ登録ドメインの下に、キットから作った別のサイトを置くと、片方のログアウトでもう片方のログインも切れる。サイトが1つでも、公開側の匿名セッションの Cookie（`internal/web/session.go`）や、共通認証の途中の Cookie まで消える。
- `"storage"` で消えるのは、アクセス解析の同意（`analytics.js` の localStorage）くらいで、ログアウトのたびに同意を聞き直すことになる。
- `"cache"`: 管理画面は既定の `no-store` で、キャッシュに残らない。
- ログアウトは、サーバーのセッションを消し、管理者の Cookie を消している。これで足りる。

決定は `docs/domain/auth.md` の「守らない範囲」に一文で残す。

## 8. テスト

- Go（`features/auth`）:
  - 見つからないパスキー・無効のパスキーで 404 `credential_unknown`（`AUTH-INV-29`）。
  - 署名の失敗、アカウントの停止、`userHandle` の不一致、壊れた行は 401 `login_rejected` のまま。
  - DBの失敗で `credential_unknown` を返さず、503か500になる。
  - 3.4節の条件を外れる設定（RP ID が上位ドメイン、`localhost`、有効なパスキーが0件）では `credential_unknown` を返さず、画面にも一覧を埋め込まない。
  - パスキー管理の画面に、本人の有効なパスキーだけが埋め込まれ、無効のもの・他人のものが入らない。0件なら埋め込まない（`AUTH-INV-30`）。
- ブラウザ（`test/browser`）: `federated_test.go` と同じく、Chrome の仮想認証器（CDP の WebAuthn ドメイン）で登録・ログインする。`signalAllAcceptedCredentials`・`signalUnknownCredential` を、`defer` のスクリプトより前に記録用の関数へ差し替え、次を確かめる。
  - 管理画面を開くと、有効なパスキーの一覧で呼ぶ。
  - `credential_unknown` で呼び、`login_rejected`（401）や符号の無い404では呼ばない。
  - 登録の `synced_credential` で呼び、`credential_exists` では呼ばない。
  - 関数が無いブラウザ（差し替えで消す）でも、登録・ログイン・管理画面が今までどおり動く。
- 守りを外して落ちることを確かめる: DBの失敗で `credential_unknown` を返す、3.4節の条件を外す、無効のパスキーを一覧に含める、空の一覧で呼ぶ、`credential_exists` で呼ぶ。
- 実機: 手元の Chrome と Googleパスワードマネージャーで、消したパスキーが選択肢から消えることを見る（できた段階で）。

## 9. レビュー

`minimal-web-kit-design` の3節の4・6（認証と守りに触れる）に当たるため、計画の段階と、できた段階で、外部のモデル（Fable）のレビューを受ける。

計画の段階のレビュー（2026-11-14）で取り込んだもの:
- 今のログインは、DBの失敗も401にしている。404にするのは `ErrCredentialUnavailable` だけにし、DBの失敗は503か500へ、壊れた行は別のエラーへ分ける。
- 同じ RP ID を別のDBのサイトや環境が使うと、普通の構成で正しいパスキーを消させる。3.4節の条件を足した。
- 既定の設定（同期型を拒否）では、ログインの片付けはほとんど効かない。効く範囲を1節に書き、登録の失敗の片付けを足した。
- base64url の長さの検査の誤り、JSの判定を符号で行うこと、`errorMessages` の追加、複製から戻す向きの危険、一覧が古くなる場合、署名の前に答えることの扱い、仮想認証器の既存の試験、Clear-Site-Data の補強。

できた段階のレビュー（2026-11-14、高0・中1・低6）で取り込んだもの:
- JS側の守り（同期型だけで知らせる、サーバーが許すときだけ、空の一覧、符号の無い404、知らせを待ってから移る）を外しても、ブラウザの試験が落ちなかった。応答を差し替える試験と、遅れて解決する記録の関数を足した。
- 無効のパスキーだけのDBの試験、`*.localhost` の除外、利用者の切断のログ、ポート違いの環境と「有効なパスキーがあるか」が外から分かることの文書。
- 実機の確認（8節の最後）: 2026-11-14 に、本番の紹介サイト（同期型を許可）で、利用者が Chrome（シークレットのウィンドウ）と Googleパスワードマネージャーで確かめた。管理画面で登録URLを鍵のリセット付きで発行し直した後、古いパスキーでログインを試すと 404 の `credential_unknown` になり、そのパスキーがログインの選択肢から消えた。ログインの成功とパスキー管理の画面での一覧の知らせ、同期型の登録の拒否の知らせは、実機では見ていない。

## 10. 確かめた資料（2026-11-14）

- Chrome「Keep passkeys consistent with credentials on your server with the Signal API」（https://developer.chrome.com/docs/identity/webauthn-signal-api 、2024-11-29 更新）:
  - 知らせをどう扱うかは提供者が決める。Googleパスワードマネージャーは反映でき、デスクトップの拡張機能の提供者は反映するかを自分で決める。
  - `signalAllAcceptedCredentials` で一覧に無いパスキーは「隠す」扱いで、すぐには消さない。後の一覧に入っていれば戻す。
  - 有効なパスキーを一覧から漏らすとログインできなくなる。空の一覧は、そのユーザーのパスキーを全部隠しうる。
  - `signalAllAcceptedCredentials` は、パスキーを消したときと、ログインのたびに呼ぶ。`signalUnknownCredential` は、パスキーが無いためにログインが失敗したときに呼ぶ。未認証のときは、パスキーの数を明かさないよう `signalUnknownCredential` を使う。
  - 対応: Chrome・Edge 132、Safari 26、Firefox は未対応。
- Chrome「Signal API for passkeys available on Chrome for Android」（https://developer.chrome.com/blog/signal-api-android 、2025-12-05）:
  - Chrome 144 から Android でも使える。Android 14 以降は、端末で有効な提供者すべてに知らせが届く。
  - 以前は「無い」と知らせたパスキーを完全に消していたが、今の Googleパスワードマネージャーは隠すだけで、誤りなら戻せる。
- 資料に無いもの（確かめていない）: セキュリティキー、Windows Hello、iCloudキーチェーンの扱い。同じ RP ID を複数のサイトで使う場合の注意。
