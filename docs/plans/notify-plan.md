# 運営者への通知（Webhook） 実装計画

状態: 2026-11-13、利用者が承認境界3（Slack・Discord への送信）、件数のメモリでの集計、管理者のログインの成功を知らせないことを承認した。外部のモデルによる計画のレビューの前。

対象の時点: `d20c406` から。

正本: 実装の後、今の仕様は `domain/notify.md`（新規）に移す。

## 1. 目的と範囲

複数のサイトを運営するとき、お問い合わせの到着や、管理者の認証に関わる出来事に、サイトごとの管理画面を見に行かずに気づけるようにする。気づくだけにして、読む・対応するのは今までどおり各サイトの管理画面で行う。

- 送り先は、Slack の Incoming Webhook か、Discord の Webhook のどちらか1つ。複数のサイトが同じ URL を使えば、1つのチャンネルに集まる。
- 送る文は、サイト名・出来事の種類・件数・時間の幅・固定の案内文だけにする。個人の情報、本文、IP アドレス、アカウントの番号、パスキーの名前は載せない。
- 設定しなければ、外への通信は一切しない。

作らないもの: メール、ntfy、その他の送り先、送り先ごとの出来事の選択、しきい値の設定、通知の履歴の保存、通知からの操作（既読にする等）、監査ログ、管理者のログインの成功の通知。

## 2. 拾う出来事

出来事は、各機能がすでに出しているログ（slog）から、決まった名前の表で拾う。機能のコードは原則として変えない。

| 種類 | 元のログ（メッセージ） | 条件 | 送り方 |
|---|---|---|---|
| お問い合わせの新着 | `contact submission` | 属性 `result` が `saved` のときだけ | 1時間ごとにまとめる。0件なら送らない |
| パスキーの登録 | `auth passkey registered` | なし | すぐ |
| パスキーの削除 | `auth passkey deleted` | なし | すぐ |
| パスキーの無効化（複製の疑い） | `auth passkey disabled` | なし | すぐ |
| アカウントの作成・削除 | `auth account created`・`auth account deleted` | なし | すぐ |
| 登録URLの発行 | `auth setup url issued` | なし | すぐ |
| AIエージェントの接続の承認 | `auth agent approved`（新規に1行足す） | なし | すぐ |
| MCPのクライアントの追加・変更 | `mcp client added`・`mcp client changed` | なし | すぐ |
| MCPの設定の変更 | `mcp setting changed` | なし | すぐ |
| ログインの拒否の連続 | `auth login rejected`・`federated login rejected` | 10分に10件以上 | 超えたら1通。続く間は10分に1通まで |
| 予期しない停止 | `panic recovered` | 1件で | すぐ |
| エラーの連続 | Error の水準のログ全部（通知自身のログを除く） | 5分に5件以上 | 超えたら1通。続く間は10分に1通まで |
| 起動 | 起動の完了 | 起動の前に出た Warn の件数を添える | 起動のとき1通 |

「すぐ」は、1分ごとの見回りで送る。1分の間に同じ種類が重なれば、件数を足して1通にする。

文の例:

- `[サイト名] お問い合わせの新着 3件（10:00〜11:00）。管理画面で確かめてください。`
- `[サイト名] パスキーが登録されました（1件）。覚えがなければ、管理画面で確かめてください。`
- `[サイト名] 起動しました（起動時の警告 0件）。`

## 3. 仕組み

```
各機能 ─ slog ─▶ 見張り役（Handler）─▶ メモリの集計 ─ 1分ごと ─▶ 送り役 ─ HTTPS ─▶ Slack / Discord
                 └─▶ 元の出力（標準出力の JSON）はそのまま
```

- `internal/notify` を新しく作る（Core）。
- 見張り役は `slog.Handler` を包む。`Handle` で、メッセージと必要な属性だけを見て数え、元の Handler にそのまま渡す。`WithAttrs`・`WithGroup` でも包みを保つ。数える処理はロックを短く持つだけにして、送信を待たない。
- 集計はメモリだけに持つ。DB は変えない。
- 見回りは1分ごとのゴルーチン。送る文を作り、送り役の待ち行列（上限32通）に入れる。満杯なら古いものを捨て、捨てた件数を次の文に添える。
- 送り役は1本のゴルーチンで、1通ずつ送る（Slack の目安の毎秒1通を超えない）。
- 停止の合図を受けたら、まとめ待ちの件数を5秒以内に送ってから止まる。予期しない停止では、まとめ待ちの件数（最大1時間分）が失われる。お問い合わせ自体は DB に残る。
- サブコマンド（`backup` 等）では、通知を動かさない。

## 4. 送り先と送信

- 設定は `NOTIFY_WEBHOOK_URL_FILE` の1つ。指すファイルに URL を1行で書く。読み込みは `federation.SecretFile` と同じ検査（通常のファイル、所有者だけが読める、大きさの上限）を行う。
- 許す URL は次の接頭辞だけ。それ以外、または読めない・権限が緩い場合は、起動を止める。エラーとログに URL を含めない。
  - `https://hooks.slack.com/services/` → Slack の形
  - `https://discord.com/api/webhooks/` → Discord の形
  - 旧ドメインの `discordapp.com` と、GovSlack の `slack-gov.com` は、公式の資料で確かめられなかったため、許さない。
- 送る形:
  - Slack: `{"text": "…"}`。文の中の `&`・`<`・`>` を `&amp;`・`&lt;`・`&gt;` に置き換える。
  - Discord: `{"content": "…", "allowed_mentions": {"parse": []}}`。呼び出し（`@everyone` 等）を効かせない。
- HTTP: タイムアウト10秒、転送（リダイレクト）には従わない、本文は読み捨てる（上限を付けて読む）。成功は 2xx。
- 送り直し: 429 と 5xx のときだけ、1回だけ送り直す。429 の `Retry-After` は上限60秒で従う。それでも失敗したら、その通は捨てる。
- 送り先が消えたとき: 404 が返ったら、それ以降は再起動まで送らない（Discord は 404 の後に同じ Webhook を使い続けないよう求めている）。ログに1回だけ残す。
- 文の長さ: Discord の上限（2,000文字）より十分短い文だけを作る。
- 失敗のログ: `notify send failed`（応答のコードだけ）。URL・応答の本文・送る文は出さない。このログは見張り役が数えない（通知の失敗が通知を呼ぶ循環を防ぐ）。

### 確かめた公式の資料（2026-11-13）

| 項目 | 確かめたこと | 出典 |
|---|---|---|
| Slack の URL | 例として `https://hooks.slack.com/services/T…/B…/…`。接頭辞の規則は書かれていない | docs.slack.dev の Sending messages using incoming webhooks |
| Slack の形と成功 | `{"text": …}` を JSON で POST。成功は多くの場合 200 と本文 `ok` | 同上 |
| Slack の失敗 | 400・403・404 等と、本文の短いエラー名（`invalid_payload` 等）。直さずに送り直さない | 同上 |
| Slack の置き換え | `&`・`<`・`>` だけを `&amp;`・`&lt;`・`&gt;` にする。文全体を符号化しない | docs.slack.dev の Formatting message text |
| Discord の形と成功 | `POST /webhooks/{id}/{token}`、`content` は2,000文字まで。`wait` の既定は false で、そのときは 204 | docs.discord.com の Webhook |
| Discord の 429 | `Retry-After` の見出しか、本文の `retry_after`（秒）に従う。404 の後は同じ Webhook を使わない | docs.discord.com の Rate Limits |

確かめられなかったこと: Slack の Webhook の回数の上限、Discord の実行の URL のホスト（`discord.com/api` は資料の中で明記されていない）、`allowed_mentions` の `parse: []` の原文（実装の前に読み直す）、`discordapp.com` が今も使えるか。

## 5. 不変条件（案）

| 番号 | 条件 |
|---|---|
| NOTIFY-INV-1 | 送る文は、サイト名・出来事の種類・件数・時間の幅・固定の案内文だけで作る。ログの属性の値（`result` の判定に使う値を除く）を文に入れない |
| NOTIFY-INV-2 | 送り先は、4節の接頭辞に一致する HTTPS の URL だけ。違えば起動を止める。転送には従わない |
| NOTIFY-INV-3 | URL は所有者だけが読めるファイルから読み、URL・応答の本文をログとエラーに出さない |
| NOTIFY-INV-4 | 送信の失敗・遅れ・待ち行列の満杯で、要求の処理やログの出力を止めたり遅らせたりしない |
| NOTIFY-INV-5 | 設定しなければ、外へ通信しない |
| NOTIFY-INV-6 | 拾うログの名前は固定の表で持ち、表の名前はすべてコードに実在する |
| NOTIFY-INV-7 | Slack の文は `&`・`<`・`>` を置き換え、Discord は呼び出しを効かせない |
| NOTIFY-INV-8 | 通知自身のログは数えない |

## 6. 承認境界とプライバシー

| 境界 | 判定 |
|---|---|
| 1 `go.mod` | 当たらない。標準の `net/http`・`encoding/json`・`log/slog` だけで作る |
| 2 保存データ | 当たらない。集計はメモリだけ。設定の URL は秘密のファイルで、台帳の「DBの外のファイル」に書き足す |
| 3 外部への通信 | 当たる。承認済み（2026-11-13） |
| 4・5 | 当たらない |

- Slack・Discord に個人の情報は渡らない。`minimal-web-kit-privacy` でポリシーの変更が要らないことを確かめる。サイト名と出来事の件数が外部のサービスに残ることは、`docs/deploy.md` に書く。

## 7. 試験

- 文に属性の値が出ないこと: お問い合わせの本文・返信先・パスキーの名前等をカナリアにしてログを流し、送る文に出ないこと（INV-1）。
- 許可していない URL（`http://`、別のホスト、接頭辞違い、`hooks.slack.com.example`、利用者情報付き `https://x@hooks.slack.com/…`）で起動が止まり、エラーに URL が出ないこと（INV-2・3）。
- 転送の応答（302）に従わないこと（INV-2）。
- 権限の緩いファイルを断ること（INV-3）。
- 送り先が応答しない・遅い・待ち行列が満杯のときも、ログの出力がすぐ返ること（INV-4）。
- 未設定で、送り役のゴルーチンと HTTP の通信が起きないこと（INV-5）。
- 表のメッセージの名前が、`features/`・`internal/` のコードに文字列として実在すること（INV-6）。
- Slack・Discord の送る JSON の形と置き換え（INV-7）。
- 送信の失敗のログを流しても、エラーの件数が増えないこと（INV-8）。
- しきい値・まとめ・1分の見回りは、時刻を差し替えて確かめる。
- 守りを外して、対応する試験が落ちることを確かめる（置き換え、転送、権限、循環、表の実在）。

## 10. レビューで見てほしい点

- ログに相乗りする設計の危うさ（名前の変更、属性の扱い、`WithAttrs` の包み方、ログの水準の設定との関係）。
- 送り先の検査の抜け（URL の解析、大文字小文字、ポート、パスの正規化）。
- ログの出力の経路に処理を挟むことによる遅れ・デッドロック・循環。
- 1時間のまとめ、しきい値の妥当性。
- 予期しない停止で件数が失われることの扱い。
