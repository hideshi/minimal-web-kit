# 画像機能 実装計画

状態: 案（2026-11-01）。未実装。14節の決定、承認境界2・5の承認、計画のレビューの前。対象の時点は `main` の `8b38887` の後。今の仕様の正本は、実装の前に `docs/domain/media.md` として作る。関連する正本: [お知らせ](../domain/news.md)、[カタログ](../domain/catalog.md)、[固定ページ](../domain/pages.md)、[本文の書き方](../richtext.md)、[MCP](../domain/mcp.md)。

## 1. 目的と範囲

管理画面で画像を登録し、お知らせ・カタログ・固定ページで使い回して、公開ページに表示できるようにする。今のキットには画像のアップロードが無い。

- 画像はSQLiteにBLOBとして保存する。実行ファイル1つとDB1つの形を保ち、今の `backup` コマンドで画像も一緒に複製する。
- 対象の機能はお知らせ・カタログ・固定ページだけ。社内文書・お問い合わせには付けない。
- 新しい同梱機能 `media`（`features/media/`、`make add-media`・`remove-media`）。管理者認証を使う。
- 作らないもの: 動画、画像以外の添付、閲覧者や一般ユーザーの投稿、画像の編集（切り抜き等）、外部のオブジェクトストレージ、SVG、大きさ違いの複製（`srcset`）、`og:image`、JSON APIへの画像の項目。
- 向かない用途: 写真が大量に増えるサイト。容量が数GBを超えそうなら、別の方式を検討する。

## 2. 決まったこと

| 事項 | 決定 |
|---|---|
| 保存先 | SQLiteのBLOB |
| 公開の状態 | 画像に公開状態を持たせない。公開中の記事と紐づいている間だけ公開する |
| 使い回し | 画像と記事は別に管理する。1枚を複数の記事で使える |
| 権限 | アップロードと管理は `CanManageSite` のロール（システム管理者・サイト管理者）。一般ユーザーは不可 |
| 保存前の加工 | サーバーで縮小・再エンコードしてから保存する。表示が粗くならない大きさにする |
| 画像の保存先の機能 | `features/media` に1つ作り、各機能はそれを使う |
| MCP | 第1段階は管理画面だけ。MCPからのアップロードは第2段階（10節） |

## 3. 公開の判定

画像が持つのは、どの記事から使われているかの参照だけ。公開中かは保存せず、記事の状態から毎回判定する。

| 画像が使われている先 | 公開の経路（`/media/...`） | 管理者の経路 |
|---|---|---|
| どの記事からも使われていない | 404 | 見える |
| 下書きの記事だけ | 404 | 見える |
| 公開中の記事が1つ以上 | 200 | 見える |

- 記事を公開すると、同時に画像も見えるようになる。画像への別の操作は要らない。
- 記事の保存と同じトランザクションで、参照を更新する。記事を消すと参照も消える。
- `media` は各機能の表を読まない。機能は `features` の新しい口で「この参照先は公開中か」に答える。機能を外して答える相手が居ない参照は、公開中として数えない。
- 公開予約のように日時で公開が変わる機能を足すときは、その判定も機能の答えに含める。

## 4. 受け取りと加工

処理の順番: 認証 → 本文サイズの上限 → multipartの解析 → CSRF → 形式の判定 → 画素数の検査 → デコード → 向きの適用 → 縮小 → 再エンコード → 全体の容量の検査と保存。

| 項目 | 内容 |
|---|---|
| 入力の形式 | JPEG・PNGだけ。判定はファイルの中身で行い、拡張子と申告のContent-Typeを信用しない。SVG・GIF・WebP・HEICは断る |
| 入力の上限 | 14節の決定1。超えたら理由を示して断る |
| 画素数の上限 | `image.DecodeConfig` で先に調べ、2,400万画素を超えたら、デコードせずに断る（小さなファイルが巨大に展開される画像への対策） |
| 同時処理 | 1件まで。埋まっていれば503と `Retry-After` |
| 縮小 | 長辺1,800pxまで。拡大はしない。本文の表示幅は最大で約870pxで、高精細な画面の2倍でも足りる。Lanczos系の縮小を標準ライブラリだけで書く（`go.mod` を変えない） |
| 写真 | JPEG、品質85 |
| 図・スクリーンショット | PNG。透明が無ければJPEGも作り、小さいほうを保存する。透明があればPNGのまま |
| 向き | JPEGのEXIFの向きを読み、画素を回転してから保存する。読むのは向きだけで、書式の外れた値は無視する |
| 落とす情報 | 再エンコードでEXIF全体を落とす。撮影位置を保存しない |
| 元のファイル | 保存しない。元のファイル名も保存せず、ログにも出さない |

手元の模擬画像（`image` の標準ライブラリ、平均による簡易な縮小、品質82）で測った値:

| 入力 | 入力の容量 | 処理時間 | 確保したメモリ | 長辺1,600pxの出力 |
|---|---|---|---|---|
| 2000×1500 | 317KB | 約0.1秒 | 約21MB | 247KB |
| 4000×3000 | 1,140KB | 約0.3秒 | 約61MB | 180KB |

実際の写真と本番のVPSでは測っていない。実装の前に、写真・図・スクリーンショットで容量と画質を確かめ、大きさと品質を決める（13節の1）。

見栄えの注意:

- iPhoneの写真はP3色域のことがある。標準ライブラリは色プロファイルを扱わないため、色が薄く見えるかを実機の写真で確かめる。問題があれば、変換の実装か注意の表示を決める。
- JPEGの再エンコードは画質が少し落ちる。保存後に画像の詳細で確かめられるようにする。
- 本文の幅より小さい画像は、引き伸ばさず、元の大きさで表示する。

## 5. 保存

| 表 | 列 | 目的 |
|---|---|---|
| `media_items` | 乱数のID、形式、幅、高さ、バイト数、説明、作成日時 | 一覧と判定。本体を読まない |
| `media_blobs` | ID、本体 | 配信のときだけ読む |
| `media_refs` | 画像のID、機能、参照先のキー | 使用先と公開の判定 |

- 保存した人のIDは持たない（目的に要らないため）。
- 説明（代替テキスト）は必須で、1〜200字の1行。
- 全体の上限は既定300MBで、`MEDIA_TOTAL_LIMIT_MB` で変えられる。合計の確認と保存は1つのトランザクションで行う。平均250KBなら約1,200枚。
- 大きな書き込みは短いトランザクションにする。加工はトランザクションの外で済ませる。
- 消した領域はSQLiteの中で再利用される。ファイルは自動では縮まない。

## 6. 配信

| 経路 | 用途 | 応答 |
|---|---|---|
| `GET /media/{id}.{ext}` | 公開ページ | 公開中なら200。それ以外は404 |
| `GET /admin/media/{id}/image` | 管理画面とプレビュー | `CanManageSite` のロールに200。`no-store` |

- 公開の経路は独立経路で、Cookieを読まず、発行しない。下書きの判定に管理者のセッションを使わない。
- 拡張子を `.jpg`・`.png` にする。Cloudflareは拡張子でキャッシュを決め、拡張子が無いURLは既定でキャッシュしない。
- 公開の200は `Cache-Control: public, max-age=86400`（14節の決定3）。`immutable` にしない。
- 公開の404は `no-store` にする。Cloudflareは404を既定で数分キャッシュするため、公開した直後に404が残らないようにする。
- `Content-Type` はサーバーが保存した形式で固定する。`X-Content-Type-Options: nosniff` は今の共通のヘッダーで付く。CSPは `default-src 'self'` のままで表示できる。
- IDは推測できない乱数にする。URLが漏れても、公開の判定は変わらない。
- 公開を取り消しても、CDNとブラウザに残った分は、キャッシュの期間が過ぎるまで表示され得る。CDNの消去は外部通信になるため作らない。

## 7. 管理画面

| 経路 | 画面の型 | 内容 |
|---|---|---|
| `/admin/media` | 一覧＋追加 | 縮小表示、説明、大きさ、使用の数、「未使用」の表示、ページ送り、追加のフォーム、全体の使用量 |
| `/admin/media/{id}` | 編集 | 画像、説明の編集、使用先の一覧 |
| `/admin/media/{id}/delete` | 削除の確認 | 使用先があれば削除できない |

- 使用中の画像は、公開か下書きかによらず削除できない。使用先の一覧から記事を直してから消す。下書きの穴を公開の時まで残さないため。
- 未使用の画像も自動では消さない。
- JavaScriptは使わない。ファイルの選択は `<input type="file">` で行う。

## 8. 各機能への組み込み

### 8.1 固定ページ

- 本文の書き方に、行全体の画像の記法を足す。`![説明](/media/ID.jpg)`。段落の判定より前に読み、途中の文字に混ざった `![` は文字のまま。
- URLは `/media/` の経路だけを許可する。外部の画像は読まない（閲覧者の情報が外部へ渡るため）。書き方の規則は `docs/richtext.md` を先に直し、例を全部テストにする。
- 保存のとき、本文から画像を読み取り、存在を確かめて参照を更新する。無い画像なら保存を断る。
- 説明は必須。使う場所ごとに文脈が違うため、記法の説明を優先する。
- 編集の画面に「画像を挿入」の `details` を足す。画像の一覧の各行に「本文の末尾に追加」のボタンを置く。ボタンは今のプレビューと同じ `formaction` の形で、保存せずに、記法を足した入力を描き直す。JavaScriptもコピーも要らない。
- プレビューでは、画像を管理者の経路で描く。下書きの画像は公開の経路では404のため。
- 公開ページは `page.html` の `richtext` の部品のまま、画像の部品を足す。

### 8.2 お知らせ

- 本文はプレーンテキストのまま（14節の決定2）。記事に代表画像を1枚持てる。
- 作成・編集の画面に「代表画像」の選択を足す。縮小表示つきのラジオで、先頭は「なし」。
- 公開の詳細（`news_show.html`）の見出しの下に表示する。一覧には出さない。
- `/api/news` と `/news` の一覧は変えない。

### 8.3 カタログ

- 本文はプレーンテキストのまま。項目に代表画像を1枚持てる。
- 作成・編集の画面は、お知らせと同じ選択の部品を使う。
- 公開の詳細（`show.html`）の見出しの下と、公開の一覧（`list.html`）のカードに表示する。一覧はhtmxの差し替えでも同じ部品で描く。
- 一覧のカードは、画像が無い項目でも崩れないようにする。

### 8.4 共通

- 列の追加（`news_posts`・`catalog_items` の代表画像のID）は、`store.BackupBeforeMigration` の要否を確かめ、既存のデータを保つ移行にする。
- 記事の編集の画面で画像を足すときは、「画像の管理」を新しいタブで開く。編集中の入力を失わないため。戻ったら、プレビュー等で一覧を描き直す。
- 選択の一覧は新しい順に上限を決めて出す。
- `media` を外しても、各機能は画像なしで動く。「他の機能があるか」で分岐せず、`features` の口を使う。
- MCPの更新は全置換のため、代表画像の値を消さないようにする。第1段階のツールは値を変えず、対象の状態のハッシュに含める。

## 9. 公開ページの表示

- 共通の部品 `media-image` を `components.html` に足す。出力は `<img src alt width height loading="lazy" decoding="async">`。`width`・`height` で読み込み時のずれを防ぐ。
- CSSは `style.css` に足す。`max-width: 100%`、`height: auto`。インラインの `style` は使わない。
- 代表画像は `figure` にしない。説明の文を画面に出す機能は今回作らない。
- 画像を読めないときも本文は読める。
- 公開ページはセッションを照合しない今の形を保つ。

## 10. MCP（第2段階）

第1段階では、固定ページの本文に既存の画像の記法を書ける（管理画面と同じ検査）。代表画像の変更とアップロードは第2段階にする。

- 今の本文の上限は64KBで、画像は入らない。上限を広げても、画像の文字データがAIの会話を通るため採らない。
- まず読み取りのツール `media_list` を足す。
- アップロードは、確認を通った書き込みのツールが1回限りの切符を返し、エージェントが別の経路へファイルを送る形にする。

```sh
curl -X POST https://example.com/media/upload \
  -H "Authorization: Bearer <1回限りの切符>" \
  -F file=@photo.jpg
```

| 時点 | 確かめること |
|---|---|
| 発行 | トークン、`mcp:write`、`CanManageSite`、機能のMCPが有効、利用者の確認の承諾 |
| 送信 | 切符が存在し、期限内で未使用、アカウントが有効でロールが足りる、接続が停止されず認可の世代が同じ、機能のMCPが有効、ファイルが範囲内 |

- 切符は短命の認証情報で、AIの会話を通る。256ビットの乱数にし、DBにはSHA-256のハッシュだけを保存する。期限5分、1回限り、ファイル1枚、アカウントと接続に結びつける。
- 切符をURLに入れない。ログに出さない。POSTだけ受け、Cookieを使わず、CORSを許可しない。発行に回数の上限を付ける。
- 切符の消費と保存は1つのトランザクションで行う。保存した画像は未使用で、公開には記事の更新か公開が要り、その操作は利用者の確認を通る。
- ファイルを送れるクライアントでしか使えない。切符の表と経路は承認境界2・5で、今のMCPの承認の範囲に入らない。MCP-INV-2との関係を設計で決める。

## 11. バックアップとプライバシー

- 毎日DB全体を複製するため、画像の容量は世代の分だけ増える。300MBなら、14世代で約4GB、30世代で約9GB。画像は圧縮が効きにくい。`docs/deploy.md` に見積もりと、容量の監視を足す。
- 消した画像も、複製の保持期間が過ぎるまで残る。
- 閲覧者の情報は新しく取得しない。外部の画像も読まない。
- 画像には人の顔や名札等が写り得る。公開前に運営者が確かめる。写真の掲載の許可は運営者の責任で、キットは判断しない。
- `minimal-web-kit-privacy` で `/privacy` の雛形を見直す。アップロードの画面に、撮影位置を保存しないことと、公開前の確認の注意を出す。
- CDNを使う構成では、画像のキャッシュと、公開の取り消しの遅れを説明する。

## 12. 文書とテスト

文書:

- `docs/domain/media.md`（用語、状態、`MEDIA-INV-*`、権限）を実装の前に作る。
- `docs/domain/news.md`・`catalog.md`・`pages.md` の「作らないもの」と不変条件を直す。
- `docs/richtext.md`、`docs/components.md`、`docs/ui/use-cases.md`、`docs/data-inventory.md`、`docs/deploy.md`、`README.md`、トップの同梱機能のカード、`test/landing_test.go` の対応表を更新する。

テスト:

- 公開の判定の表: 未使用、下書きだけ、公開中、複数の記事、非公開へ戻す、参照を外す、記事の削除、機能が無い参照。
- 応答: 公開の200と404のヘッダー、Cookieを発行しない、一般ユーザーと未ログインは管理者の経路に入れない。
- 入力: 形式の偽装、SVG、壊れたファイル、上限の超過、画素数の超過をデコードの前に断る、CSRFなし。ファズを足す。
- 加工: 長辺、拡大しない、EXIFの全ての向き、透明の維持、位置情報の文字列が保存結果に無いこと。
- 保存: 全体の上限を同時の送信でも超えない、使用中の削除の拒否、記事の保存と参照の不可分性。
- 記法: `docs/richtext.md` の例、意地悪な入力でも読む時間が入力の長さに比例すること、外部のURLを読まないこと。
- ログ: ファイル名、説明、IDをログに出さないカナリア。
- 画面: `test/admin_ui_test.go` の見本、公開ページの `alt`・`width`・`height`、`make test-ui` で狭い画面の崩れ。

## 14. 決めること

| # | 事項 | 僕の案 | 影響 |
|---|---|---|---|
| 1 | 入力の上限 | 8MB（今は1MBの方向） | 1MBのままなら、多くのスマホの写真は手元で縮小が要る。8MBなら、この経路だけ今の本文の上限1MiBを広げる。保存時に縮小するため、DBの容量はほぼ増えない |
| 2 | お知らせの本文に画像を入れるか | 入れず、代表画像1枚にする | 本文にも入れるなら、本文の形式を変える |
| 3 | 公開画像のキャッシュ | 1日 | 公開を取り消しても最長1日残る。短くするとCDNの効きが弱くなる |

| 種類 | 内容 |

## 16. 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 画像を別のファイルに保存する | バックアップと削除の整合の手間が増える。書き込み先のフォルダと権限も増える |
| 画像だけ別のDBファイルにする | 主DBは軽くなるが、整合とバックアップの手間が戻る。将来の選択肢として残す |
| 画像に公開状態を持たせる | 記事の状態とずれる。編集者の操作も、MCPの確認も増える |
| 公開の判定に中身のハッシュのURLを使う | ランダムなIDより推測されやすく、同じ画像の記事間の関係も見える |
| 公開の経路で管理者のセッションを読む | 公開の経路がCookieを読むことになる。管理者の経路を分ければ要らない |
| 外部画像の記法を許す | 閲覧者の情報が外部へ渡る |
| MCPの引数に画像を入れる | 本文の上限を超え、AIの会話を画像の文字データが通る |
| 切符をURLに入れる | URLはログや履歴に残りやすい |
