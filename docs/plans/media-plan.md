# 画像機能 実装計画

状態: 2026-11-01、利用者が14節の3項目と、第1段階の承認境界2・5を承認した。未実装。計画のレビュー（Fable・Sol）の指摘を反映した（17節）。実際の写真での確認の前。対象の時点は `main` の `8b38887` の後。今の仕様の正本は、実装の前に `docs/domain/media.md` として作る。関連する正本: [お知らせ](../domain/news.md)、[カタログ](../domain/catalog.md)、[固定ページ](../domain/pages.md)、[本文の書き方](../richtext.md)、[MCP](../domain/mcp.md)。

## 1. 目的と範囲

管理画面で画像を登録し、お知らせ・カタログ・固定ページで使い回して、公開ページに表示できるようにする。今のキットには画像のアップロードが無い。

- 画像はSQLiteにBLOBとして保存する。実行ファイル1つとDB1つの形を保ち、今の `backup` コマンドで画像も一緒に複製する。
- 対象の機能はお知らせ・カタログ・固定ページだけ。社内文書・お問い合わせには付けない。
- 新しい同梱機能 `media`（`features/media/`、`make add-media`・`remove-media`）。管理者認証を使う。
- 作らないもの: 動画、画像以外の添付、閲覧者や一般ユーザーの投稿、画像の編集（切り抜き等）、外部のオブジェクトストレージ、SVG、大きさ違いの複製（`srcset`）、`og:image`、JSON APIへの画像の項目。
- 向かない用途: 写真が大量に増えるサイト。容量が数GBを超えそうなら、別の方式を検討する。

## 2. 決まったこと

| 事項 | 決定 |
|---|---|
| 保存先 | SQLiteのBLOB |
| 公開の状態 | 画像に公開状態を持たせない。公開中の記事と紐づいている間だけ公開する |
| 使い回し | 画像と記事は別に管理する。1枚を複数の記事で使える |
| 権限 | アップロードと管理は `CanManageSite` のロール（システム管理者・サイト管理者）。一般ユーザーは不可 |
| 保存前の加工 | サーバーで縮小・再エンコードしてから保存する。表示が粗くならない大きさにする |
| 画像の保存先の機能 | `features/media` に1つ作り、各機能はそれを使う |
| MCP | 第1段階は管理画面だけ。MCPからのアップロードは第2段階（10節） |

## 3. 公開の判定

画像が持つのは、どの記事から使われているかの参照だけ。公開中かは保存せず、記事の状態から毎回判定する。

| 画像が使われている先 | 公開の経路（`/media/...`） | 管理者の経路 |
|---|---|---|
| どの記事からも使われていない | 404 | 見える |
| 下書きの記事だけ | 404 | 見える |
| 公開予約で、公開日時の前のお知らせだけ | 404 | 見える |
| 公開予約のお知らせで、公開日時を過ぎた（操作なし） | 200 | 見える |
| 公開中の記事が1つ以上 | 200 | 見える |

- 記事を公開すると、同時に画像も見えるようになる。画像への別の操作は要らない。
- `media` は各機能の表を読まない。機能は `features` の新しい口で「この参照先は公開中か」に答える。答えは、その機能の公開ページの条件と同じにする。お知らせは `status` に加えて `published_at <= 現在` を見る。条件を2か所に書かず、公開ページと共有する。
- 機能を外して答える相手が居ない参照は、公開中として数えない。

### 3.1 参照の更新

- 参照の更新は、記事を保存するトランザクションの中で行う。`media` はトランザクションを始めない。機能が持つ `*sql.Conn` を受け取る口にする（例: `MediaRefs.Replace(ctx, conn, 機能, 参照先, 画像のID)`、`Delete`）。
- 固定ページとお知らせの作成・更新・削除・`*IfUnchanged` は今は単文のため、カタログの `write()`（専用の接続と `BEGIN IMMEDIATE`）と同じ形に揃える。画像の存在の確認、参照の更新、画像の削除の使用中の判定も同じ排他の下に置く。
- 画像の使用中の削除は、`media_refs.media_id` の外部キー（`ON DELETE RESTRICT`）でもDBで止める。

### 3.2 機能の追加と削除

`remove-*` は保存データを残すため、機能を外している間に、参照が実態とずれ得る。

- **参照は起動時に作り直す。** 起動時、サーバーが待ち受ける前に、`media` が有効な各機能へ全ての参照を問い合わせ、機能ごとに1つのトランザクションで置き換える。記事を読むだけで作り直せる。待ち受けの前のため、作り直しの途中で公開されることはない。
- 外した機能の参照は残す。公開中として数えず、画像の削除は止める。使用先の一覧に「無効な機能」と示す。

`media` が無い構成:

| 場面 | 振る舞い |
|---|---|
| 固定ページの表示 | 画像の行は説明の文字として描く |
| 固定ページの保存 | 画像の検査をせず保存する。既存のページの編集を止めないため |
| お知らせ・カタログ | 代表画像の選択を出さず、列の値は変えない |

画像が見つからないときの表示も、説明の文字に揃える。

## 4. 受け取りと加工

処理の順番: 同一オリジン → セッションとロール → 宣言された長さの検査 → 同時処理の枠の取得 → 読み取り期限の延長 → multipartを先頭から順に読む（CSRF → 説明 → ファイル） → 形式の判定 → 画素数の検査 → デコード → 向きの適用 → 縮小 → 再エンコード → 枠の解放 → 全体の容量の検査と保存。

### 4.1 本文の受け取り（Coreと管理者認証の変更）

今の作りでは8MBを受け取れない。次の3つを、機能の前に変える。

- **本文の上限:** `MaxBytes(1MiB)` は全経路の最上位で掛かり、機能の中からは緩められない。Coreに経路ごとの本文の上限を足し、`POST /admin/media` だけに適用する。ファイルは8,000,000バイトまで、本文全体はそれに付帯分を足した値にして、2つの上限を分ける。ほかの経路は1MiBのまま。
- **読み取りの期限:** サーバーの `ReadTimeout` は10秒、`WriteTimeout` は15秒で、遅い回線の8MBは途中で切れる。全体の値は変えず、認証を通した後に、この経路だけ `http.NewResponseController` で読み書きの期限を延ばす。未認証の送信には延ばさない。
- **multipartの口:** `features.Admin` の `Form` は `ParseForm` を使うため、multipartのCSRFトークンを読めず403になる。`features.Admin` に新しい口を足し、`auth` と `federatedauth` の両方で実装する。

| 項目 | 内容 |
|---|---|
| 読み方 | `r.MultipartReader()` で順に読む。`ParseMultipartForm` は一時ファイルを書き得るため使わない |
| 部品の順 | `csrf_token`、説明、ファイルの順に決め打ちする。順が違う、余分な部品がある、部品が足りないときは断る。ファイルを読む前にCSRFを確かめる |
| 欄の上限 | CSRFトークンと説明は小さな上限を置く |
| メモリ | ファイルは上限つきでメモリに読む |
| 上限の超過 | `Content-Length` が上限を超えれば、本文を読む前に413の画面を返す。無い場合は上限で打ち切る。ブラウザに画面が届かず、接続が切れることがある |

### 4.2 加工

| 項目 | 内容 |
|---|---|
| 入力の形式 | JPEG・PNGだけ。判定はファイルの中身で行い、拡張子と申告のContent-Typeを信用しない。SVG・GIF・WebP・HEICは断る |
| 入力の上限 | 14節の決定1。超えたら理由を示して断る |
| 画素数の上限 | `image.DecodeConfig` で先に調べ、デコードせずに断る（小さなファイルが巨大に展開される画像への対策）。通常のJPEGと8ビットのPNGは2,400万画素、プログレッシブのJPEGと16ビットのPNGは1,200万画素まで。辺の長さは1辺12,000pxまで |
| 同時処理 | 本文を読む前に枠を取り、再エンコードの後に返す。1件まで。埋まっていれば503と `Retry-After` |
| 縮小 | 長辺1,600pxまで（利用者が2026-11-01に決定）。拡大はしない。本文の表示幅は最大で約870pxで、高精細な画面の約2倍。Lanczos系の縮小を標準ライブラリだけで書く（`go.mod` を変えない） |
| 写真 | JPEG、品質80（利用者が2026-11-01に決定） |
| 図・スクリーンショット | PNG。透明が無ければJPEGも作り、小さいほうを保存する。透明があればPNGのまま |
| 向き | JPEGのEXIFの向きを読み、画素を回転してから保存する。読むのは向きだけで、走査する長さとオフセットを制限し、書式の外れた値は無視する。ファズの対象にする |
| 落とす情報 | 再エンコードでEXIF全体を落とす。撮影位置を保存しない |
| 元のファイル | 保存しない。元のファイル名も保存せず、ログにも出さない |

手元の模擬画像（`image` の標準ライブラリ、平均による簡易な縮小、品質82）で測った値:

| 入力 | 入力の容量 | 処理時間 | 確保したメモリ | 長辺1,600pxの出力 |
|---|---|---|---|---|
| 2000×1500 | 317KB | 約0.1秒 | 約21MB | 247KB |
| 4000×3000 | 1,140KB | 約0.3秒 | 約61MB | 180KB |

この値は通常のJPEGと簡易な縮小のもので、予定の処理の値ではない。Goの `image/jpeg` はプログレッシブで係数を全画面分持ち、`image/png` は16ビットを1画素8バイトで読むため、同じ画素数でもメモリが数倍になる。上の画素数の上限は仮の値で、実際の処理で測って決める。

実装の前に、実際の写真・図・スクリーンショットと、最大の画素数、細長い画像、回転、透明のPNGで、容量、画質、メモリの山、処理時間を測る（13節の1）。結果から、大きさ、品質、画素数の上限と、`docs/deploy.md` のメモリの目安（systemdの `MemoryMax=` を含む）を決める。本番のVPSでも測る。途中の結果は [画像の加工の測定](../experiments/media-image-processing.md)。写真の容量は見積もりより大きく、メモリも上の値より大きかった。

見栄えの注意:

- iPhoneの写真はP3色域のことがある。標準ライブラリは色プロファイルを扱わず、手元に実機の写真も無い。初版では変換せず、「P3の写真は色が少し薄く見えることがある」と文書に書く（利用者が2026-11-01に決定）。
- JPEGの再エンコードは画質が少し落ちる。保存後に画像の詳細で確かめられるようにする。
- 本文の幅より小さい画像は、引き伸ばさず、元の大きさで表示する。

## 5. 保存

| 表 | 列 | 目的 |
|---|---|---|
| `media_items` | 乱数のID、形式、幅、高さ、バイト数、説明、作成日時 | 一覧と判定。本体を読まない |
| `media_blobs` | ID、本体 | 配信のときだけ読む |
| `media_refs` | 画像のID、機能、参照先のキー | 使用先と公開の判定 |

- 保存した人のIDは持たない（目的に要らないため）。
- 説明（代替テキスト）は必須で、1〜200字の1行。
- 全体の上限は既定300MBで、`MEDIA_TOTAL_LIMIT_MB` で変えられる。合計の確認と保存は、`BEGIN IMMEDIATE` の1つのトランザクションで行う。測定の写真の平均370KBなら約800枚。
- 大きな書き込みは短いトランザクションにする。加工はトランザクションの外で済ませる。
- この上限は画像の合計で、DBファイルの大きさの上限ではない。消した領域はSQLiteの中で再利用され、ファイルは自動では縮まない。

### 5.1 代表画像の列

- `news_posts`・`catalog_items` に、NULLを許す代表画像のIDの列を足す。**外部キーは付けない。** 全接続で `foreign_keys` が有効なため、`media` の表が無い構成で記事を保存できなくなる。
- 整合は `media_refs` を同じトランザクションで更新して守る。
- 追加は `pragma_table_info` で列の有無を見て `ALTER TABLE ... ADD COLUMN` にする。表を作り直さないため、`store.BackupBeforeMigration` は要らない。新規のDB、既存のDB、機能の再追加、移行の再実行で確かめる。

## 6. 配信

| 経路 | 用途 | 応答 |
|---|---|---|
| `GET /media/{file}` | 公開ページ | 公開中なら200。それ以外は404 |
| `GET /admin/media/{id}/image` | 管理画面とプレビュー | `CanManageSite` のロールに200。`no-store` |

- `net/http` のパターンは `{id}.{ext}` の形を書けず、登録すると起動が止まる。`{file}` で受け、`^[a-f0-9]{32}\.(jpg|png)$` の形だけを認める。拡張子と保存した形式が違えば404。正規のURLは1つだけにする。
- 公開の経路は独立経路で、Cookieを読まず、発行しない。下書きの判定に管理者のセッションを使わない。
- 本体はDBから読み終えて接続を返してから送る。遅い閲覧者がDBの読み取りを保持しないようにする。送信は `http.ServeContent` で行い、`Range`・`If-Modified-Since` に応える。`HEAD` は本体を読まない。
- 固定ページの予約語に `media` を足す。
- 拡張子を `.jpg`・`.png` にする。Cloudflareは拡張子でキャッシュを決め、拡張子が無いURLは既定でキャッシュしない。
- 公開の200は `Cache-Control: public, max-age=86400`（14節の決定3）。`immutable` にしない。
- 公開の404は `no-store` にする。Cloudflareは404を既定で数分キャッシュするため、公開した直後に404が残らないようにする。
- `Content-Type` はサーバーが保存した形式で固定する。`X-Content-Type-Options: nosniff` は今の共通のヘッダーで付く。CSPは `default-src 'self'` のままで表示できる。
- IDは推測できない乱数にする。URLが漏れても、公開の判定は変わらない。
- 公開を取り消しても、CDNとブラウザに残った分は、キャッシュの期間が過ぎるまで表示され得る。CDNの消去は外部通信になるため作らない。
- `docs/deploy.md` の `/static/` のキャッシュの注意（Browser Cache TTLの引き上げ等）に `/media/` も足す。

## 7. 管理画面

| 経路 | 画面の型 | 内容 |
|---|---|---|
| `/admin/media` | 一覧＋追加 | 縮小表示、説明、大きさ、使用の数、「未使用」の表示、ページ送り、追加のフォーム、全体の使用量 |
| `/admin/media/{id}` | 編集 | 画像、説明の編集、使用先の一覧 |
| `/admin/media/{id}/delete` | 削除の確認 | 使用先があれば削除できない |

- 使用中の画像は、公開か下書きかによらず削除できない。使用先の一覧から記事を直してから消す。下書きの穴を公開の時まで残さないため。
- 未使用の画像も自動では消さない。
- JavaScriptは使わない。ファイルの選択は `<input type="file">` で行う。
- 縮小版は持たない。管理画面の縮小表示は原寸を読むため、一覧と選択は1ページ12件にし、`loading="lazy"` を付ける。転送が重ければ、縮小版の列を足す案を、承認を取ってから検討する。
- 部品を足す。`form.Field` に `Accept` を足す。画像つきの選択の部品（`media-choices`）を `components.html` と `docs/components.md` の手順で作る。機能のテンプレートに入力欄を直接書くと `test/template_test.go` が落ちるため。
- `test/admin_ui_test.go` の全機能の登録と、`cmd/kit/main.go` の `bundles` に `media` を足す。

## 8. 各機能への組み込み

### 8.1 固定ページ

- 本文の書き方に、行全体の画像の記法を足す。`![説明](/media/ID.jpg)`。段落の判定より前に読み、途中の文字に混ざった `![` は文字のまま。
- URLは `/media/` の正規の形（6節）だけを許可する。クエリ、符号化された区切り、形の違う拡張子は許可しない。外部の画像は読まない（閲覧者の情報が外部へ渡るため）。書き方の規則は `docs/richtext.md` を先に直し、例を全部テストにする。
- 本文の途中の `![…](/media/…)` は、今の規則どおり「!」とサイト内リンクのままとし、その旨を書く。説明の中の `\]` と行末の空白は、今の `lex` の規則で定義する。
- 保存のとき、**表示と同じ `richtext.Parse` の画像のブロック**から参照を取り出す。正規表現で別に探さない。エスケープされた記法や、表の中の文字を参照に数えないため。存在を確かめて参照を更新し、無い画像なら保存を断る（`media` が無い構成を除く。3.2節）。
- 説明は必須。使う場所ごとに文脈が違うため、記法の説明を優先する。
- `Parse` はDBを読まない。幅と高さは、描画の前に本文の画像のIDを集めて、`media` の口でまとめて取り出す。`test/sql_static_test.go` を通す形で書く。
- 編集の画面に「画像を挿入」の `details` を足す。画像の一覧の各行に「本文の末尾に追加」のボタンを置く。ボタンは今のプレビューと同じ `formaction` の形で、保存せずに、記法を足した入力を描き直す。JavaScriptもコピーも要らない。記法の文字は、説明のエスケープまで含めて、読み取りと同じ規則の関数で作る。
- プレビューでは、画像を管理者の経路で描く。下書きの画像は公開の経路では404のため。
- 公開ページは `page.html` の `richtext` の部品のまま、画像の部品を足す。

### 8.2 お知らせ

- 本文はプレーンテキストのまま（14節の決定2）。記事に代表画像を1枚持てる。
- 作成・編集の画面に「代表画像」の選択を足す。縮小表示つきのラジオで、先頭は「なし」。
- 公開の詳細（`news_show.html`）の見出しの下に表示する。一覧には出さない。
- `/api/news` と `/news` の一覧は変えない。

### 8.3 カタログ

- 本文はプレーンテキストのまま。項目に代表画像を1枚持てる。
- 作成・編集の画面は、お知らせと同じ選択の部品を使う。
- 公開の詳細（`show.html`）の見出しの下と、公開の一覧（`list.html`）のカードに表示する。一覧はhtmxの差し替えでも同じ部品で描く。
- 一覧のカードは、画像が無い項目でも崩れないようにする。

### 8.4 共通

- 列の追加は5.1節。
- 記事の編集の画面で画像を足すときは、「画像の管理」を新しいタブで開く。編集中の入力を失わないため。戻ったら、プレビュー等で一覧を描き直す。
- 選択の一覧は新しい順に1ページ12件で出す。**今選んでいる画像は、一覧の範囲の外でも必ず出す。** 本文だけの保存で「なし」に変わる事故を防ぐため。古い画像にはページ送りで届くようにする。ページ送りは編集中の入力を保つ。
- `media` を外しても、各機能は画像なしで動く。「他の機能があるか」で分岐せず、`features` の口を使う。
- MCPの更新は全置換のため、代表画像の値を消さないようにする。第1段階の更新は代表画像の列を `SET` に含めない。
- 対象の状態のハッシュに代表画像のIDを足すだけでは、競合を防げない。お知らせの `UpdateIfUnchanged`・`SetPublishedIfUnchanged` の `WHERE` と、カタログのトランザクション内の照合にも代表画像のIDを足す。編集と公開・非公開の両方のツールで、確認の後に管理画面が画像を変えた場合は保存しない。

## 9. 公開ページの表示

- 共通の部品 `media-image` を `components.html` に足す。出力は `<img src alt width height loading="lazy" decoding="async">`。`width`・`height` で読み込み時のずれを防ぐ。
- CSSは `style.css` に足す。`max-width: 100%`、`height: auto`。インラインの `style` は使わない。
- 代表画像は `figure` にしない。説明の文を画面に出す機能は今回作らない。
- 画像を読めないときも本文は読める。
- 公開ページはセッションを照合しない今の形を保つ。

## 10. MCP（第2段階）

第1段階では、固定ページの本文に既存の画像の記法を書ける（管理画面と同じ検査）。代表画像の変更とアップロードは第2段階にする。

- 今の本文の上限は64KBで、画像は入らない。上限を広げても、画像の文字データがAIの会話を通るため採らない。
- まず読み取りのツール `media_list` を足す。
- アップロードは、確認を通った書き込みのツールが1回限りの切符を返し、エージェントが別の経路へファイルを送る形にする。

```sh
curl -X POST https://example.com/media/upload \
  -H "Authorization: Bearer <1回限りの切符>" \
  -F file=@photo.jpg
```

| 時点 | 確かめること |
|---|---|
| 発行 | トークン、`mcp:write`、`CanManageSite`、機能のMCPが有効、利用者の確認の承諾 |
| 送信 | 切符が存在し、期限内で未使用、アカウントが有効でロールが足りる、接続が停止されず認可の世代が同じ、機能のMCPが有効、ファイルが範囲内 |

- 切符は短命の認証情報で、AIの会話を通る。256ビットの乱数にし、DBにはSHA-256のハッシュだけを保存する。期限5分、1回限り、ファイル1枚、アカウントと接続に結びつける。
- 切符をURLに入れない。ログに出さない。POSTだけ受け、Cookieを使わず、CORSを許可しない。発行に回数の上限を付ける。
- 切符の消費と保存は1つのトランザクションで行う。保存した画像は未使用で、公開には記事の更新か公開が要り、その操作は利用者の確認を通る。
- ファイルを送れるクライアントでしか使えない。切符の表と経路は承認境界2・5で、今のMCPの承認の範囲に入らない。MCP-INV-2との関係を設計で決める。

## 11. バックアップとプライバシー

- 毎日DB全体を複製するため、画像の容量は世代の分だけ増える。300MBなら、14世代で約4GB、30世代で約9GB。画像は圧縮が効きにくい。
- `VACUUM INTO` は複製の間、DBと同じ容量を追加で使う。`pre-migration-*.db` も画像の分だけ大きくなり、自動では消えない。
- `docs/deploy.md` に、世代の見積もり、DBの実サイズ、WAL、複製を作る間の空き容量の監視、複製の所要時間、容量不足のときの失敗と復旧を足す。代表的な容量で複製の時間を測る。
- 消した画像も、複製の保持期間が過ぎるまで残る。
- 閲覧者の情報は新しく取得しない。外部の画像も読まない。

- CDNを使う構成では、画像のキャッシュと、公開の取り消しの遅れを説明する。

| 画像を別のファイルに保存する | バックアップと削除の整合の手間が増える。書き込み先のフォルダと権限も増える |

## 18. 画像の記法の読む規則（案）

Fableの短いレビューの指摘（高は無し）を反映した案。実装のときに `docs/richtext.md` へ移す。

### 18.1 対象

`richtext.Parse` は固定ページと社内文書の両方が使う。社内文書には画像を付けないため、今の `Parse(body)` は変えない。画像を読む入口を別に足す（例: `ParseWithImages(body)`）。読み方の違いは、次の行の種類の有無だけにする。社内文書で同じ行を書いても段落のままになる。

固定ページの呼び出しは3か所（保存の検査 `store.go`、公開の表示 `pages.go`、プレビュー `admin.go`）とも新しい入口に替える。1か所でも残すと、上限を超えた本文が保存を通って公開ページが500になる、プレビューに画像が出ない、といった食い違いが起きる。`body_limit` の文言にも画像の上限を入れる。

### 18.2 行の種類

`docs/richtext.md` 2節の表で、順5（表の行）の後、順6（箇条書き）の前に足す。

| 順 | 条件 | 種類 | 今のブロック |
|---|---|---|---|
| 5.5 | 整えた行が18.3の形に全部当たる | 画像 | 閉じる |

- `!` で始まる行は順2〜5に当たらないため、今の表の判定は変わらない。
- 形に当たらない行は、これまでどおり段落の行として読む。書き方の誤りはエラーにしない。
- 段落の途中でも、画像の行は新しいブロックを始める。
- ブロックの種類に `image` を足す。持つのは説明とファイル名（`<id>.<ext>`）で、URLは持たない。公開ページは `/media/...`、プレビューは管理者の経路と、描く側が組み立てる。

### 18.3 形

判定は `lex` の結果の記号で行う。`!` は今の `escapable`・`symbols` に足さない。

1. 行全体を1回 `lex` で読む。先頭のトークンが文字の `!`（`\` で作った文字でない）。行頭に空白が無い。
2. 次のトークンが記号の `[`。
3. 次の記号の `]` までが説明。その間の `[`・`(`・`)`・`|`・`*` の記号は文字として扱う。強調やリンクは読まない。
4. `]` の直後が記号の `(`。
5. 次の記号の `)` までがURL。`)` が行の最後の文字。
6. URLに `\` で作った文字が無く、`^/media/[a-f0-9]{32}\.(jpg|png)$` に当たる。
7. 説明は、`\` を解決し、前後の空白を除いた後の文字（rune）で数えて1〜200文字で、その文字を説明に使う。リンクの文字と違い、前後の空白を除く。

どれかに当たらなければ、同じトークンを段落の行として読む。

| 入力 | 読み方 |
|---|---|
| `![本社](/media/<32文字>.jpg)` | 画像 |
| `![a\]b](/media/<32文字>.png)` | 画像（説明は `a]b`） |
| `![a*b(c)](/media/<32文字>.jpg)` | 画像（説明は `a*b(c)`） |
| `![a](/media/<32文字>.jpg) ` | 画像（行末の空白は整える段階で消える） |
| ` ![a](/media/<32文字>.jpg)` | 段落 |
| `!\[a](/media/<32文字>.jpg)` | 段落（文字として書く方法） |
| `![](/media/<32文字>.jpg)`・`![ ](/media/<32文字>.jpg)` | 段落 |
| `![a](/media/<32文字>.gif)`・`![a](/media/<32文字>.jpg?x=1)`・`![a](/media/ABC.jpg)`・`.JPG`・`.jpeg`・32文字の大文字の16進数 | 段落 |
| `![a](/media/<32文字>\.jpg)` | 段落（`\` で作った文字があるため。行全体が文字になる） |
| `![[a]](/media/<32文字>.jpg)` | 段落（説明は最初の `]` まで） |
| `![a]`・`![a](/media/<32文字>.jpg` | 段落 |
| `\![a](/media/<32文字>.jpg)` | 段落（文字「\!」とリンク） |
| 201文字以上の説明 | 段落（`!` とリンク） |
| `![a](https://example.com/x.jpg)`・`![a](/about)` | 段落。`[a](…)` のリンクの規則で読む |
| `![a](/media/<32文字>.jpg) 続き` | 段落 |
| `前 ![a](/media/<32文字>.jpg)`・`- ![a](…)`・`\| ![a](…) \|` | 今の規則のまま。画像にならない |
| `本文`、`![a](…)`、`続き` の3行 | 段落・画像・段落に分かれる |
| 表の直後の画像の行 | 表を閉じて、画像になる |

例は全部テストにする。

### 18.4 上限と速さ

- 画像の行は1行の中だけを読み、形に当たらない行も同じトークンを段落に渡す。読む時間は行の長さに比例する。
- 1ページの画像は100個まで。超えたら `Parse` と同じ上限のエラーを返す。

### 18.5 挿入のボタンの文字

説明の `\` と `]` だけを `\` で逃がして記法を作る関数を `richtext` に置く。ほかの文字を逃がしても読みは同じで、手で直しにくくなるだけのため。

「本文の末尾に追加」は、本文が改行で終わらなければ先に改行を足す。読む規則では空行は要らないが、見やすさのため、画像の行の前に空行を1つ置く。

ファズは `form.Line` を通った説明と任意の本文で、追加すると画像のブロックがちょうど1つ増え、同じ説明とファイル名に戻ることを確かめる。

### 18.6 既存の本文

今の本文に同じ形の行があれば、配備の直後から画像として読まれる。参照は3.2節の起動時の作り直しで数えられる。形の32文字のIDは人が書く値ではないため、衝突は無視する。
