# 業務記録（Records）の計画

状態: 計画のレビュー済み・実装の前（2026-11-05）。見本の定義（日報・備品）の表と列の追加は利用者が承認。計画のレビューは Sol、完成のレビューは Fable の予定。対象の時点は `1e1d66f`。実装の後、今の仕様は `docs/domain/records.md` に移す。

## 目的

日報、備品の台帳、訪問記録のような、小さな会社・団体の業務の記録を、機能ごとに手で作らずに用意したい。Kintone のように、項目と型を定義すると、それに沿った一覧と編集の画面ができる仕組みにする。

ただし、項目を決めるのはログインした利用者ではなく、アプリを保守・カスタマイズする会社・個人とする。定義は Go のコードで書き、実行ファイルに組み込む。項目を変えるには、定義を直してビルドとデプロイをする。

## 決めたこと（利用者との壁打ち、2026-11-05）

| 事項 | 決定 | 理由 |
|---|---|---|
| 項目を決める人 | 保守・カスタマイズする会社・個人。利用者は画面で項目を変えられない | 利用者が自由に項目を作れると、何を預かるかを作る時点で説明できず、データ台帳と承認境界2が働かない |
| 定義の書き方 | Go のコード | 型や選択肢の誤りをコンパイラが止める。YAML は直接依存が増える（境界1）。JSON は解析と検査を自分で書くことになる |
| 作り方 | 定義を読んで動く共通の機能。種類ごとのコードは生成しない | 不具合や脆弱性の修正が全部の種類に効く。定義と生成物のずれが起きない |
| 台帳 | 目的・保持・削除は定義だけに書く。`docs/data-inventory.md` の業務記録の節は定義から生成し、テストで一致を確かめる | 正本を1つにする。Markdown を入力にしない |
| 最初の範囲 | 1つの種類は1つの表。決まった権限の型から選ぶ。状態の遷移、承認、種類をまたぐ参照と更新は無し | 承認や複数の表をまたぐ操作は、種類ごとに形が違い、定義が膨らむ |
| 名前 | 業務記録（Records）。`features/records`、`make add-records` | 「台帳」は `data-inventory.md`（取得・保存データ台帳）と混ざる。「フォーム」はお問い合わせと混ざる |
| MCP | 対応する。読み取りは確認なし、作成と編集は確認あり、削除は無し | 今のMCPの決まりと同じ |

採らなかった案:

- **実行時に項目を定義する（Kintone型）**: 上の理由。必要なら、キットから作る別のアプリとして作る。
- **種類ごとにコードを生成する**: 修正のたびに作り直しが要り、作り直し忘れに古い不具合が残る。
- **全部の種類を1つの表に入れ、値を JSON の列に持つ**: 移行は要らなくなるが、消した項目の値が JSON の中に残り続け、台帳とスキーマの突き合わせも中身まで届かない。

## 承認が要る事項

- **保存データの追加（境界2）**: 業務記録の種類ごとに表を1つ作る。共通の列は `id`・`owner_account`・`revision`・`created_at`・`updated_at`（`revision` は計画のレビューの後に足した、同時の編集の照合用の数）。キットには見本の定義として「日報」と「備品」を同梱し（下の「見本の定義」）、その表と列を足す。今後、定義を足す・項目を足すことも、それぞれ境界2に当たる。承認は定義の差分と、生成された台帳の節の差分で行う。
- 依存（境界1）、外部通信（境界3）、CSS・JS（境界4）は変えない。画面はサーバーで描き、絞り込みと並び替えは普通のフォームの GET で行う。
- 公開範囲（境界5）: 経路は全部ログインの後（`/admin/records/...`）と、既存の `/mcp`。公開ページには何も出さない。

## 定義

```go
package defs

var DailyReport = records.Def{
	Name:      "daily_report", // 表の名前と経路に使う。英小文字・数字・_、30字以内
	Title:     "日報",
	Purpose:   "その日の業務の内容と、翌日の予定を共有するため",
	Retention: "記録を消すまで。退職したアカウントの記録はシステム管理者が消す",
	Access:    records.OwnerWriteAllRead,
	MCP:       true,
	Fields: []records.Field{
		{Name: "work_date", Label: "日付", Type: records.Date, Required: true},
		{Name: "body", Label: "内容", Type: records.LongText, Required: true, Max: 4000},
		{Name: "next_plan", Label: "翌日の予定", Type: records.LongText, Max: 2000},
	},
	ListFields: []string{"work_date", "body"}, // 一覧に出す項目
	SortBy:     "work_date",                    // 既定の並び（新しい順）
}
```

- 定義の一覧（`defs.All`）に登録したものだけが有効になる。
- 起動の時に定義を検査し、誤りがあれば起動を止める。名前の形、重複、`Purpose`・`Retention` が空でないこと、`ListFields`・`SortBy` が実在の項目を指すこと、選択肢の重複、`Max` の範囲、`RenamedFrom`・`Removed` の衝突（下の「移行」）。`RenamedFrom`・`Removed`・`Retired` に書いた名前にも、同じ名前の規則を当てる。テストでも同じ検査を通す。

### 型（最初の版）

| 型 | 列の型 | 入力欄 | 検査 |
|---|---|---|---|
| `Text` | TEXT | 1行 | 文字数の上限（既定200）、改行とタブを拒否 |
| `LongText` | TEXT | 複数行 | 文字数の上限（既定4000）。表示は改行を保つ平文。記法は無し |
| `Integer` | INTEGER | 数値 | 整数、`Min`・`Max` |
| `Date` | TEXT（`YYYY-MM-DD`） | 日付 | 実在の日付 |
| `Select` | TEXT | 選択 | 定義の選択肢のどれか |
| `Bool` | INTEGER（0/1） | チェック欄 | — |

メール、電話、住所、画像、添付、別の種類の行を指す項目は、最初の版に入れない。ただし `Text`・`LongText` には何でも書けるので、個人に結びつく内容を書く運用になる種類は、`Purpose` にそう書く。これは型で防げない限界として、ドメインモデルの「守らない範囲」に書く。

### 権限の型

| 型 | 作る | 読む | 編集・削除 |
|---|---|---|---|
| `OwnerOnly` | ログインした全員 | 本人だけ | 本人 |
| `OwnerWriteAdminRead` | ログインした全員 | 本人とシステム管理者 | 本人。削除はシステム管理者も |
| `OwnerWriteAllRead` | ログインした全員 | ログインした全員 | 本人。削除はシステム管理者も |
| `AllReadWrite` | ログインした全員 | ログインした全員 | ログインした全員 |

- 「ログインした全員」は、停止中でない全ロール（一般ユーザーを含む）。画面は `AccountPage`・`AccountForm` で守る。
- 「システム管理者」はロール `admin`。サイト管理者（`site_admin`）は、公開サイトの編集の役で、業務記録では一般ユーザーと同じ扱いにする。
- 上長や部署による権限は、部署の機能が無いので作らない。
- システム管理者が削除できる型があるのは、`Retention` に書いた「退職したアカウントの記録を消す」を実行できるようにするため。
- **所有者が停止中・削除済みの記録**: どの型でも、システム管理者は、所有者ごとの件数を見て、まとめて削除できる。`OwnerOnly`・`OwnerWriteAdminRead` でも本文は見せず、件数だけを出す（社内文書の移管の画面と同じ考え方）。これが無いと、`OwnerOnly` の記録は本人を削除した後に誰も消せない。移管は最初の版に入れない。
- 停止中の所有者の記録は、読める人（`OwnerWriteAllRead`・`AllReadWrite` の全員）からは引き続き読める。編集は、`AllReadWrite` なら全員、それ以外は誰もできない（本人が再開すれば戻る）。

### 見本の定義

キットに同梱し、テストの対象にする。キットから作るアプリでは、消すか書き換える前提。

- **日報**（`daily_report`）: 上の例。`OwnerWriteAllRead`。
- **備品**（`equipment`）: 品名（`Text`）、管理番号（`Text`）、状態（`Select`: 在庫・貸出中・修理中・廃棄）、使っている人の呼び名（`Text`、任意）、メモ（`LongText`）。`AllReadWrite`。「使っている人」は個人に結びつく項目なので、`Purpose` に書く。

## 保存

### 表

種類ごとに1つ。

```
records_<Name>(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  owner_account TEXT NOT NULL,   -- 作ったアカウントのID。認証の表と外部キーでつながない（社内文書と同じ）
  revision INTEGER NOT NULL,     -- 保存のたびに1増やす。同時の編集の照合に使う
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  f_<項目名> <型>,                -- 項目ごと。NULL 可
  ...
)
```

- 項目の列に `f_` を付け、共通の列と名前がぶつからないようにする。
- 項目の列は全部 NULL 可にする。必須は保存の時にアプリで検査する（後から必須の項目を足しても、既存の行で移行が止まらないように）。
- 照合に `updated_at` を使わない。秒の単位なので、同じ秒の中の2回の保存を見分けられない。`revision` は保存のたびに必ず変わる。

### アカウントの一覧

- `features.AccountDirectoryConsumer` を実装し、アカウントの呼び名と状態を `AccountDirectory` から読む。提供する機能が無い構成（`federatedauth` だけ等）では、社内文書と同じく起動を止める。
- 一覧に無いIDは「削除済みのアカウント」、`Disabled` は「停止中」と分けて出す。
- 一覧の取得に失敗した時は、「削除済み」と扱わず、要求をエラーにする。所有者が居なくなった記録の削除の画面は、特に、誤って現役のアカウントの記録を消さないよう、取得の失敗で止める。

### SQL

表名と列名は定義から組み立てるので、SQLが固定であることの検査（`test/sql_static_test.go`）の例外に登録する。今の例外は「ファイルと、そのファイルで許す箇所の数」で数えるので、業務記録も、文を実行するファイルを1つ（例: `features/records/sqlexec.go`）に限り、箇所の数も固定する。守り:

- 名前に使えるのは、起動の時に検査した定義の `Name`・項目名・`RenamedFrom`・`Removed`・`Retired` だけ（英小文字・数字・`_`、30字以内）。利用者の入力は名前にならない。
- 文は、起動の時に種類ごとに組み立てて、検査済みの文の表として持つ。要求の側は、表から文を**選ぶだけ**で、文字列を足さない。任意のSQLの文字列を受け取る公開の関数は作らない。
- 絞り込みは、種類ごとに1つの文に全部の条件を入れ、使わない条件はプレースホルダの値で無効にする（例: `(? = '' OR f_customer LIKE ? ESCAPE '\')`）。だから、絞り込みの組み合わせで文が増えない。
- 並び替えは、許された「項目と向き」から、完成済みの文への対応表で選ぶ。表に無い指定は既定の並びにする（エラーにしない）。
- 部分一致の語の `%`・`_`・`\` は、文字として扱う（`ESCAPE` で逃がす）。
- テストでは、組み立てた文の識別子が規則に合うことに加えて、画面とMCPの入口から、不正な種類名・項目名・並びの指定・`'` や `%` を含む語を渡し、文が変わらず、結果が正しいことを確かめる。

## 移行

起動の時に、業務記録の `Init` で、組み込まれた定義と実際のDBを比べて差を埋める。DBに版の番号は持たない（今のキットの移行と同じ）。

### 起動の時の動き

| DBの状態と定義 | 動き | 先に取るバックアップ |
|---|---|---|
| 種類の表が無い | 表を作る | 無し |
| 項目の列が無い（改名元も無い） | 列を足す（NULL 可） | 無し |
| 選択肢・上限・必須を変えた | DBは変えない。合わなくなった既存の値はそのまま表示し、編集の時に直してもらう | 無し |
| 項目の列が無く、`RenamedFrom` に書いた昔の名前の列がちょうど1つある | 列の名前を変える | 取る |
| 項目の列も、昔の名前の列も両方ある | **起動を止める**（下の「前の版へ戻すとき」の事故の跡）。DBを戻すよう案内する | — |
| 昔の名前の列が2つ以上ある | **起動を止める** | — |
| `Removed` に書いた列がある | 列を消す | 取る |
| 列の SQL の型が定義と違う | **起動を止める** | — |
| 定義に無い列がある | 使わずに残し、起動のたびに警告のログを出す | — |
| 定義にも `Retired` にも無い `records_` の表がある | 残し、警告のログを出す | — |

- `RenamedFrom` は、昔の名前の**一覧**にする（`a → b → c` と2回変えたなら `c` に `{"a", "b"}`）。途中の版を飛ばした環境でも、残っている昔の名前から直接変えられる。
- 定義の検査で、次を拒否する: 2つの項目が同じ昔の名前を持つ、昔の名前が今の項目名と同じ、同じ名前が `RenamedFrom` と `Removed` の両方にある、`Removed` の名前が今の項目名と同じ。
- 名前の変更と削除は、`store.BackupBeforeMigration` で複製を作ってから、1つのトランザクションで行う。失敗したら元のままで起動を止める。
- 定義に無い列で起動を止めない理由: 列を足した版から前の版へ戻すと、前の版から見てその列は「定義に無い列」になる。止めると、実行ファイルだけで戻せなくなる。残すだけならデータは失われない。
- `RenamedFrom`・`Removed` は、既定では消さない。消してよいのは、全部の環境が反映済みで、かつ、戻す可能性のあるバックアップ（日々のバックアップの保持の期間と、移行の前の複製）も全部反映後のものになってから。残っていても、対象の列が無ければ何もしない。
- 消した列の中身: DBは `secure_delete` が有効なので、消した値は空きの領域でも上書きされる。ただし、日々のバックアップと移行の前の複製には残り、それぞれの保持の期間で消える。これを台帳の削除の欄に書く。

### 型の変更と、書き換えの誤りの検出（開発の時）

`Text`・`LongText`・`Date`・`Select` はどれも TEXT の列なので、起動の時にDBの型と比べるだけでは、`Text → Date` のような意味の変更を見分けられない。また、項目名を書き換えただけの誤り（改名のつもりが、新しい項目と、残った古い列になる）も、起動の時には「列の追加」と「定義に無い列」にしか見えない。

これは開発の時に止める。生成した台帳の節（下の「台帳」）は、項目ごとの論理の型まで持つので、**コミット済みの台帳の節を、前の状態の記録として使う**。

- `make records-inventory` は、今の台帳の節と定義を比べ、次の場合は書き出さずに止める。
  - 台帳にある項目が、定義から消えたのに、`Removed` にも、どれかの項目の `RenamedFrom` にも無い。
  - 同じ項目の論理の型が変わった。
- 台帳のテストも同じ比べ方をするので、定義だけ直して台帳を作り直さないと落ちる。
- 限界: 台帳の節を手で消してから作り直すと、この検査は効かない。起動の時は、SQL の型が変わった場合だけを止める。これを `docs/domain/records.md` に書く。

### 種類をやめるとき

- 種類を定義の一覧から外すときは、`Retired`（やめた種類の名前と、残っているデータの説明）に移す。表は残り、台帳の節にも「やめた種類（データは残っている）」として載り続ける。画面とMCPには出ない。
- 表を消す操作は、コマンド（`CommandFeature`）として、確認と複製つきで用意する。消した後に `Retired` から外す。
- `Retired` に書かずに定義から外すと、台帳の節の検査（上と同じく、台帳にある種類が消えた）で、`make records-inventory` が止まる。これで、データが残っているのに台帳から説明が消えることを防ぐ。

### 前の版へ戻すとき

- 種類や項目を足しただけなら、前の版の実行ファイルへ戻すだけでよい。前の版は、知らない表と列を警告だけで残し、読み書きを続ける（全部の文が列名を明示する）。新しい版へ戻せば、その列の値も残っている。
- 名前の変更・削除をした後に、**DBを戻さずに**前の版を起動すると、前の版は昔の名前の列を「足りない列」として空で作り直してしまう。その前の版で書いた値は昔の名前の列に入り、新しい版へ戻した時には、新旧の両方の列がある状態になる。新しい版はこれを検出して起動を止める（上の表）が、値は2つの列に分かれてしまう。
- だから、名前の変更・削除の後に前の版へ戻すときは、**起動する前に**移行の前の複製からDBも戻す。`docs/deploy.md` の表を作り直す更新と同じ扱いで、手順書に書く。

## 台帳

- `docs/data-inventory.md` に「業務記録」の節を置き、その中の種類ごとの表は、印（`<!-- records:begin -->` と `<!-- records:end -->`）で囲んだ生成の範囲にする。手で直さない。
- `make records-inventory` が、定義から節を書き出す。テストは、定義から作った節と、台帳にある節が一致することを確かめる。ずれたら落ち、作り直しのコマンドを案内する。
- 節は、今の台帳と同じ形（`### テーブル: records_<Name>` と、列名の表）で書く。共通の列（`id`・`owner_account`・`revision`・`created_at`・`updated_at`）も行として出す。表の前の文に、種類の目的、保持、削除の方法、権限の型、MCPに出すかを書き、列の行に項目の論理の型と表示名を書く。
- `test/data_schema_test.go` は、今は Core と各機能の `migration.sql` だけを流し、Go の移行を呼ばない。業務記録の表を作るため、テストから、本番と同じ業務記録の移行の関数を、見本の定義で呼ぶ。テスト専用の DDL は持たない。
- やめた種類（`Retired`）と、定義に無いまま残っている列は、新しいDBの検査では見つからない。やめた種類は上のとおり台帳に残す。残っている列は、本番の起動の時の警告で見つけ、`Removed` に書いて消す運用にする（デプロイの手順で、警告のログを確かめる）。
- 台帳の冒頭の「makeコマンドで自動生成・更新されません」を、「業務記録の節だけは、定義から生成します」に直す。
- ログインの後の `/admin/data-notice` に、有効な種類ごとの目的と保持を出す（`PrivacyNotices`）。

## 画面

`docs/components.md` の「画面の型」で作り、`test/admin_ui_test.go` の見本の表に、見本の定義の画面を足す。

| 経路 | 画面の型 |
|---|---|
| `GET /admin/records` | 一覧（使える種類の一覧） |
| `GET /admin/records/{name}` | 一覧（絞り込み・並び替え・ページ送り） |
| `GET/POST /admin/records/{name}/new` | 作成 |
| `GET /admin/records/{name}/{id}` | 詳細 |
| `GET/POST /admin/records/{name}/{id}/edit` | 編集 |
| `GET/POST /admin/records/{name}/{id}/delete` | 削除の確認 |
| `GET/POST /admin/records/{name}/orphans` | 一覧（停止中・削除済みの所有者ごとの件数と、まとめての削除。システム管理者だけ） |

- 一覧の絞り込み: `Text`・`LongText` の語（部分一致）、`Select` の値、`Date` の期間、`OwnerWriteAllRead`・`AllReadWrite` では「自分の記録だけ」。並びは `ListFields` の項目と更新日時から選ぶ。
- 管理画面のナビに、読める種類を1つずつ出す（「日報」「備品」）。
- 同時の編集: 編集の画面で読んだ時の `revision` を送り、`UPDATE ... WHERE id = ? AND revision = ?` の1つの文で照合と保存を行う。変わっていたら保存せず、もう一度開くよう案内する。削除も同じ。
- 読めない行、存在しない種類・行は、同じ404にする（行の有無を漏らさない）。
- JS は使わない。

## MCP

`features.MCPFeature` を実装し、`MCP: true` の種類ごとにツールを出す。

| ツール | 内容 | 確認 |
|---|---|---|
| `records_<name>_list` | 一覧（画面と同じ絞り込み） | 無し |
| `records_<name>_get` | 1件 | 無し |
| `records_<name>_create` | 作成 | クライアントで確認 |
| `records_<name>_update` | 編集 | クライアントで確認 |

- 入力の形（JSON Schema）は定義から作る。`Select` は `enum`、`Date` は `format: date`、上限は `maxLength` 等。
- 確認の文は、今の機能と同じく `features.MCPSummary` で組み立てる。最初の3行に操作・対象・変わる項目の名前を置き（MCP-INV-9）、入力の値は `features.MCPQuote` で引用する。対象は「日報 #12（作った人: 呼び名）」のように、種類と行のIDで特定する。編集では変わる項目だけを、値は省略せずに全部出す。
- 確認の文の上限（4,000字）を超える場合は、省略せずに実行を断り、管理画面で編集するよう案内する。日報の内容（上限4,000字）のような長い項目は、MCPでは書けない場合がある。これを `docs/domain/records.md` に書く。
- 権限は接続したアカウント本人と同じ。一般ユーザーも使える（`AllRoles`）。ロールや状態は実行の時にも読み直す。
- 確認から実行までに行が変わっていたら実行しない。確認の時の `revision` を計画に持ち、実行は画面と同じ `UPDATE ... WHERE id = ? AND revision = ?` の1つの文で行う（照合と保存の間に割り込めない）。
- 削除は無し（今のMCPの決まりと同じ）。
- `/admin/mcp` で有効にする時に、記録の内容がAIのサービスへ送られることを注意として出す（`MCPEnableNoticeFeature`）。台帳の節にも、MCPに出す種類はそう書く。

## ドメインモデルと文書

- `docs/domain/records.md` を作る。用語、権限の表、不変条件（`RECORDS-INV-n`）、守らない範囲。
- 守らない範囲（案）: 利用者による項目の定義、承認・状態の遷移、部署・上長による権限、種類をまたぐ参照と更新、添付と画像、行の履歴、移管、一括の取り込みと書き出し、`Text`・`LongText` に書かれた個人に結びつく内容を型で防ぐこと、台帳の節を手で消した後の型の変更の検出。
- `docs/ui/use-cases.md` に業務記録の節を足す（記録を書く、他の人の記録を読む、退職者の記録を消す、項目を足す〔保守の会社〕）。
- README に機能の節と `make add-records` を足す。
- 定義の書き方と、項目の追加・名前の変更・削除・種類をやめる手順を、`docs/domain/records.md` に書く。前の版へ戻す時の注意は `docs/deploy.md` にも書く。
- プライバシーポリシー: 業務記録はログインの後の利用なので、公開の `/privacy` には載せず、`/admin/data-notice` に出す（AUTH-INV-28 と同じ）。

## テスト（主なもの）

- 定義の検査: 名前の規則（`RenamedFrom`・`Removed`・`Retired` も）、目的・保持が空、存在しない項目の指定、`RenamedFrom`・`Removed` の衝突、で起動を止める。
- 移行: 次の表で、起動の後のDBと、起動を止めるかを確かめる。2回起動しても変わらない。

  | DB | 確かめること |
  |---|---|
  | 新規 | 表と列ができる |
  | 前の版（列が少ない） | 列が足される |
  | 改名の前 | 改名され、複製が作られる |
  | 改名を2回分飛ばした（`a` のまま、定義は `c`） | `a` から `c` へ変わる |
  | 改名済み | 何もしない |
  | 新旧の両方の列がある | 起動を止める |
  | `Removed` の列がある | 消え、複製が作られる |
  | 定義に無い列がある | 残して警告 |
  | SQL の型が違う | 起動を止める |

- 新しい版 → 前の版 → 新しい版: 列を足しただけなら、値を失わずに行き来できる。改名の後にDBを戻さず前の版を起動すると、新しい版が起動を止める。
- 台帳の検査: 項目を `Removed`・`RenamedFrom` に書かずに消すと止まる。論理の型を変えると止まる。種類を `Retired` に書かずに外すと止まる。生成した節と台帳が一致する。印の中を手で直すと落ちる。
- 台帳とスキーマ: 見本の定義で業務記録の移行を流したDBと、台帳の表名・列名が一致する。
- 権限: 4つの型ごとに、本人・他のアカウント（一般ユーザー・サイト管理者）・システム管理者・停止中・削除済みの所有者について、一覧・詳細・編集・削除・まとめての削除・MCPで何ができるかを表で確かめる。読めない行と存在しない行が同じ404。ロールを下げた後のMCPの再実行。アカウントの一覧の取得に失敗した時に、削除済みと扱わない。
- 入力の検査: 型ごとの境界（上限ちょうど・超え、実在しない日付、選択肢に無い値、改行入りの `Text`）。
- 同時の編集: 同じ秒の中の2回の保存でも、古い `revision` の保存が止まる。MCPの確認の後の変更で止まる。
- SQL: 組み立てた文の識別子が規則に合う。画面とMCPの入口から、不正な種類名・項目名・並びの指定と、`'`・`%`・`_`・`\` を含む語を渡しても、文が変わらず、結果が正しい。
- MCP: 確認の文の最初の3行、値の引用、上限を超えた時に断ること。
- 画面: 見本の定義の画面が、画面の型の検査を通る。
- ログ: 記録の値がログに出ない（今のカナリアの検査に、見本の定義を足す）。

## 外部のレビュー

設計スキルの決まり（守りに触れる変更、SQLの検査の例外）により、実装の前に計画のレビューを受け、出来上がりもレビューを受ける。計画は Sol、出来上がりは Fable。

### 計画のレビュー（Sol、2026-11-05）で直したこと

| 重大度 | 指摘 | 直したこと |
|---|---|---|
| 高 | 改名・削除の後にDBを戻さず前の版を起動すると、前の版が昔の名前の列を作り直し、値が新旧の列に分かれる | 起動する前にDBも戻すことを明記。新旧の両方の列があれば起動を止める |
| 高 | `Text → Date` のような論理の型の変更は、DBの型との比較では見分けられない | コミット済みの台帳の節を前の状態として使い、開発の時に止める。起動の時はSQLの型だけ |
| 高 | 台帳とスキーマのテストは `migration.sql` だけを流し、業務記録の表を作らない | テストから本番と同じ移行の関数を呼ぶ。節の形を今の台帳にそろえる |
| 中 | 定義から外した種類・列が、データが残ったまま台帳から消える | やめた種類は `Retired` に移して台帳に残す。外し忘れは台帳の検査で止める |
| 中 | `OwnerOnly` は本人を削除すると誰も消せない | 停止中・削除済みの所有者の記録を、件数だけ見せてまとめて消す画面をシステム管理者に用意 |
| 中 | 改名の衝突と、途中の版を飛ばした環境の扱いが無い | 昔の名前を一覧にし、衝突は定義の検査で拒否。消してよい条件にバックアップを含める |
| 中 | `updated_at` は秒の単位で、同じ秒の保存を見分けられない | `revision` を足し、照合と保存を1つの文で行う |
| 中 | MCPの確認の文が、今の表示の決まりと4,000字の上限を満たさない | `MCPSummary`・`MCPQuote` を使い、上限を超えたら断って管理画面へ案内 |
| 中 | SQLの例外の範囲と、絞り込みの文の選び方が曖昧 | 実行するファイルと箇所の数で例外にする。絞り込みは1つの文、並びは対応表。入口からの試験を足す |
| 中 | アカウントの一覧を読む口と、取得の失敗の扱いが無い | `AccountDirectoryConsumer` を使い、提供者が無ければ起動を止め、失敗を削除済みと扱わない |
