# 業務記録（Records）の計画

状態: 計画のレビュー済み・実装中（2026-11-06）。見本の定義（日報・備品）の表と列、共通の列 `revision`、種類の記録の表 `records_tables` と手順の記録の表 `records_steps` の追加は利用者が承認。計画のレビューは Sol（1回目）、Fable と Sol（2〜5回目）。完成のレビューは Fable と Sol の予定。対象の時点は `1e1d66f`。今の仕様の正本は [docs/domain/records.md](../domain/records.md)（実装の前に書いた）。

## 目的

日報、備品の台帳、訪問記録のような、小さな会社・団体の業務の記録を、機能ごとに手で作らずに用意したい。Kintone のように、項目と型を定義すると、それに沿った一覧と編集の画面ができる仕組みにする。

ただし、項目を決めるのはログインした利用者ではなく、アプリを保守・カスタマイズする会社・個人とする。定義は Go のコードで書き、実行ファイルに組み込む。項目を変えるには、定義を直してビルドとデプロイをする。

## 決めたこと（利用者との壁打ち、2026-11-05）

| 事項 | 決定 | 理由 |
|---|---|---|
| 項目を決める人 | 保守・カスタマイズする会社・個人。利用者は画面で項目を変えられない | 利用者が自由に項目を作れると、何を預かるかを作る時点で説明できず、データ台帳と承認境界2が働かない |
| 定義の書き方 | Go のコード | 型や選択肢の誤りをコンパイラが止める。YAML は直接依存が増える（境界1）。JSON は解析と検査を自分で書くことになる |
| 作り方 | 定義を読んで動く共通の機能。種類ごとのコードは生成しない | 不具合や脆弱性の修正が全部の種類に効く。定義と生成物のずれが起きない |
| 台帳 | 目的・保持・削除は定義だけに書く。`docs/data-inventory.md` の業務記録の節は定義から生成し、テストで一致を確かめる | 正本を1つにする。Markdown を入力にしない |
| 最初の範囲 | 1つの種類は1つの表。決まった権限の型から選ぶ。状態の遷移、承認、種類をまたぐ参照と更新は無し | 承認や複数の表をまたぐ操作は、種類ごとに形が違い、定義が膨らむ |
| 名前 | 業務記録（Records）。`features/records`、`make add-records` | 「台帳」は `data-inventory.md`（取得・保存データ台帳）と混ざる。「フォーム」はお問い合わせと混ざる |
| MCP | 対応する。読み取りは確認なし、作成と編集は確認あり、削除は無し | 今のMCPの決まりと同じ |

採らなかった案:

- **実行時に項目を定義する（Kintone型）**: 上の理由。必要なら、キットから作る別のアプリとして作る。
- **種類ごとにコードを生成する**: 修正のたびに作り直しが要り、作り直し忘れに古い不具合が残る。
- **全部の種類を1つの表に入れ、値を JSON の列に持つ**: 移行は要らなくなるが、消した項目の値が JSON の中に残り続け、台帳とスキーマの突き合わせも中身まで届かない。

## 承認が要る事項

- **保存データの追加（境界2）**: 業務記録の種類ごとに表を1つ作る。共通の列は `id`・`owner_account`・`revision`・`created_at`・`updated_at`（`revision` は計画のレビューの後に足した、同時の編集の照合用の数）。キットには見本の定義として「日報」と「備品」を同梱し（下の「見本の定義」）、その表と列を足す。今後、定義を足す・項目を足すことも、それぞれ境界2に当たる。承認は定義の差分と、生成された台帳の節の差分で行う。
- **種類の記録と手順の記録の表（境界2）**: `records_tables(table_name, state)` と `records_steps(table_name, version, step)`（主キーは `table_name` と `version`）。種類の状態（`active`・`dropped`）と、その環境に当てた手順ごとの番号・手順の文字列（例: `rename:customer:client`）を持つ。名前・番号・文字列はすべて定義から来て、個人情報は入らない。日時は持たない（正しさに要らないため。いつ変わったかは、移行の前の複製のファイル名とログで分かる）。3回目・4回目のレビューの後に形を替えた（列ごとの状態 → 種類ごとの番号と列の記録 → 手順の記録。5回目の後に、手順の要約のハッシュを手順の文字列に替えた。それぞれ利用者が承認）。
- 依存（境界1）、外部通信（境界3）、CSS・JS（境界4）は変えない。画面はサーバーで描き、絞り込みと並び替えは普通のフォームの GET で行う。
- 公開範囲（境界5）: 経路は全部ログインの後（`/admin/records/...`）と、既存の `/mcp`。公開ページには何も出さない。

## 仕様

今の仕様（型、権限、画面、不変条件、移行、戻し方、MCP、守らない範囲）は [docs/domain/records.md](../domain/records.md) に置く。この計画書には、実装の進め方と、仕様に書かない判断だけを書く。

### 定義の例

```go
var DailyReport = records.RecordDef{
	Name:      "daily_report",
	Title:     "日報",
	Purpose:   "その日の業務の内容と、翌日の予定を共有するため",
	Retention: "記録を消すまで。削除したアカウントの記録はシステム管理者がまとめて消す",
	Access:    records.OwnerWriteAllRead,
	MCP:       true,
	Steps: []records.RecordStep{
		{Version: 1, Add: &records.Add{Field: "work_date", Type: records.Date}},
		{Version: 2, Add: &records.Add{Field: "body", Type: records.LongText}},
		{Version: 3, Add: &records.Add{Field: "next_plan", Type: records.LongText}},
	},
	Fields: []records.RecordField{
		{Name: "work_date", Label: "日付", Required: true},
		{Name: "body", Label: "内容", Required: true, MaxLen: 4000},
		{Name: "next_plan", Label: "翌日の予定", MaxLen: 2000},
	},
	ListFields: []string{"work_date", "body"},
	SortBy:     "work_date",
}
```

### 見本の定義

キットに同梱し、テストの対象にする。キットから作るアプリでは、消すか書き換える前提。

- **日報**（`daily_report`）: 上の例。`OwnerWriteAllRead`。
- **備品**（`equipment`）: 品名（`Text`）、管理番号（`Text`、重複は防がない）、状態（`Select`: 在庫・貸出中・修理中・廃棄）、使っている人の呼び名（`Text`、任意）、メモ（`LongText`）。`AllReadWrite`。「使っている人」は個人に結びつく項目なので、`Purpose` に書く。`AllReadWrite` は削除済みの所有者の記録のまとめての削除の対象外なので、`Retention` に「削除したアカウントの記録はシステム管理者がまとめて消す」とは書かない。

## 実装の進め方

### 段階

1. 定義の型と検査、種類の記録と手順の記録、移行（手順の当て方、3つの突き合わせ、前の版と分岐の検出）、定義の記録と台帳の生成、確認のコマンド、表を消すコマンド。
2. 保存と画面と権限、削除済みの所有者の記録の削除。
3. MCP。
4. 文書（README、`docs/deploy.md` の9節、デプロイのスキル、`/admin/data-notice`）。`minimal-web-kit-privacy` のスキルで、プライバシーの説明（ログインの後の `/admin/data-notice`、アカウント削除の後の保持、バックアップ、MCPでAIのサービスへ送ること）を見直し、生成した台帳の節と画面の説明と食い違わないことを確かめる。これを完了の条件にする。

段階ごとに、監査のスキルの「守りをわざと外す確認」を行い、表を残す。

### SQL

- 文を実行するのは `features/records/sqlexec.go` の決まった箇所だけにし、`test/sql_static_test.go` の `sqlExceptions` に、理由と箇所の数で載せる。移行とコマンドのDDLもここを通る。
- 文は `recordsStatement`（パッケージの外に出ない型）で持ち、作れるのは `buildRecordStatements` だけ。テスト（AST の検査）で、`recordsStatement` の値を作る・欄に代入する・型変換する箇所が `buildRecordStatements` の中だけであることを確かめる。
- コマンド（`records-check`・`records-drop`）は `Init` を通らないので、自分で定義の検査と文の組み立てを呼ぶ。
- 列の有無は `pragma_table_info(?)` に表名をプレースホルダで渡して調べる。
- 読み書きの文は列を全部名前で書く。`SELECT *` と、行を置き換える書き方（`INSERT OR REPLACE` 等）は使わない（RECORDS-INV-18）。
- 絞り込みは種類ごとに1つの文に全部の条件を入れ、使わない条件は値で無効にする。並びは入口で番号に変え、作っておいた文の配列から選ぶ。
- 入口の試験: 画面とMCPに、不正な種類名・項目名・並びの指定、`'`・`%`・`_`・`\` を含む語を渡し、実行された文が起動の時に作った集合のどれかであること（テストの時だけの記録の口で確かめる）と、結果が正しいことを見る。ファズ（`testing.F`）でも同じことを見る。

### 確認のコマンド

- `cmd/server/main.go` で、`backup` と同じく、Store の初期化（ファイルの作成、WAL の設定、Core の DDL）の**前に** `records-check` を分岐する。定義は records のパッケージの関数から直接取る（機能の登録や `Init` は通さない）。
- DBは `mode=ro` で開く（`internal/store/backup.go` に前例）。`immutable=1` は使わない（稼働中のDBの WAL の内容を読み落とすため。`VerifyBackup` の静止した複製向けの指定）。稼働中のサーバーと同時に実行してよい。SQLite が `-wal`・`-shm` を作る・触ることはあるが、表と行は変えない。DBのファイルが無い時は「新しいDB（全部作る）」と出す。
- 定義の検査、文の組み立て、前の版と分岐の検出（`checkRecordsVersion`）、移行の計画（`planRecordsMigration`）と3つの突き合わせ（`reconcileRecordsSchema`）だけを使い、適用はしない。
- 出すもの: 種類ごとの、手順の記録の最後の番号と定義の番号、当てる手順、型の変換で変換できない行の種類・項目・ID、起動を止める理由（分岐、前の版、`dropped`、突き合わせ）、消した印のある表が残っていること。最後に「この更新の後に前の版へ戻すときは、DBも戻す必要がある／実行ファイルだけでよい」の1行。
- これからデプロイする実行ファイルで実行する（前の版は新しい定義を知らない）。

### 表を消すコマンド

- `records-drop <種類>` は `CommandFeature` として作り、Store の初期化の後、`Init` の前に動く。`Init` を通らないので、定義の検査と文の組み立てを自分で呼ぶ。対象は `RetiredDefs` にある種類だけ。

### 台帳

- 生成する節には、`records_tables`・`records_steps` と、種類ごとの `### テーブル: records_<Name>`（共通の列と項目の列）を、今の台帳と同じ形で書く。表の前の文に、目的・保持・削除の方法・権限の型・MCPに出すかを書く。
- やめた種類は `### テーブル:` の見出しにせず、「やめた種類」の箇条書きにする（新しいDBには表が無く、`test/data_schema_test.go` が落ちるため）。表を消したかも書く。
- `test/data_schema_test.go` から、見本の定義で本番と同じ移行の関数を呼び、業務記録の表を作ってから照合する。
- 台帳の冒頭の「makeコマンドで自動生成・更新されません」を、「業務記録の節だけは、定義から生成します」に直す。

### テスト（主なもの）

- 定義の検査: 名前の規則（`a"; DROP TABLE x; --`、大文字、全角、31字、空）、使い回し、衝突、許されない型の変換、`RetiredDefs` と定義の一覧の名前の重複。
- 移行: 新しいDB（手順を1から当てる）、項目の追加、手順ごとの当て方（改名、削除、型の変換の変換ごとの境界、1行でも失敗すれば何も変わらない、NULL と空の文字列、列の宣言の型、作業用の列）、版を飛ばした環境（足した項目を次の版で改名・削除・変換、改名を2回、改名して消す、はい・いいえ → 整数 → 文字）、2回起動しても変わらない、複製は壊す手順を当てる起動だけで1つ。
- 前の版と分岐の検出: 定義の版を複数用意し、壊す手順の後の前の版、往復の中間の版、同じ番号で中身の違う手順（2つのブランチ。最後の項目の名前と型が同じになる組も含む）、で止まる。追加だけの版の行き来（v1 → 足した版 → v1 → 足した版）では止まらず、値を失わない。
- 3つの突き合わせ: あるはずの列が無い、列の宣言の型が合わない、あるはずの無い `f_` の列（知らない番号の追加の分は除く）、種類の記録の無い `records_` の表、で止まる。記録の表と `tmp_` の列は見ない。
- やめた種類: 8節の表の4つの状態ごとに、起動の時と `records-drop` の動きを見る。表を消す前のDB全体の複製を戻した時に警告が出る。`records-drop` の後に、その種類を使う前の版を起動すると止まる。やめた後に作った新しいDBでは、前の版が空の表を作って動く。`RetiredDefs` に無い種類は消せない。
- 手順の文字列: 見本の定義の各手順の文字列を、決まった値で固定して検査する（形を変えると落ちる）。読めない文字列は壊す手順として扱う。
- 前の版で書いた行: 新しい版 → 前の版で既存の行を編集・新しい行を作成 → 新しい版、で、新しい版が足した列の値が残り、前の版で作った行のその列が空で、必須なら次の保存で入力を求める。
- 開発の時の検査: RECORDS-INV-9 の各条件で `make records-inventory` が止まる。定義の記録と台帳の節が今の定義と違うとテストが落ちる。
- 確認のコマンド: 書き込む接続が無い状態で、実行の前後にDBの本体のファイルのハッシュが変わらない。別の接続が書き込み中でも読めて、表と行を変えない（こちらはハッシュでは見ず、表の定義と行で見る）。DBのファイルが無い時の出力。値を出さない。戻し方の1行が正しい。
- 権限: 4つの型ごとに、本人・他の一般ユーザー・サイト管理者・システム管理者・停止中・削除済みの所有者について、一覧・詳細・編集・削除・まとめての削除・MCPを表で確かめる。アカウントの一覧の取得に失敗した時に削除済みと扱わない。ロールを下げた後のMCPの再実行。
- 同時の編集: 同じ秒の中の2回の保存でも、古い版の数の保存が止まる。MCPの確認の後の変更で止まる。
- ログ: 業務記録のカナリアの検査を書く（`test/documents_test.go` の社内文書のものと同じ形）。値・語・変換できない値がログと確認のコマンドの出力に出ない。
- 画面: 見本の定義の画面が、画面の型の検査を通る。`make test-ui` で撮って見る。

## 外部のレビュー

設計スキルの決まり（守りに触れる変更、SQLの検査の例外、Core の起動の経路の変更）により、実装の前に計画のレビューを受け、出来上がりもレビューを受ける。

### 1回目の計画のレビュー（Sol、2026-11-05）で直したこと

| 重大度 | 指摘 | 直したこと |
|---|---|---|
| 高 | 改名・削除の後にDBを戻さず前の版を起動すると、前の版が昔の名前の列を作り直し、値が新旧の列に分かれる | 起動する前にDBも戻すことを明記。新旧の両方の列があれば起動を止める |
| 高 | `Text → Date` のような論理の型の変更は、DBの型との比較では見分けられない | 定義の記録（JSON）に前の定義を残し、開発の時に止める。起動の時はSQLの型だけ。最初はコミット済みの台帳の節を使う案だったが、Markdown を入力にしない決まりに反するので、利用者との確認で JSON に替えた |
| 高 | 台帳とスキーマのテストは `migration.sql` だけを流し、業務記録の表を作らない | テストから本番と同じ移行の関数を呼ぶ。節の形を今の台帳にそろえる |
| 中 | 定義から外した種類・列が、データが残ったまま台帳から消える | やめた種類は `Retired` に移して台帳に残す。外し忘れは台帳の検査で止める |
| 中 | `OwnerOnly` は本人を削除すると誰も消せない | 停止中・削除済みの所有者の記録を、件数だけ見せてまとめて消す画面をシステム管理者に用意 |
| 中 | 改名の衝突と、途中の版を飛ばした環境の扱いが無い | 昔の名前を一覧にし、衝突は定義の検査で拒否。消してよい条件にバックアップを含める |
| 中 | `updated_at` は秒の単位で、同じ秒の保存を見分けられない | `revision` を足し、照合と保存を1つの文で行う |
| 中 | MCPの確認の文が、今の表示の決まりと4,000字の上限を満たさない | `MCPSummary`・`MCPQuote` を使い、上限を超えたら断って管理画面へ案内 |
| 中 | SQLの例外の範囲と、絞り込みの文の選び方が曖昧 | 実行するファイルと箇所の数で例外にする。絞り込みは1つの文、並びは対応表。入口からの試験を足す |
| 中 | アカウントの一覧を読む口と、取得の失敗の扱いが無い | `AccountDirectoryConsumer` を使い、提供者が無ければ起動を止め、失敗を削除済みと扱わない |

### 2回目の計画のレビュー（Fable と Sol、2026-11-05）で直したこと

2人とも、DBが「どこまで適用したか」を持たないことによる穴を見つけた。利用者の承認を得て、列の記録の表 `records_columns` を足した。

| 重大度 | 指摘 | 直したこと |
|---|---|---|
| 高 | DBでは同じ型の列のままの変換（文字 → 日付 など）は、変換済みかを判定できず、起動のたびに再検査して、後の定義の変更で起動が止まる（Fable・Sol） | 列の記録に論理の型を持ち、記録と定義が同じなら何もしない。変換の検査は型の形だけにし、上限・選択肢・必須は見ない |
| 高 | 文字 → 整数 → 文字のような2回の変換や、版を飛ばした環境を区別できない（Sol） | 列の記録の型から変換する。`TypeChangedFrom` を過去の型の一覧にする |
| 高 | 前の版を、DBを戻さずに起動すると、昔の名前の列を空で作り直して値が分かれる（1回目の指摘の残り） | 列の記録の状態（`renamed`・`removed`・`dropped`）を見て、前の版が起動を止める |
| 高 | 停止中の所有者の記録をまとめて消せ、確認の後に再開された人の記録を消す道がある（Fable・Sol） | 対象を削除済みのアカウントだけにした（利用者の判断）。削除したアカウントは戻らず、IDも使い回さないので、競合が起きない |
