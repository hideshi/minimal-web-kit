# 業務記録（Records）の計画

状態: 計画のレビュー待ち（2026-11-05）。見本の定義（日報・備品）の表と列の追加は利用者が承認。計画のレビューは Sol、完成のレビューは Fable の予定。対象の時点は `1e1d66f`。実装の後、今の仕様は `docs/domain/records.md` に移す。

## 目的

日報、備品の台帳、訪問記録のような、小さな会社・団体の業務の記録を、機能ごとに手で作らずに用意したい。Kintone のように、項目と型を定義すると、それに沿った一覧と編集の画面ができる仕組みにする。

ただし、項目を決めるのはログインした利用者ではなく、アプリを保守・カスタマイズする会社・個人とする。定義は Go のコードで書き、実行ファイルに組み込む。項目を変えるには、定義を直してビルドとデプロイをする。

## 決めたこと（利用者との壁打ち、2026-11-05）

| 事項 | 決定 | 理由 |
|---|---|---|
| 項目を決める人 | 保守・カスタマイズする会社・個人。利用者は画面で項目を変えられない | 利用者が自由に項目を作れると、何を預かるかを作る時点で説明できず、データ台帳と承認境界2が働かない |
| 定義の書き方 | Go のコード | 型や選択肢の誤りをコンパイラが止める。YAML は直接依存が増える（境界1）。JSON は解析と検査を自分で書くことになる |
| 作り方 | 定義を読んで動く共通の機能。種類ごとのコードは生成しない | 不具合や脆弱性の修正が全部の種類に効く。定義と生成物のずれが起きない |
| 台帳 | 目的・保持・削除は定義だけに書く。`docs/data-inventory.md` の業務記録の節は定義から生成し、テストで一致を確かめる | 正本を1つにする。Markdown を入力にしない |
| 最初の範囲 | 1つの種類は1つの表。決まった権限の型から選ぶ。状態の遷移、承認、種類をまたぐ参照と更新は無し | 承認や複数の表をまたぐ操作は、種類ごとに形が違い、定義が膨らむ |
| 名前 | 業務記録（Records）。`features/records`、`make add-records` | 「台帳」は `data-inventory.md`（取得・保存データ台帳）と混ざる。「フォーム」はお問い合わせと混ざる |
| MCP | 対応する。読み取りは確認なし、作成と編集は確認あり、削除は無し | 今のMCPの決まりと同じ |

採らなかった案:

- **実行時に項目を定義する（Kintone型）**: 上の理由。必要なら、キットから作る別のアプリとして作る。
- **種類ごとにコードを生成する**: 修正のたびに作り直しが要り、作り直し忘れに古い不具合が残る。
- **全部の種類を1つの表に入れ、値を JSON の列に持つ**: 移行は要らなくなるが、消した項目の値が JSON の中に残り続け、台帳とスキーマの突き合わせも中身まで届かない。

## 承認が要る事項

- **保存データの追加（境界2）**: 業務記録の種類ごとに表を1つ作る。キットには見本の定義として「日報」と「備品」を同梱し（下の「見本の定義」）、その表と列を足す。今後、定義を足す・項目を足すことも、それぞれ境界2に当たる。承認は定義の差分と、生成された台帳の節の差分で行う。
- 依存（境界1）、外部通信（境界3）、CSS・JS（境界4）は変えない。画面はサーバーで描き、絞り込みと並び替えは普通のフォームの GET で行う。
- 公開範囲（境界5）: 経路は全部ログインの後（`/admin/records/...`）と、既存の `/mcp`。公開ページには何も出さない。

## 定義

```go
package defs

var DailyReport = records.Def{
	Name:      "daily_report", // 表の名前と経路に使う。英小文字・数字・_、30字以内
	Title:     "日報",
	Purpose:   "その日の業務の内容と、翌日の予定を共有するため",
	Retention: "記録を消すまで。退職したアカウントの記録はシステム管理者が消す",
	Access:    records.OwnerWriteAllRead,
	MCP:       true,
	Fields: []records.Field{
		{Name: "work_date", Label: "日付", Type: records.Date, Required: true},
		{Name: "body", Label: "内容", Type: records.LongText, Required: true, Max: 4000},
		{Name: "next_plan", Label: "翌日の予定", Type: records.LongText, Max: 2000},
	},
	ListFields: []string{"work_date", "body"}, // 一覧に出す項目
	SortBy:     "work_date",                    // 既定の並び（新しい順）
}
```

- 定義の一覧（`defs.All`）に登録したものだけが有効になる。
- 起動の時に定義を検査し、誤りがあれば起動を止める。名前の形、重複、`Purpose`・`Retention` が空でないこと、`ListFields`・`SortBy` が実在の項目を指すこと、選択肢の重複、`Max` の範囲。テストでも同じ検査を通す。

### 型（最初の版）

| 型 | 列の型 | 入力欄 | 検査 |
|---|---|---|---|
| `Text` | TEXT | 1行 | 文字数の上限（既定200）、改行とタブを拒否 |
| `LongText` | TEXT | 複数行 | 文字数の上限（既定4000）。表示は改行を保つ平文。記法は無し |
| `Integer` | INTEGER | 数値 | 整数、`Min`・`Max` |
| `Date` | TEXT（`YYYY-MM-DD`） | 日付 | 実在の日付 |
| `Select` | TEXT | 選択 | 定義の選択肢のどれか |
| `Bool` | INTEGER（0/1） | チェック欄 | — |

メール、電話、住所、画像、添付、別の種類の行を指す項目は、最初の版に入れない。ただし `Text`・`LongText` には何でも書けるので、個人に結びつく内容を書く運用になる種類は、`Purpose` にそう書く。これは型で防げない限界として、ドメインモデルの「守らない範囲」に書く。

### 権限の型

| 型 | 作る | 読む | 編集・削除 |
|---|---|---|---|
| `OwnerOnly` | ログインした全員 | 本人だけ | 本人 |
| `OwnerWriteAdminRead` | ログインした全員 | 本人とシステム管理者 | 本人。削除はシステム管理者も |
| `OwnerWriteAllRead` | ログインした全員 | ログインした全員 | 本人。削除はシステム管理者も |
| `AllReadWrite` | ログインした全員 | ログインした全員 | ログインした全員 |

- 「ログインした全員」は、停止中でない全ロール（一般ユーザーを含む）。画面は `AccountPage`・`AccountForm` で守る。
- 「システム管理者」はロール `admin`。サイト管理者（`site_admin`）は、公開サイトの編集の役で、業務記録では一般ユーザーと同じ扱いにする。
- 上長や部署による権限は、部署の機能が無いので作らない。
- システム管理者が削除できる型があるのは、`Retention` に書いた「退職したアカウントの記録を消す」を実行できるようにするため。

### 見本の定義

キットに同梱し、テストの対象にする。キットから作るアプリでは、消すか書き換える前提。

- **日報**（`daily_report`）: 上の例。`OwnerWriteAllRead`。
- **備品**（`equipment`）: 品名（`Text`）、管理番号（`Text`）、状態（`Select`: 在庫・貸出中・修理中・廃棄）、使っている人の呼び名（`Text`、任意）、メモ（`LongText`）。`AllReadWrite`。「使っている人」は個人に結びつく項目なので、`Purpose` に書く。

## 保存

### 表

種類ごとに1つ。

```
records_<Name>(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  owner_account TEXT NOT NULL,   -- 作ったアカウントのID。認証の表と外部キーでつながない（社内文書と同じ）
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  f_<項目名> <型>,                -- 項目ごと。NULL 可
  ...
)
```

- 項目の列に `f_` を付け、共通の列と名前がぶつからないようにする。
- 項目の列は全部 NULL 可にする。必須は保存の時にアプリで検査する（後から必須の項目を足しても、既存の行で移行が止まらないように）。
- アカウントの停止・削除で行は消えない。一覧に無いアカウントは「削除済みのアカウント」と出す。移管は最初の版に入れない。

### SQL

表名と列名は定義から組み立てるので、SQLが固定であることの検査（`test/sql_static_test.go`）では、業務記録の文の組み立てを1か所に集め、例外として登録する。守り:

- 名前に使えるのは、起動の時に検査した定義の `Name` と項目名だけ（英小文字・数字・`_`）。利用者の入力は名前にならない。
- 値は全部プレースホルダで渡す。絞り込みの語、並びの方向も、入力をそのまま文に入れず、定義の項目名と `ASC`/`DESC` の固定の値に照らして選ぶ。
- 文は起動の時に種類ごとに組み立てて持ち、要求のたびに組み立てない。
- テストで、全部の見本の定義から組み立てた文に、名前の規則に合わない識別子が無いことを確かめる。

## 移行

起動の時に、業務記録の `Init` で、組み込まれた定義と実際のDBを比べて差を埋める。版の番号は持たない（今のキットの移行と同じ）。

| 定義の変更 | 起動の時の動き | 先に取るバックアップ |
|---|---|---|
| 種類を足す | 表を作る | 無し |
| 項目を足す | 列を足す（NULL 可） | 無し |
| 選択肢・上限・必須を変える | DBは変えない。合わなくなった既存の値はそのまま表示し、編集の時に直してもらう | 無し |
| 項目の名前を変える（`RenamedFrom` を書く） | 古い列があり、新しい列が無ければ、列の名前を変える | 取る |
| 項目を消す（`Removed` に書く） | 列があれば消す | 取る |
| 型を変える | 対応しない。起動を止める | — |
| 定義に無い列がDBにある | 列を使わずにそのまま残し、起動のたびに警告のログを出す（`RenamedFrom` か `Removed` を書くよう案内する） | — |
| 種類を定義から外す | 表は残し、警告のログを出す | — |

- 名前の変更と削除は、`store.BackupBeforeMigration` で複製を作ってから、1つのトランザクションで行う。失敗したら元のままで起動を止める。
- 名前を変えただけのつもりで項目名を書き換えると、「古い項目が消え、新しい項目が足された」と見分けられない。だから、定義に書いていない列を勝手に消さない。
- 定義に無い列で起動を止めない理由: 列を足した版から前の版へ戻すと、前の版から見てその列は「定義に無い列」になる。止めると、実行ファイルだけで戻せなくなる。残すだけならデータは失われない。
- その代わり、書き換えの誤りは開発の側で気づけるようにする。項目名を書き換えると、生成した台帳の節の差分に「列の削除と追加」が出るので、承認境界2のレビューで見つかる。起動の時の警告も、デプロイの手順のログの確認で見る。
- `RenamedFrom`・`Removed` は、全部の環境に反映した後に定義から消してよい。残っていても、対象の列が無ければ何もしない。
- 消した列の中身: DBは `secure_delete` が有効なので、消した値は空きの領域でも上書きされる。ただし、日々のバックアップと移行の前の複製には残り、それぞれの保持の期間で消える。これを台帳の削除の欄に書く。
- 種類ごと消す操作（表を消す）は、最初の版では作らない。必要になったら、コマンド（`CommandFeature`）として、確認と複製つきで足す。

### 前の版へ戻すとき

- 種類や項目を足しただけなら、前の版の実行ファイルへ戻すだけでよい。前の版は知らない表と列を無視する（全部の文が列名を明示する）。
- 名前の変更・削除をした後は、前の版は起動の時に「定義に無い列」ではなく「定義にある列が無い」状態になり、読み書きに失敗する。移行の前の複製からDBも戻す。`docs/deploy.md` の表を作り直す更新と同じ扱い。
- 前の版の定義に無い列（新しい版で足した列）は、前の版では警告が出るだけで、読み書きは続く。新しい版へ戻せば、その列の値も残っている。

## 台帳

- `docs/data-inventory.md` に「業務記録」の節を置き、その中の種類ごとの表は、印（`<!-- records:begin -->` と `<!-- records:end -->`）で囲んだ生成の範囲にする。手で直さない。
- `make records-inventory` が、定義から節を書き出す。テストは、定義から作った節と、台帳にある節が一致することを確かめる。ずれたら落ち、作り直しのコマンドを案内する。
- 節には、種類ごとに表名、目的、保持、削除の方法、権限の型、MCPに出すか、と、項目ごとの列名・型・表示名を出す。
- 今ある `test/data_schema_test.go`（台帳とスキーマの表名・列名の照合）は、生成された節も普通の行として読むので、そのまま効く。
- 台帳の冒頭の「makeコマンドで自動生成・更新されません」を、「業務記録の節だけは、定義から生成します」に直す。
- ログインの後の `/admin/data-notice` に、有効な種類ごとの目的と保持を出す（`PrivacyNotices`）。

## 画面

`docs/components.md` の「画面の型」で作り、`test/admin_ui_test.go` の見本の表に、見本の定義の画面を足す。

| 経路 | 画面の型 |
|---|---|
| `GET /admin/records` | 一覧（使える種類の一覧） |
| `GET /admin/records/{name}` | 一覧（絞り込み・並び替え・ページ送り） |
| `GET/POST /admin/records/{name}/new` | 作成 |
| `GET /admin/records/{name}/{id}` | 詳細 |
| `GET/POST /admin/records/{name}/{id}/edit` | 編集 |
| `GET/POST /admin/records/{name}/{id}/delete` | 削除の確認 |

- 一覧の絞り込み: `Text`・`LongText` の語（部分一致）、`Select` の値、`Date` の期間、`OwnerWriteAllRead`・`AllReadWrite` では「自分の記録だけ」。並びは `ListFields` の項目と更新日時から選ぶ。
- 管理画面のナビに、読める種類を1つずつ出す（「日報」「備品」）。
- 同時の編集: 編集の画面で読んだ時の `updated_at` を送り、保存の時に変わっていたら保存せず、もう一度開くよう案内する。
- 読めない行、存在しない種類・行は、同じ404にする（行の有無を漏らさない）。
- JS は使わない。

## MCP

`features.MCPFeature` を実装し、`MCP: true` の種類ごとにツールを出す。

| ツール | 内容 | 確認 |
|---|---|---|
| `records_<name>_list` | 一覧（画面と同じ絞り込み） | 無し |
| `records_<name>_get` | 1件 | 無し |
| `records_<name>_create` | 作成 | クライアントで確認 |
| `records_<name>_update` | 編集 | クライアントで確認 |

- 入力の形（JSON Schema）は定義から作る。`Select` は `enum`、`Date` は `format: date`、上限は `maxLength` 等。
- 確認の文は、表示名で「日付: 2026-11-05」のように組み立てる。編集では変わる項目だけを出す。
- 権限は接続したアカウント本人と同じ。一般ユーザーも使える（`AllRoles`）。
- 確認から実行までに行が変わっていたら実行しない。照合は `updated_at` と全項目の値で行う（項目を足しても照合から漏れない）。
- 削除は無し（今のMCPの決まりと同じ）。
- `/admin/mcp` で有効にする時に、記録の内容がAIのサービスへ送られることを注意として出す（`MCPEnableNoticeFeature`）。台帳の節にも、MCPに出す種類はそう書く。

## ドメインモデルと文書

- `docs/domain/records.md` を作る。用語、権限の表、不変条件（`RECORDS-INV-n`）、守らない範囲。
- 守らない範囲（案）: 利用者による項目の定義、承認・状態の遷移、部署・上長による権限、種類をまたぐ参照と更新、添付と画像、行の履歴、移管、一括の取り込みと書き出し、`Text`・`LongText` に書かれた個人に結びつく内容を型で防ぐこと。
- `docs/ui/use-cases.md` に業務記録の節を足す（記録を書く、他の人の記録を読む、退職者の記録を消す、項目を足す〔保守の会社〕）。
- README に機能の節と `make add-records` を足す。
- 定義の書き方と、項目の追加・名前の変更・削除の手順を、`docs/domain/records.md` か README の節に書く。
- プライバシーポリシー: 業務記録はログインの後の利用なので、公開の `/privacy` には載せず、`/admin/data-notice` に出す（AUTH-INV-28 と同じ）。

## テスト（主なもの）

- 定義の検査: 名前の規則、目的・保持が空、存在しない項目の指定、型の変更、で起動を止める。
- 移行: 新規のDB、項目の追加、名前の変更、削除（複製が作られる）、定義に無い列は残して警告、型の変更で止まる、2回起動しても変わらない、前の版のDB（列が少ない）から上がる。
- 権限: 4つの型ごとに、本人・他のアカウント・システム管理者・停止中が、一覧・詳細・編集・削除・MCPで何ができるかを表で確かめる。読めない行と存在しない行が同じ404。
- 入力の検査: 型ごとの境界（上限ちょうど・超え、実在しない日付、選択肢に無い値、改行入りの `Text`）。
- 同時の編集: 古い `updated_at` での保存が止まる。MCPの確認の後の変更で止まる。
- SQL: 組み立てた文の識別子が規則に合う。絞り込みの語に `'` や `%` が入っても文が変わらない。
- 台帳: 生成した節と台帳が一致する。印の中を手で直すと落ちる。
- 画面: 見本の定義の画面が、画面の型の検査を通る。
- ログ: 記録の値がログに出ない（今のカナリアの検査に、見本の定義を足す）。

## 外部のレビュー

設計スキルの決まり（守りに触れる変更、SQLの検査の例外）により、実装の前に計画のレビューを受け、出来上がりもレビューを受ける。これまでと同じく、計画は Sol、出来上がりは Fable を想定する。

### レビューで見てほしいこと

1. SQLを定義から組み立てる守り（名前の規則、起動の時に組み立てて持つ、検査の例外の範囲）で足りるか。
2. 権限の4つの型と、一般ユーザー・システム管理者の扱いに、穴や紛らわしさが無いか。
3. 移行の「定義に無い列は残して警告」で、書き換えの誤り（名前を変えたつもりで新しい項目になった）が見逃されないか。前の版へ戻した時の挙動に穴が無いか。
4. 台帳の生成の範囲と、今のテストの関係に、二重管理や抜けが無いか。
5. MCPの照合と確認の文が、今のMCPの決まりと合っているか。
