# お知らせの LINE への一斉送信 実装計画

状態: 2026-11-17、利用者が範囲（一斉送信だけ、題名と URL だけ、サイト管理者以上、1記事に1回だけ、毎回通知する）と、承認境界2（送った記録の表）・3（`api.line.me` への送信）を承認した。外部のモデル（Codex、gpt-6.1-sol）の計画のレビューを受け、12節のとおり直した。2026-11-18、利用者がトークンの種類を案B（送るたびにステートレスのトークンを発行する）に決め、トークンの発行の送り先も承認境界3に含めた（5節）。

対象の時点: `150b100` から。

正本: 実装の作業の初めに [domain/news.md](../domain/news.md) と [ui/use-cases.md](../ui/use-cases.md) へ移す（10節）。

## 1. 目的と範囲

見込み顧客や顧客が LINE 公式アカウントの友だちになっているサイトで、新しいお知らせを、管理画面から友だち全員へ知らせられるようにする。知らせるだけにして、読むのはサイトの記事のページで行う。

- 送るのは、サイト名・記事の題名・記事の URL のテキスト1通だけ。本文や冒頭は送らない。
- 送るのは、管理者がボタンを押したときだけ。公開の操作や予約公開の時刻に合わせて自動では送らない（予約公開の記事は、公開日時を過ぎると操作なしで公開側に出るため、自動で送るには裏で動く仕組みが要る）。
- 1つの記事は1回だけ送れる。届いたか分からないまま期限を過ぎた記事も、キットからは送らない（3節）。
- 設定しなければ、ボタンを出さず、外へ通信しない。

作らないもの: 個別の送信（Push）、友だちの識別子の保存、Webhook の受信、リッチメニューの設定、絞り込みの配信（Narrowcast）、画像や Flex Message、通知の音を消す選択、確認の画面での残りの通数・友だちの数の表示、お知らせ以外の機能（カタログ・固定ページ）からの送信、AIエージェント（MCP）からの送信、送信の予約、届いたか分からない記事の送り直し。個別のやり取りは、LINE 公式アカウントの管理画面かアプリのチャットで行う（無料の通数を使わない）。

## 2. 画面

| 画面 | 経路 | 型 | 内容 |
|---|---|---|---|
| お知らせの編集 | `GET /admin/news/{id}`（既存） | 作成・編集 | 公開などの別操作の並びに「LINE で知らせる」のリンクを足す。記録の状態（3節）に応じて、リンクの代わりに「LINE で知らせた日時」か「届いたか分からない」を出す |
| LINE での知らせの確認 | `GET /admin/news/{id}/line` | 取り消せない操作の確認（新しい型。下記） | 送る文面をそのまま見せ、友だち全員に届くこと、取り消せないこと、通数を使うこと、1回だけ送れることを説明する |
| 送信 | `POST /admin/news/{id}/line` | — | 送って、編集の画面へ戻し、結果を `notice`・`error` で見せる |

- 守り: 既存のお知らせの管理画面と同じ `f.admin.Page`・`f.admin.Form`（サイト管理者以上。CSRF の検査を含む）。
- 確認の画面に出す文面:
  - 記録が無ければ、今の記事から作った文面を出し、その SHA-256 をフォームの隠し項目で送る。送信のときに作り直した文面と照らし、違えば（確認の後に題名が直された）送らずに確認の画面を出し直す。
  - 記録があれば、保存した文面を出す。題名を後から直しても変わらないことを添える。
- **画面の型**: 今の「削除の確認」の検査は、ボタンの横に「削除せずに戻る」の文字列を求めている（`test/admin_ui_test.go` の `kindConfirm`）。「取り消せない操作の確認」の型を足し、`h1`（「〜の確認」）→ 対象と影響の説明 → `btn-primary` の送信と「送らずに戻る」（`btn-secondary`）の `action-bar` とする。削除の確認の型と検査は変えない。`docs/components.md` の4節と、検査の型の表に足す。

送る文面（例）:

```
{SITE_NAME}のお知らせ
{題名}
{SITE_URL}/news/{id}
```

題名は200文字まで（`maxTitleRunes`）なので、LINE の上限（UTF-16 の単位で5,000）には届かない。それでも、作った文面の UTF-16 の長さを確かめ、超えたら送らない。

## 3. 送信の手順と二重送信の防止

### 記録の項目

記事ごとに1行（4節）。

- `retry_key`・`message`: 再送の鍵と、送る文面。保存した後は、5節の鍵の入れ替えのとき以外は変えない。
- `key_first_sent_at`: 今の鍵で初めて LINE へ要求を出そうとした日時。まだなら NULL。
- `in_flight`: 結果をまだ書いていない要求の数。
- `uncertain`: 受け付けられたかもしれない要求が一度でもあったか（0か1）。1になったら0に戻さない。
- `sent_at`: 送信済みになった日時。

状態は項目から決める。

| 状態 | 条件 | できること |
|---|---|---|
| 未送信 | 行が無い | 送れる |
| 送れる | `sent_at` が NULL、`uncertain` が0、`in_flight` が0 | 送れる。前の要求はすべて、LINE が受け付けなかったと分かっている |
| 結果待ち | `sent_at` が NULL で、`uncertain` が1か `in_flight` が1以上、`key_first_sent_at` から23時間たっていない | 同じ鍵と文面でだけ送れる |
| 届いたか分からない | 結果待ちの条件で、23時間を過ぎた | 送れない |
| 送信済み | `sent_at` が NULL でない | 送れない |

時刻はサーバーの UTC の Unix 秒で比べ、`now < key_first_sent_at + 23時間` のときだけ「たっていない」とする。

### 手順

1. **送る前の書き込み（1つのトランザクション）**
   1. 記事が公開側に出ているか（公開の状態で、公開日時が今以前）を、このトランザクションの中で読む。出ていなければ送らない。
   2. 記録を読み、状態で分ける。送信済み・届いたか分からないなら、送らずに理由を見せる。
   3. 未送信なら、新しい鍵（`crypto/rand` の UUID v4）と、確認した文面で行を作る。
   4. 送れる状態で、`key_first_sent_at` から23時間を過ぎていたら、鍵だけを新しくし、`key_first_sent_at` を NULL に戻す（前の鍵の要求は、どれも受け付けられていないため）。文面は変えない。
   5. `in_flight` を1増やし、`key_first_sent_at` が NULL なら今の時刻を入れる。
   6. コミットする。**コミットに失敗したら、LINE へ送らない**。
   - 2人が同時に押して、両方が「行が無い」と読んだ場合: 行の作成は主キーで1つだけ通る。失敗した側は、トランザクションをやり直して保存済みの行を読む（作った鍵は捨てる）。保存していない鍵では送らない。
   - 1の前に、トークンを発行する（5節）。発行に失敗したら、記録を作らず・変えずに「設定を確かめる」と見せる。一斉送信の要求は出ていないため、受け付けられた心配は無い。
2. **送信**: トランザクションの外で、保存した文面を、保存した鍵の `X-Line-Retry-Key` を付けて送る。同時に押された場合は、同じ鍵の要求が2つ出るが、LINE の側で1回に絞られる。
3. **送った後の書き込み**: 応答で分ける。どの場合も `in_flight` を1減らす。`sent_at` が入っている行は、他の項目を変えない（遅れて返った失敗で、送信済みを戻さない）。

| 応答 | 判断 | 記録 | 画面 |
|---|---|---|---|
| 200 | 受け付けた | `sent_at` を入れる | 送りました |
| 409 で `x-line-accepted-request-id` の見出しがある | 同じ鍵の要求を受け付け済み | `sent_at` を入れる | 送りました |
| 400・401・403・429 | 受け付けなかった（LINE は、エラーを返したときは送信しないと説明している） | 変えない | 429 は「回数か月の通数の上限」、400・401・403 は「設定を確かめる」 |
| それ以外（5xx、上の表に無い 4xx・3xx、見出しの無い 409）・時間切れ・接続の失敗・応答の読み取りの失敗 | 受け付けたかもしれない | `uncertain` を1にする | 結果が分からない。23時間のうちに押すと、同じ鍵で送り直す（重ならない） |

- 送った後の書き込みに失敗したとき（例: 200 の後に DB が書けない）: `in_flight` が残るため、結果待ちになる。画面には「LINE に送ったが、記録に失敗した。もう一度押すと確かめられる（同じ鍵なので重ならない）」と出す。23時間のうちに押せば、409 で送信済みになる。押さずに23時間を過ぎると、届いたか分からないになる。
- プロセスが要求の途中で止まったときも、`in_flight` が残るため、同じ扱いになる。
- 届いたか分からない記事の画面: 「LINE 公式アカウントの管理画面か、友だちのトークで届いたかを確かめる。届いていなければ、LINE 公式アカウントの管理画面から送る」と案内する。キットからは送らない（1記事に1回の決まりと、二重送信を防ぐことを優先する）。
- 送り直しは、管理者がもう一度押したときだけ。自動では送り直さない。
- 送り直しでは、文面を作り直さない（LINE は送り直しで中身を変えないよう求めている）。

### 公開の状態との競合

公開側に出ているかは、1の送る前のトランザクションで確かめる。その後、送信までの間に、別の管理者か AIエージェントが記事を非公開にしたり消したりしても、送信は止めない（送る操作を受け付けた時点で公開中ならよい、とする）。送信の操作と非公開・削除の操作を排他にしない。消した記事の記録は一緒に消えるため、送った後の書き込みは0行になり、画面には結果だけを出す。この競合は `docs/domain/news.md` の守らない範囲に書く。

## 4. 保存するもの（承認境界2）

表 `news_line_broadcasts` を足す。

| 列 | 中身 |
|---|---|
| `post_id` | 記事の番号。主キー。`news_posts(id)` を参照し、記事を消したら一緒に消す |
| `retry_key` | 再送の鍵（UUID） |
| `message` | 送る文面（公開済みの題名と URL だけ） |
| `key_first_sent_at` | 今の鍵で初めて要求を出そうとした日時。NULL を許す |
| `in_flight` | 結果をまだ書いていない要求の数 |
| `uncertain` | 受け付けられたかもしれない要求があったか（0か1） |
| `created_at` | 行を作った日時 |
| `sent_at` | 送信済みになった日時。NULL を許す |

- 個人の情報は入らない。友だちの情報は LINE が持ち、サイトは受け取らない。
- 保持: 記事を消すまで。
- `docs/data-inventory.md` に、この表と、秘密のファイル（DBの外のファイル）を足す。

## 5. 設定と秘密（承認境界3）

**トークンの種類（2026-11-18、利用者が案Bに決めた）**

LINE は、長期のチャネルアクセストークンをセキュリティの面から勧めていない。勧めているのは、短期（30日）・v2.1（30日まで）・ステートレス（15分）のどれか（6節）。

| 案 | サイトが持つ秘密 | 動き | 外への送り先 |
|---|---|---|---|
| A. 長期のトークン | トークン | コンソールで発行したものをそのまま使う | 一斉送信だけ |
| B. ステートレスのトークンを送るたびに発行（勧め） | チャネル ID とチャネルシークレット | 送るたびに15分のトークンを発行し、使い捨てる。保存しない | トークンの発行と一斉送信 |
| C. v2.1 | 秘密鍵（JWK） | JWT に署名してトークンを発行し、期限の前に発行し直す | トークンの発行と一斉送信 |

- 案Aは、いちばん簡単だが、LINE が勧めていない。
- 案Bは、LINE の勧めに入り、トークンの期限の管理も要らない。ただし、チャネルシークレットも期限の無い秘密で、漏れたときの重さはトークンと変わらない（コンソールで発行し直して対処する）。送るたびに、送り先が1つ増える。
- 案Cは、更新の仕組み（裏で動く処理か、送るときの判定）と、鍵の組の作り方の手順が要り、この用途には重い。
**トークンの発行（案B）**

- `POST https://api.line.me/oauth2/v3/token`、`Content-Type: application/x-www-form-urlencoded`。本文は `grant_type=client_credentials`、`client_id`（チャネル ID）、`client_secret`（チャネルシークレット）。JWT の方式は使わない。
- 200 の応答の `token_type`（`Bearer`）・`access_token`・`expires_in`（例: 900）を読む。`token_type` が `Bearer` でない、または `access_token` が空なら、発行の失敗とする。
- トークンは、その1回の一斉送信にだけ使い、メモリにも保存しない。発行したトークンは取り消せないが、15分で切れる。
- 発行の失敗（400 はチャネル ID かシークレットの誤り、その他の応答、時間切れ、接続の失敗）は、一斉送信の前なので、3節の記録を変えない。

**設定と共通の扱い**

- `LINE_CHANNEL_ID`: チャネル ID。秘密ではないので、環境変数にそのまま書く。数字だけを許す。
- `LINE_CHANNEL_SECRET_FILE`: チャネルシークレットを1行で書いたファイル。通知の Webhook と同じ `federation.SecretFile`（通常のファイル、所有者だけが読める）で読む。前後の空白と、末尾の改行1つを除き、残りが空、または中に空白・改行・制御文字があれば起動を止める。エラーに値を含めない。2つは両方そろったときだけ有効にし、片方だけなら起動を止める。
- 有効にするときは、`SITE_URL`（記事の絶対 URL を作るため）と `SITE_NAME` を必須にする。
- 送信は `federation.Client` を使う。許す URL は、`https://api.line.me/oauth2/v3/token` と `https://api.line.me/v2/bot/message/broadcast` の2つだけ。転送に従わない。タイムアウトは10秒。応答の本文は小さい上限で読む。
- ログには、チャネルシークレット、トークン、`Authorization` の見出し、発行と一斉送信の応答の本文、`err.Error()` を出さない。`news line broadcast` に、記事の番号と結果の分類（`sent`・`already_accepted`・`rate_limited`・`rejected`・`uncertain`）だけを付ける。画面にも、応答の本文とエラーの文を出さない。

## 6. 確かめた公式の資料（2026-11-17）

| 項目 | 確かめたこと | 出典 |
|---|---|---|
| 送り先と見出し | `POST https://api.line.me/v2/bot/message/broadcast`。`Content-Type: application/json`、`Authorization: Bearer {トークン}`。`X-Line-Retry-Key` は任意 | Messaging API リファレンス（Send broadcast message） |
| 中身 | `messages` は5つまで。`notificationDisabled` の既定は `false`（通知する）。送り先の指定は無く、友だち全員に届く | 同上 |
| 回数の上限 | 1つのチャネルで1時間に60回。超えると 429 | 同上 |
| エラーのとき | 「エラーが返された場合、メッセージは送信されません」。429 の原因に、当月の上限目安の超過がある | 同上（日本語版） |
| 再送の鍵 | 16進の UUID を送る側が作る。最初の要求から24時間有効。受け付け済みなら 409 と `x-line-accepted-request-id`。中身と宛先を変えずに送り直す | Retrying an API request |
| 通数 | 送った相手の人数で数える。1回の要求の吹き出しの数は数に影響しない。一斉送信は数える対象。ブロックした人など受け取れない人は数えない。上限を超えて送ろうとすると、エラーが返り送信されない | Messaging API pricing |
| 文字数 | テキストは5,000文字まで。UTF-16 の単位で数え、サロゲートペアや一部の絵文字は2文字以上になる | リファレンス（Text message） |
| トークン | 4種類。ボットの作り方のページは v2.1 を勧める。法人向けの開発ガイドラインは、長期をセキュリティの面から勧めず、短期・v2.1・ステートレスのどれかを勧める | Building a bot、開発ガイドライン（法人ユーザー向け）、Channel access token |
| ステートレスの発行（2026-11-18） | `POST https://api.line.me/oauth2/v3/token`、`application/x-www-form-urlencoded`。チャネル ID とシークレットの方式は `grant_type=client_credentials`・`client_id`・`client_secret`。応答は `token_type`・`access_token`・`expires_in`。15分有効、発行の数に上限なし、取り消せない。400 は ID かシークレットの誤り | リファレンス（Issue stateless channel access token） |

確かめられなかったこと:
- 一斉送信の節は「送信されません」と書くが、「どのユーザーにも」とは書いていない（その書き方は multicast と narrowcast の節だけ）。一部に届くことは無いと読むが、断定しない。応答を受け取れなかったときや 5xx は、この説明では「送っていない」とは言えないため、受け付けたかもしれない扱いにする（3節）。
- 23時間の余白は、24時間の期限の数え方（LINE の側の時刻）とのずれを見込んだもの。

## 7. 不変条件（案）

番号は `NEWS-INV-19` から。守る場所は、実装の後に識別子で埋める。

| 番号 | 条件 |
|---|---|
| NEWS-INV-19 | LINE へ送るのは、送る前のトランザクションで公開側に出ていた記事だけ。送る文面は、サイト名・題名・記事の URL だけで作る |
| NEWS-INV-20 | 鍵と文面をコミットしてからでないと送らない。1つの記事について、送信済みか、届いたか分からない状態になった後は送らない |
| NEWS-INV-21 | 受け付けられたかもしれない要求が一度でもあった記録は、鍵と文面を変えず、今の鍵の最初の要求から23時間の間だけ送り直す。受け付けなかったと分かっている要求だけの記録に限り、23時間の後に鍵を入れ替える |
| NEWS-INV-22 | 送信済みの記録は、後の応答で戻さない |
| NEWS-INV-23 | 送れるのはサイト管理者以上。AIエージェント（MCP）のツールからは送れない |
| NEWS-INV-24 | 送り先は `https://api.line.me/oauth2/v3/token` と `https://api.line.me/v2/bot/message/broadcast` だけで、転送に従わない。チャネルシークレットは所有者だけが読めるファイルから読む。シークレット・トークン・応答の本文・エラーの文をログと画面に出さず、トークンを保存しない |
| NEWS-INV-25 | 設定しなければ、ボタンを出さず、外へ通信しない |

## 8. 試験

- 公開の条件（INV-19）: 下書き、予約公開、公開日時ちょうど（今と同じ時刻は出る）、1秒前で、リンクと送信。
- 文面（INV-19）: 本文をカナリアにして、文面に出ない。確認の後に題名を直したら、送らずに確認を出し直す。記録の後に題名を直しても、文面が変わらない。
- 送る前の書き込み（INV-20）: コミットに失敗したら、HTTP の要求が出ない。送信済み・届いたか分からないで、要求が出ない。
- 応答の分類（INV-20〜22）: 200・409（見出しあり・なし）・400・401・403・429・500・302・418・時間切れ・接続の失敗・応答の読み取りの失敗ごとの、記録と画面。
- 23時間（INV-21）: 境界の前後1秒。受け付けたかもしれない要求の後の 401・429 では、鍵を入れ替えない。受け付けなかった要求だけなら、23時間の後に鍵を入れ替え、文面は変えない。
- 同時の操作（INV-20・22）: 順序を差し替えられる偽の送り先で、2つの要求が同じ鍵を使う。行の作成が競合した側が保存済みの行を読む。遅れて返った失敗が送信済みを戻さない。200 の後の書き込みの失敗で、結果待ちになり、次の押下が同じ鍵で送る。
- 権限（INV-23）: 未ログインと一般ユーザーは断られる。CSRF の検査に外れる送信は断られる。MCP のツールの一覧に送信が無い。
- 秘密と漏洩（INV-24）: 別の URL・転送（302）を断る。権限の緩いファイル、空、中の空白・制御文字、末尾の改行の扱い。シークレット・発行したトークン・`Authorization`・偽の応答の本文・通信のエラーの文をカナリアにして、ログと HTTP の応答の両方に出ない（`test/` のログ非漏洩カナリア）。トークンの発行の失敗（400・500・時間切れ・`token_type` が違う・`access_token` が空）で、一斉送信の要求が出ず、記録が変わらない。`LINE_CHANNEL_ID` だけ・シークレットだけの設定で起動を止める。
- 未設定（INV-25）: リンクが出ず、HTTP の通信が起きない。有効なのに `SITE_URL` か `SITE_NAME` が無ければ起動を止める。
- 画面: 新しい経路を `test/admin_ui_test.go` の見本の表（確認の画面、送信）に足す。取り消せない操作の確認の型の検査。
- LINE の API は `httptest` の偽の送り先で差し替える。実際の LINE には試験から送らない。
- 守りを外して、対応する試験が落ちることを確かめる。

## 12. 計画のレビューで直したこと（2026-11-17、Codex gpt-6.1-sol）

| 指摘 | 重さ | 直したこと |
|---|---|---|
| 受け付けなかった要求でも、23時間を過ぎると永久に送れない | 進めない | 受け付けたかもしれない要求の有無（`uncertain`・`in_flight`）を記録し、無ければ23時間の後に鍵を入れ替えて送れるようにした（3節、INV-21） |
| 送る前のコミットと、送った後の書き込みの失敗が未定義 | 進めない | コミットに失敗したら送らない。送った後の書き込みの失敗は結果待ちとして扱い、案内を決めた（3節、INV-20） |
| 正本の更新が実装の後になっている | 進めない | 正本を実装の前に直す順にした（10節） |
| 同時の操作の扱いと試験 | 直したほうがよい | 行の作成の競合、保存していない鍵では送らない、送信済みを戻さないを決め、試験を足した（3節、INV-22、8節） |
| 23時間の判定の時点と、表に無い応答 | 直したほうがよい | 判定は送る前のトランザクションの中、境界は `<`。表に無い応答は受け付けたかもしれない扱い（3節） |
| 非漏洩の試験が不変条件を覆っていない | 直したほうがよい | 応答の本文とエラーの文、画面も試験に入れた。秘密のファイルの空白の扱いを決めた（5節、8節） |
| 公開の判定と、非公開・削除の競合 | 直したほうがよい | 送る操作を受け付けた時点で公開中ならよい、とし、守らない範囲に書くことにした（3節） |
| トークンの推奨の記述が違う | 直したほうがよい | 公式の推奨を書き直し、案を並べて利用者の判断に回した（5節、6節） |
| 通数が足りないときの挙動は確かめられる | 直したほうがよい | 確かめた範囲を書き、5xx 等は送っていないと断定しないことにした（6節） |
| 確認の画面の文面と編集の競合 | 直したほうがよい | 記録があれば保存した文面を出す。記録が無ければ文面の SHA-256 で照らす（2節） |
| 確認の画面の型と試験 | 直したほうがよい | 取り消せない操作の確認の型を足す。見本の表と、権限・CSRF・時刻の境界・書き込みの失敗を試験に足した（2節、8節） |
