状態: 実装中（2026-11-03）。7節の手順1〜5と、手順6のうちキットの文書（`docs/deploy.md` の「WordPressからの移行」、README）を終えた。残りは宣伝サイトの営業資料の見直しと、完成のレビュー。利用者が2節の決定と、承認境界1・2を承認した。FableとSolの計画のレビューを受け、10節に反映した（10節は3〜5節に優先する）。11節の4項目を利用者が決めた（2026-11-03）。7節の手順1の結果を12節に書いた（12.2は10節に足す）。手順2の規則のレビューを13節に反映した（13節は3〜12節に優先する）。対象の時点は `main` の `ba32510`。関連する正本: [お知らせ](../domain/news.md)、[固定ページ](../domain/pages.md)、[画像](../domain/media.md)、[本文の書き方](../richtext.md)。

## 1. 目的と範囲

宣伝サイトの営業資料は「WordPressから自動で移す道具はありません」と書いていて、乗り換えの提案で引っかかりやすい。WordPressの書き出し（WXR）と画像のフォルダから、キットへ内容を移す道具を作る。

この計画は3つの変更を含む。

1. お知らせの本文で、リンクの記法 `[文字](URL)` を読む。
2. お知らせに専用のカテゴリを足す（1記事に1つ）。
3. 移行の道具（別の実行ファイル `cmd/wpimport`）。

作らないもの: テーマ・見た目・ページビルダーのレイアウトの再現、プラグインの機能、コメント・ユーザー・お問い合わせのプラグインの受信データの移行（個人情報のため、あえて移さない）、元のサイトからの画像のダウンロード（外部通信になる）、キットの中の転送の機能、WordPressの他の書き出しの形式（データベースの直接の読み取り等）。

## 2. 決まったこと（2026-11-03）

| 事項 | 決定 |
|---|---|
| お知らせのリンク | 本文で `[文字](URL)` の記法だけを読む（案B）。見出し・リスト・表は読まない |
| お知らせの分類 | お知らせ専用のカテゴリ。カタログとはデータを共有しない。1記事に1つ。管理画面と絞り込みの部品は共通にしてよい |
| 移行の道具 | 別の実行ファイルにし、その実行ファイルだけ `golang.org/x/net/html` を使う。本番のサーバーの依存は増やさない |
| 古いURL | 対応表をCloudflareの一括転送（Bulk Redirects）のCSVで書き出す。キットに転送の機能は足さない |
| 画像 | 全部移す。手元に取ってきたアップロードのフォルダを読み、通信はしない |
| 移した記事 | 全部下書きにする。人が確かめてから公開する |

## 3. お知らせのリンク

- 本文を段落と行に分ける今の読み方（`form.Paragraphs`）は変えず、各行の中だけを `richtext` の文字の並びの規則で読む。読むのはリンクだけで、強調（`**`）は文字のまま。`docs/richtext.md` の4節・5節の規則（`https://` とサイト内のパスだけ、`\` で逃がせる）をそのまま使う。
- `richtext` に、行の中のリンクだけを読む入口を足す（例: `richtext.LinksOnly(line)`）。読む時間は行の長さに比例すること、許可しないURLは文字のまま出すことを、今の規則のテストと同じ形で確かめる。
- 既存の記事: 本文に `[文字](URL)` の形がある記事は、配備の直後からリンクとして表示される。移行の前に、既存の記事にこの形があるかを数えるコマンドの出力か、テストの手順で確かめる。`\[` で文字として書ける。
- 本文の `\` の扱い: リンクの記法の外の `\` は今までどおり文字として出すか、記法と同じく逃がしとして読むかを、記法の規則のレビューで決める（9節）。既存の記事の見え方が変わらない方を優先する。
- APIの `/api/news` の本文は、記法の文字のまま返す（NEWS-INV-7 の項目は変えない）。README とAPIの説明に、記法を書く。
- 管理画面の本文の説明に、リンクの書き方を足す。

## 4. お知らせのカテゴリ

| 表・列 | 内容 |
|---|---|
| `news_categories` | id、名前（1〜50字、正規化して重複させない）、作成日時 |
| `news_posts.category_id` | NULLを許す。`news_categories(id)` への外部キー、`ON DELETE SET NULL` |

- 列の追加は `pragma_table_info` で有無を見て `ALTER TABLE ... ADD COLUMN` で行う（画像の代表画像の列と同じ形）。表は作り直さない。
- 管理画面: カテゴリの一覧＋追加、編集、削除の確認（カタログの分類の画面の型と同じ）。記事の作成・編集で選ぶ（`field` の選択）。カテゴリを消しても記事は消えない。
- 公開: `/news?category=ID` で絞り込む。公開中の記事を持つカテゴリだけを候補に出す。ページ送りは条件を残す。公開キャッシュの扱いは今の `/news` と同じ。
- API: `/api/news` の項目にカテゴリを足すかは、NEWS-INV-7 を変えるため、今回は足さない。
- MCP: お知らせのツールはカテゴリを変えない。対象の状態のハッシュと、`*IfUnchanged` の条件にカテゴリを含める（画像の代表画像と同じ扱い）。
- 共通にする部品: 分類の名前の検査と、管理画面の分類のテンプレートは、カタログと共通にできるかを実装のときに確かめる。データは共有しない。

## 5. 移行の道具（`cmd/wpimport`）

### 5.1 使い方

```sh
# 試しに読むだけ（DBを変えない）
wpimport -wxr export.xml -uploads ./wp-content/uploads -old-origin https://old.example.com -new-origin https://example.com -report report.md -dry-run
# 取り込む（サーバーを止めて、DBの複製に対して実行する）
wpimport -wxr export.xml -uploads ./wp-content/uploads -old-origin https://old.example.com -new-origin https://example.com -db app.db -report report.md -redirects redirects.csv
```

- サーバーを止めて実行する（同じDBへの同時の書き込みを避ける）。取り込みの前に `store.Backup` で複製を作る。
- 取り込みは、記事ごとに保存の検査（各機能の保存の関数）を通す。DBへ直接書かない。画像は画像機能の加工（縮小・再エンコード・EXIFを落とす）を通す。
- 同じ入力で2回実行しても、二重に取り込まない（WordPressの記事のIDと画像のファイルを記録して飛ばす。記録の置き場所は9節で決める）。
- 外部へ通信しない。

### 5.2 対応

| WordPress | キット | 扱い |
|---|---|---|
| 固定ページ（`page`、公開・下書き） | 固定ページの下書き | 本文を `docs/richtext.md` の記法に変換する。スラッグは `post_name` を使い、キットの形と予約語に合わなければ作り直して報告する。親子のページは1階層にして報告する |
| 投稿（`post`） | お知らせの下書き | 本文を段落とリンクの記法に変換する。公開日時は `post_date_gmt` を使う。最初のカテゴリをお知らせのカテゴリにし、残りとタグは報告する |
| 添付（`attachment`）とアップロードのフォルダ | 画像 | 元の画像だけを取り込む（WordPressが作る `-300x200` 等の版は飛ばす）。説明は代替テキスト（`_wp_attachment_image_alt`）、無ければ題名。どちらも無ければ報告する |
| アイキャッチ（`_thumbnail_id`） | お知らせの代表画像 | |
| 固定ページの本文の画像 | 画像の行 | 本文の中の `<img>` を、取り込んだ画像の行にする。見つからなければ説明の文字にして報告する |
| お知らせの本文の画像 | 報告 | 記法が無いため。アイキャッチが無ければ、最初の画像を代表画像にする |
| 予約投稿（`future`） | 下書き＋公開日時 | 公開は人が行う |
| 非公開・ゴミ箱・リビジョン・自動保存 | 取り込まない | 報告に件数だけを出す |
| コメント、ユーザー、作者の名前とメールアドレス | 取り込まない | 報告にも個人情報を書かない |
| カスタム投稿タイプ、独自フィールド、メニュー、ウィジェット | 取り込まない | 報告に種類と件数を出す |

### 5.3 本文の変換

`golang.org/x/net/html` で読み、決めた要素だけを記法に変える。それ以外は中の文字だけを残す。

| HTML | 固定ページ | お知らせ |
|---|---|---|
| `h1`・`h2` | `## ` | 段落 |
| `h3`〜`h6` | `### ` | 段落 |
| `p`、`br` | 段落、行 | 段落、行 |
| `ul`・`ol`（入れ子は1段にする） | `- `・`1. ` | 行頭の `・` |
| `table`（結合のある表は報告） | 表 | 文字 |
| `a`（`https://`・サイト内） | `[文字](URL)` | `[文字](URL)` |
| `a`（`http://`・`mailto:` 等） | 「文字（URL）」 | 「文字（URL）」 |
| `strong`・`b` | `**文字**` | 文字 |
| `img` | 画像の行 | 報告 |
| `script`・`style`・`iframe`・`form`・`embed` | 捨てて報告 | 同じ |
| ショートコード（`[gallery]` 等）、ブロックのコメント | 捨てて報告 | 同じ |

- 本文の文字の中の記法の記号（`*`・`[`・`]`・`|`・行頭の `#`・`-`・数字と `.` 等）は `\` で逃がし、意図しない記法にしない。変換した本文を `richtext.ParseWithImages` で読み、文字が落ちていないことを確かめる（ファズ）。
- 古いサイトの中へのリンク（`-old-origin` の下）は、対応表で新しいURLへ書き換える。見つからないものは古いURLのまま残して報告する。
- 本文の長さ・表の上限を超えるものは、取り込まずに報告する。

### 5.4 転送のCSV

- 1行に `古いURL,新しいURL,301`。見出しの行は入れない（Cloudflareの形式）。
- 古いURLは、パーマリンク（`link`）と `?p=ID` の形の両方を出す。クエリは一括転送のソースに書けないため、`?p=` の形は報告に回す。末尾の `/` の有り無しは両方の行を出す。
- 無料プランの上限は合計10,000件。超えるときは報告で知らせる。
- 2026-11-03 に Cloudflare の公式の資料で形式と上限を確かめた。資料の間で `preserve_path_suffix` の既定値の書き方が食い違っているため、列は省かずに書く。

### 5.5 報告

Markdown で、取り込んだ件数、飛ばした物と理由、変換で落ちた要素、画像の合計の容量と上限、説明の無い画像、転送の件数を書く。記事の本文、作者、メールアドレスは書かない（題名とIDまで）。

## 10. レビューの反映（2026-11-03）

FableとSolの指摘のうち、コードで確かめられるものは確かめた（`process`・`Store.Add`・`normalize` が非公開、`NewSQLiteStore` が開くだけでWALとCoreの移行を行う、`TestArchitecture_LinkedModules` が `cmd/server`・`cmd/kit` だけを見る、お知らせの説明文が本文の生の文字から作られる、`publishedAtArg` が0以下を断る、`migration.sql` だけが台帳の検査に流れる）。WordPressとCloudflareの仕様は、レビューが示した公式の資料に拠る。

### 10.1 取り込みの進め方（二重取り込み）

途中の再開と差分の追加は作らない。1回の実行で全部を移し、失敗したら全部を捨てる。

1. 利用者がサーバーを止める。
2. 道具は、稼働DBを書き込まずに開き（`mode=ro`）、`VACUUM INTO` で作業DB（例: `app.import.db`）を作る。稼働DBには何も書かない。
3. 作業DBを `store.NewSQLiteStore` で開き、news・pages・mediaの `Init` を呼ぶ。有効でない機能の表が無ければ、`make add-...` を案内して止める。
4. 2段階で処理する。1段目で全件の可否・スラッグ・移行先のIDを決めて検査する。2段目で取り込みと本文の内部リンクの書き換えを行う。
5. `PRAGMA integrity_check` と件数を確かめる。どこかで失敗したら作業DBを消す。
6. 利用者が作業DBを稼働DBの位置へ置き換え、サーバーを起動する。稼働DBは移行前の複製としてそのまま残る（`-wal`・`-shm` の扱いは `docs/deploy.md` の戻し方の手順に合わせる）。

- 試しの実行（`-dry-run`）は、同じ手順を一時の作業DBで行い、報告を出して作業DBを消す。画像も実際に加工するため、容量の上限に当たるかが分かる。
- 既に移行の記録（対応表）がある、または取り込み先に移行の印がある作業は止める。印は報告と対応表に書き、DBには保存データを増やさない。誤って2回取り込んだ場合は、移行前の複製へ戻す。
- 対応表のファイルに書くのは、WordPressの記事・添付のIDと、キットの移行先のIDとURLだけ。

### 10.2 道具からの書き込みの入口

各機能に、HTTPの外から使える入口を1つずつ足す。同じ検査と保存の関数を通し、SQLを道具に書かない。

| 機能 | 入口（例） | 通す物 |
|---|---|---|
| 画像 | `media.Feature.Import(ctx, data, alt) (file string, err error)` | 説明の検査、形式・画素数・容量の上限、加工（縮小・再エンコード・EXIFを落とす）、`Store.Add` |
| 固定ページ | `pages.Feature.Import(ctx, Input) (id int64, err error)` | `normalize`（経路の衝突は予約語と、組み立てた経路で確かめる）、参照の更新 |
| お知らせ | `news.PostStore.CreateWithCover` に カテゴリを足す | 既存の検査、参照の更新 |

画像の参照は、道具も `BuildRoutes` と同じ配線（`MediaProvider`・`MediaOwner`）で受け取り、`NoMedia` にならないようにする。終わりに `RunStartup` で参照を作り直す。

### 10.3 お知らせのリンクの記法

- お知らせの本文で `\` が逃がすのは `\`・`[`・`]`・`(`・`)` だけにする。既存の本文の `\*`・`\-` 等の見え方は変わらない。強調は読まない。
- 既存の記事への影響は、リンクの形の件数だけでなく、全本文を新旧の読み方で描いて差分を数えて確かめる。
- 検索結果・SNSの説明文は、リンクを読んだ後の文字から作る。
- NEWS-INV-5、台帳の `body` の説明、READMEのAPIの説明、MCPの本文の説明を直す。APIの本文は記法の文字のまま返す。
- 管理画面のお知らせの本文の説明に、リンクの書き方と逃がし方を書く。

### 10.4 お知らせのカテゴリ

- `news_categories` の表と `news_posts.category_id` の列は、`migration.sql` の `CREATE TABLE` にも書く（台帳の検査は `migration.sql` を流すため）。既存のDBには `pragma_table_info` と `ALTER TABLE ... ADD COLUMN ... REFERENCES news_categories(id) ON DELETE SET NULL` で足す。
- 名前の規則はカタログと同じ（`form.Line` で1〜50字、完全一致で重複させない）。カテゴリの削除・改名で記事の `updated_at` は変えない。
- 公開の候補と絞り込みは、記事の公開ページと同じ条件（状態と公開日時）で数える。予約の記事のカテゴリを先に見せない。
- ページ送りは条件を残す（カタログの `filterURL` と同じ方式）。`CanonicalPath` は `/news` のままにする。
- MCPはカテゴリを変えない。対象の状態のハッシュと `*IfUnchanged` の条件に含める。
- 管理画面の見本を `test/admin_ui_test.go` に足す。

### 10.5 WXRの読み方

- `encoding/xml` のトークンの走査で、許可した要素とpostmetaのキーだけを読む。作者・コメント・任意のpostmetaは読み飛ばし、値を持たない。
- 状態の許可表:

| 投稿タイプ | 状態 | 扱い |
|---|---|---|
| `post`・`page` | `publish` | 下書きで取り込む。転送の対象 |
| `post`・`page` | `future` | 下書き＋予約の日時（お知らせは公開日時、固定ページは公開予約）。転送の対象 |
| `post`・`page` | `draft`・`pending` | 下書き。公開日時なし。転送の対象外 |
| `post`・`page` | `private`・`trash`、未知の状態 | 取り込まない。件数だけ報告 |
| `post`・`page` | パスワード保護（`post_password` が空でない） | 下書きで取り込み、保護を再現しないことを報告する。転送の対象外 |
| `attachment` | `inherit` | 画像の候補 |
| それ以外の投稿タイプ | すべて | 取り込まない。種類と件数だけ報告（題名は出さない） |

- 公開日時は `publish`・`future` だけ `post_date_gmt` をUTCで読む。`0000-00-00 00:00:00`・欠落・不正はゼロ値にして報告する。
- カテゴリは `<category domain="category">` だけを見る。`nicename="uncategorized"` を外し、`_yoast_wpseo_primary_category` があればそれを、無ければ残りの最初を使う。残りとタグは報告する。名前が50字を超えるものは取り込まず報告し、同じ名前は1つにまとめる。

### 10.6 画像

- 候補はフォルダの走査ではなく、WXRの `attachment` から決める。読むのは `_wp_attached_file` のファイル（大きな画像は `-scaled` の版で、キットの縮小には十分）。`_wp_attachment_metadata` の `sizes`・`original_image` と `attachment_url` から、各版の旧URLを同じ移行先の画像へ結ぶ対応表を作る。メタデータが無い版を名前から推して結ぶことはしない。
- `_wp_attached_file` が絶対パス・`..`・シンボリックリンクで指定のフォルダの外を指すものは読まない。
- JPEG・PNG以外（WebP・GIF・SVG・PDF等）、上限を超える画像、容量の上限を超える分は、取り込めなかった画像として種類と件数を報告する。報告は「N枚中M枚を移した」と書き、全部移したと誤認させない。フォルダにあってWXRに無いファイルは件数だけ報告する。
- 説明は、`_wp_attachment_image_alt` → 本文の `<img alt>` → `[caption]`・`<figcaption>` の文字 → 仮の文「画像の説明を書いてください」の順。題名はファイル名と同じことが多いため使わない（元のファイル名を保存しないため）。仮の文の画像は報告に一覧する。
- 本文の `<img>` は `class="wp-image-<ID>"` を最優先に、無ければ対応表のURLで結ぶ。`<a><img></a>` は `a` を外す。
- お知らせの本文の画像: アイキャッチが無ければ最初の画像を代表画像にする。それ以外の本文の画像は、取り込んでも記事から参照されず公開されないため、取り込まずに報告する。その旧URLは転送の対象にしない。
- 外した本文の画像の報告: 記事ごとに、WordPressのID・移行先のID・題名・外した枚数を書き、画像ごとに旧URLと説明（上と同じ順で探す。無ければ「説明なし」）を書く。活動報告の現場写真のように、画像にしか無い情報を持つ物を人が見つけ、本文に書き足すか、手で代表画像に差し替えるために使う。

### 10.7 本文の変換

- クラシックエディタの本文は `<p>` を持たない。ブロックの外の文字には、空行で段落、改行で行にする最小の `wpautop` 相当を掛ける。
- ブロックのコメント（`<!-- wp:... -->`）は外して中のHTMLを残す。未知のブロック名だけを数えて報告する。
- ショートコード: `[caption]` は中の画像と文字を使い、`[gallery ids="..."]` はIDから画像の行にする。それ以外の既知の形は囲みだけを外して中身を残し、中身の無いものを捨てて報告する。角括弧の普通の文字はショートコードとして扱わない（既知の名前だけ）。
- `pre`・`code`・`blockquote`・`div` は段落の区切りにして中の文字を残す。
- 強調とリンクが重なるときはリンクを優先する。リンクの文字の中の改行は空白にする。表のセルの中の改行・画像は文字にして報告する。
- URLの中の `(`・`)` はパーセント符号化する。表現できないURLは「文字（URL）」にして報告する。
- 逃がし: 固定ページは `richtext` の11文字（`\` 自身を含む）、行頭の `![` は `!\[`、行頭の `表: ` は逃がす。お知らせは10.3の5文字だけ。出力先ごとに、その出力先の読み方で読み直して検査する。
- ファズの性質は「捨てると決めた要素を除いた文字が一致する」と「意図したリンク先・画像・ブロックの構造になる」の2つ。

### 10.8 内部リンクと転送

- 1段目で全件の移行先を決めてから、2段目で書き換える（前方参照・循環参照に対応する）。
- 親子のページの平坦化で起きるスラッグの衝突、既存のページ・予約語・登録済みの経路との衝突は、1段目で決めて報告する。
- 旧オリジンは複数指定できる（`http`・`https`・`www` の揺れ）。オリジンの一致はパスの境界まで見る。相対URL・フラグメントにも対応し、`?p=ID` の形は本文の書き換えにだけ使う。
- CSVは `encoding/csv` で、7列を全部書く（`旧URL,新URL,301,FALSE,FALSE,FALSE,FALSE`）。旧URLはスキームを除いた「ホスト＋パス」（http と https の両方に当たる）。`www` の有り無しで配信していた場合は両方の行を出す。末尾の `/` は解析したパスで両方の形を出し、重複させない。クエリ・フラグメントは入れない。同じURLへの自己転送と転送の循環は出さない。
- 転送の対象は、10.5の表で「転送の対象」とした記事だけ。CSVは、移行先を公開して確かめた後に適用する候補として出す（全件下書きのまま有効にすると、旧URLが404へ転送される）。手順書に、一覧への登録と Bulk Redirect Rule の有効化、1件で試す手順、日本語のスラッグのパーセント符号化の確認を書く。

### 10.9 個人情報

### 13.1 リンクの規則

- **説明文:** お知らせの説明文（`excerpt`）と固定ページの説明文（最初の段落）の作り方を、`richtext` の文字だけを取り出す関数（今は非公開の `plain`）に寄せる。カタログの詳細には説明文が無く、公開一覧の断片は本文を出さないため、11節の3の「カタログの説明文」「公開一覧の断片」は直す対象が無い。代わりにカタログの管理画面の本文の説明を直す。

### 13.2 変換の表

- **画像は常にそれだけの行にする（高）。** `richtext` の画像の行は行全体が条件のため、項目の中や文字の途中の画像は「!」とリンクになる。`li` の中の画像は項目を閉じて画像の行にし、文字の途中の画像は前後で行を分ける。古いギャラリーのブロック（`ul.blocks-gallery-grid`）が見本に26枚ある。
- **表:** 列数は全行の最大にして、足りないセルは空で埋める。列の上限を超える表は文字にして報告する。`<caption>` は `表: ` にする。
- **空の文字:** 文字が空のリンクはURLを文字にして報告する。文字が空の見出しは見出しにしない。
- **URL:** 先に10.8の旧オリジンの書き換えを行い、次に `url.Parse`、スキームとホストを小文字にし、`(`・`)`・`|` を符号化し、最後に許可の判定をする。失敗したものは「文字（URL）」。
- **項目の中の改行:** 項目は1行のため、`li` の中の `<br>` と入れ子の改行は空白にする。
- **お知らせの番号付きの項目:** お知らせは行頭の記法を読まないため、`ol` は `1. ` の文字で残す。表を文字にする時はセルを ` / ` で繋ぐ。
- **その他:** `<!--more-->`・`<!--nextpage-->` は消えたことを件数で報告する。改行と字下げ以外の制御文字は落として報告する。`pre` の字下げは残らない。

### 13.3 公式の見本から足した5点（12.2）の補い

- **`attachment_url` からファイルを探す:** アップロードのURLの接頭辞をフラグで与える（既定は旧オリジンの下の `/wp-content/uploads/`）。クエリ（`?w=` 等）は外す。手元のフォルダにファイルがあることで確かめ、無いものは報告する。
- **`[gallery]` の順と属性:** WordPressの既定どおり、記事に付いた添付を `menu_order`、次にIDの昇順で並べる。`ids`・`include` は書かれた順、`exclude` は除く、`id="N"` は別の記事の添付、`order="DESC"` は逆順。画像かどうかは `attachment_url` の拡張子で決める（WXRに `post_mime_type` は無い）。
- **同期パターン（`wp:block {"ref":N}`）:** 中身は `wp_block` の投稿にある。参照先が書き出しにあれば本文に差し込み、無ければ記事ごとに報告する。

- そのほか: 強調の隣の `*` の逃がし、属性に `>` のあるブロックの数え、`-scaled` の添付と小さい版の結び付け、未分類だけの記事のタグの数え、保護・下書きの記事への本文のリンクの書き換え、`-dry-run` と出力の指定の組み合わせの拒否、IDの無い添付の除外、アップロードのフォルダにあって書き出しに無い画像の件数、お問い合わせの画面が richtext の部品を使わない検査、移行のユースケース（UC-OPS-3）。
- 10.2の「SQLを道具に書かない」は、保存のSQLのこと。道具は、表の有無と `PRAGMA integrity_check` を読むだけの固定の文を持つ。

### 13.8 手順5の実装で決めたこと（2026-11-03）

- 道具は、サイトの機能の登録（`cmd/server/features.go`）を使わず、お知らせ・固定ページ・画像の3つを自分で組み立てる。作業DBに表が無い機能は初期化せず（サーバーが知らない表を足さない）、その記事は取り込まずに報告する。

### 13.7 手順4の実装で決めたこと（2026-11-03）
