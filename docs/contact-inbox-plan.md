# お問い合わせの受信箱の強化 実装計画

状態: 2026-10-30、方針の案として記録した。実装は未着手。利用者が決めたのは、CRMの前にお問い合わせを強化する案と、対応中の延長（案B、4節）まで。10節の項目と、承認境界2（DB列の追加）の承認を得てから実装する。

## 1. 目的と範囲

受信箱を、内容を読むだけの場所から、対応の進み具合を管理できる場所にする。CRMを作る前に、顧客の台帳を持たずに、必要な対応を満たせるかを確かめる。

- 状態を、未読・対応中・完了・スパムの4つにする。
- 運営者のメモを1件に1つ書けるようにする。
- 一覧を、残っている仕事だけに絞れるようにする。
- 対応中のものは、更新を続ける間、削除を延ばす。上限を設ける。

作らないもの: メールの送信、返信の機能、担当者の割り当て、やり取りの履歴の積み上げ、顧客ごとのまとめ、受付から上限を超える保存、公開フォームの項目の追加。これらが必要になったら、CRMを別に設計する。

変えないもの: 公開フォームの項目と画面、受信箱を見られるのが管理者だけであること（CONTACT-INV-3）、スパム対策、受付上限。

## 2. 状態

| 状態 | 値 | 今との対応 |
|---|---|---|
| 未読 | `unread` | 同じ |
| 対応中 | `active` | 今の既読（`read`）を置き換える |
| 完了 | `done` | 新規 |
| スパム | `spam` | 同じ |

状態の変更は、今までどおり詳細の画面のボタン（POST）で行い、開いただけでは変えない（CONTACT-INV-7）。どの状態からも、ほかの状態へ変えられる。

## 3. メモ

- 列 `note`（TEXT、既定は空文字）。2,000文字以内で、`form.Text` で検査する。
- 詳細の画面に入力欄を置き、`POST /admin/contact/{id}/note` で保存する。`AdminForm` で守る。
- 入力欄の説明に、病歴など配慮が必要な情報を書かないよう注意書きを付ける。
- ログに中身を出さない。`slog.LogValuer` を実装し、カナリアの検証に足す（CONTACT-INV-6）。

## 4. 保持と削除

| 状態 | 削除の時期 |
|---|---|
| 未読 | 受付から保持期間（既定90日） |
| 対応中 | 最後の更新から保持期間。ただし受付から上限（既定365日） |
| 完了 | 受付から保持期間 |
| スパム | 受付から保持期間 |

- 列 `last_activity_at`（INTEGER）を足す。受付のときは `created_at` と同じ値にする。
- 更新として数えるのは、メモの保存と、対応中への状態の変更と、対応中のものの状態の再設定だけ。開いて読んだだけでは更新しない。未読・完了・スパムのものでメモを保存しても、削除の時期は変わらない。
- 上限の設定は `CONTACT_ACTIVE_MAX_DAYS`（既定365）。`CONTACT_RETENTION_DAYS` 以上、365以下で、範囲外は起動時にエラーにする。
- `Purge` は次の条件で消す。判定は1つのSQL文で行う。

```sql
DELETE FROM contact_messages
WHERE (status <> 'active' AND created_at <= :retention_limit)
   OR (status = 'active' AND (last_activity_at <= :retention_limit OR created_at <= :max_limit))
```

- 対応中のものを、受付から保持期間を過ぎた後で完了にすると、次の削除の処理（起動時と1時間ごと）で消える。完了のボタンの近くに「完了にすると、1時間以内に削除されます」と表示する。

**キットの約束への影響**: 今の説明は「受付から90日で、状態に関係なく削除」である。対応中のものは最長1年残ることになるため、9節の文面をすべて直す。

## 5. 画面

| 画面 | 型 | 変更 |
|---|---|---|
| `/admin/contact` | 一覧 | 既定は未読と対応中だけ。列に「削除まで」を足す |
| `/admin/contact/all` | 一覧 | 全件。同じテンプレートで描く |
| `/admin/contact/{id}` | 詳細 | メモの欄、状態のボタン、削除の時期を足す |

- 絞り込みを `?view=all` にしないのは、部品 `pagination` が `Base` に `?page=` を付ける作りで、クエリを重ねられないため。
- 「削除まで」は、7日以内なら「あと3日」のように出す。
- 動きのあるUIは足さない。`docs/ui-guidelines.md` の1段目で作る。JavaScript・CSSファイルは増やさない。

## 6. DBの移行

`status` の CHECK 制約に値を足すには、SQLiteでは表を作り直す必要がある。`ALTER TABLE ... ADD COLUMN` だけでは足りない。

- `migration.sql` は新しい形にする（新規のDB向け）。
- 既存のDBは、`Init` で旧形式を判定し、1つのトランザクションで次を行う。新しい表を作る、`read` を `active` にして `note` は空、`last_activity_at` は `created_at` で写す、古い表を消す、名前を変える、索引を作り直す。
- `id` の採番が巻き戻らないよう、`sqlite_sequence` の値も引き継ぐ。テストで確かめる。
- 移行で削除の時期を延ばさない。`last_activity_at` に移行の時刻を入れない。
- 2回起動しても壊れないこと、途中で失敗したら元のままであることをテストで確かめる。
- 古い実行ファイルは新しい表の `active`・`done` を扱えない。戻すときは、更新の前のバックアップから戻す。`docs/deploy.md` の手順に書く。

## 7. 承認境界と保存データ

- 承認境界2に当たる: 列 `note`・`last_activity_at` の追加。
- 利用目的: `note` は対応の引き継ぎ、`last_activity_at` は保持期間の計算。
- 保持と削除: 4節のとおり。お問い合わせと一緒に消える。バックアップの複製には、その複製の保持期間のあいだ残る。
- ほかの境界（依存、外部通信、CSS・JSファイル、公開範囲）には当たらない。

## 8. 検証

- 不変条件: CONTACT-INV-2 を4節の内容に改め、新しい番号を足す（対応中の延長と上限、読むだけでは延びないこと、移行で延びないこと）。
- 単体: 状態ごとの削除の境界値（保持期間のちょうど・1秒前、上限のちょうど）、対応中から完了にしたときの削除、メモの上限、設定の範囲。
- HTTP: メンバーと未ログインの拒否、CSRF、GETで状態もメモも変わらないこと、全件の画面のページ送り。
- 台帳: `docs/data-inventory.md` の7節と実スキーマの照合。
- 管理画面: `test/admin_ui_test.go` の見本に、全件の画面と、メモの入力の失敗を足す。
- 撮影: 受信箱と詳細を1100pxと360pxで見る。表の列が増えるため、横スクロールの目安（`docs/components.md` の3節）を確かめる。
- カナリア: メモの中身がログに出ないこと。
- 全体: `go test ./...`、`make verify`、`make test-ui`。

- 公開フォームの説明（`features/contact/views/contact.html`）と、受信箱の説明（`admin_messages.html`）

## 10. 利用者が決めること

1. 「既読」を「対応中」に置き換えてよいか。推奨は置き換える。
2. メモの上限は2,000文字でよいか。推奨はこの値。
3. 一覧の既定は、未読と対応中だけでよいか。推奨はこの形で、全件の画面へのリンクを置く。
4. 承認境界2: 列 `note`・`last_activity_at` の追加を承認するか。

## 11. 進め方

1. 外部のモデルのレビューを受ける。保持の約束と、移行に触れるため。
2. 10節を決める。
3. ドメインモデルと台帳を直す。
4. 表の移行と保持の処理を、1つ目のコミットにする。
5. 画面とメモを、2つ目のコミットにする。
6. 文書と文面を、3つ目のコミットにする。
7. それぞれ8節の検証を通し、main へ早送りで取り込む。
