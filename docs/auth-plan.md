# アカウント管理 実装計画（管理者認証の複数アカウント化）

同梱機能の管理者認証（`features/auth`）を、1人の管理者だけの仕組みから、ロールを持つ複数のアカウントで使える仕組みに広げる計画です。CMSに限らず、業務アプリや社内ツール等の管理画面で使うことを前提にします。

## 1. 目的と範囲

- 最初の1人は、今までどおりサーバーで `make auth-setup` を実行してパスキーを登録する。
- 2人目以降は、管理者ロールのアカウントが管理画面でアカウントを作り、その人専用のパスキー登録URLを発行する。
- ログインは引き続きパスキーだけ（端末固定の認証器のみ。同期型は拒否）。パスワード・メールアドレス・氏名は扱わない。
- 範囲外: メールでの招待・通知（外部通信）、機能ごとの細かい権限、操作の記録（監査ログ）、外部ID連携。

## 2. 用語

| 用語 | 意味 |
|---|---|
| アカウント | 管理画面にログインできる人の単位（総称）。テーブルは `auth_accounts` |
| 管理者（`admin`） | アカウントを管理できるロール |
| メンバー（`member`） | 各機能の管理画面を使えるロール。アカウントの管理はできない |
| 呼び名 | アカウントを見分けるための表示名。実名・メールアドレスを入れないよう案内する |
| 登録URL | パスキーを登録するための1回限りのURL（`/admin/setup#token=...`）。特定のアカウントに結びつく |

管理者認証のロールは「アカウントを管理できるか」だけを決める。業務の権限（記事を公開できるか、申請を承認できるか等）は各機能が決める。機能はロールを参照できる（5節）。

## 3. ロールと権限

| 操作 | 管理者 | メンバー |
|---|---|---|
| ログイン・ログアウト | ○ | ○ |
| 各機能の管理画面（`Admin.Page`・`Admin.Form` で守られた画面） | ○ | ○ |
| 自分のパスキーの追加・名前変更・削除 | ○ | ○ |
| アカウントの一覧の表示 | ○ | × |
| アカウントの作成（呼び名・ロールの指定）と登録URLの発行 | ○ | × |
| 他のアカウントの登録URLの再発行（パスキーをなくした場合） | ○ | × |
| 他のアカウントのロール変更・停止・再開・削除 | ○ | × |
| 他のアカウントのパスキーの一覧・削除 | ○ | × |
| 機能が「管理者だけ」とした画面（`Admin.AdminPage`・`Admin.AdminForm`） | ○ | × |

決まり:

- 有効な管理者は常に1人以上いる。最後の有効な管理者は、降格・停止・削除できない（判定と更新は1つの文・トランザクションで行い、同時操作でも0人にならないようにする）。
- 自分のロールの変更・自分の停止・自分の削除はできない（別の管理者が行う）。
- ロール変更・停止・削除をしたら、そのアカウントの管理者セッションをすべて直ちに削除する。
- 停止中のアカウントは、パスキーが正しくてもログインできない。登録URLも使えない。

## 4. 流れ

### 4.1 最初のアカウント
1. `make auth-setup` は、アカウントが1件も無い場合だけ、管理者ロールのアカウント（呼び名「管理者」）を作り、その登録URLを表示する（15分有効、1回限り）。
2. 登録が済めば、その人が最初の管理者になる。

### 4.2 アカウントの追加
1. 管理者が `/admin/accounts/new` で呼び名とロールを入力する。
2. アカウントを作り、そのアカウントに結びついた登録URLを画面に1回だけ表示する（再表示しない。DBにはハッシュのみ）。
3. 管理者は、URLを別の手段で本人に渡す。キットはメールを送らない。
4. 本人がURLを開いて端末名を入力し、パスキーを登録する。登録後はログインし直してもらう（今と同じ）。
5. 有効期限は24時間（未決定A）。発行し直すと、そのアカウントの未使用のURLは無効になる。

### 4.3 パスキーをなくしたアカウント
1. 管理者が、そのアカウントの登録URLを再発行する。
2. 再発行の画面で「このアカウントの登録済みのパスキーとログイン状態を削除する」を選べる（紛失・盗難時）。選んだ場合は、URLの発行と同じトランザクションで削除する。

### 4.4 全員がログインできない場合（`make auth-recover`）
未決定B。おすすめは次の案。

- 全アカウントのパスキー・管理者セッション・登録URLを削除する。アカウント（呼び名・ロール）は残す。
- 管理者ロールのアカウントを1つ選ぶ（引数でIDを指定。省略時は一覧を表示して終了）か、新しい管理者アカウントを作り、その登録URLを表示する。
- 他のアカウントは、復旧した管理者が登録URLを再発行する。
- 乗っ取りが疑われるときに、全員の鍵を確実に入れ替えるための手順とする。

### 4.5 複製の疑い
署名カウンタで複製の疑いを検出したら、そのパスキーを無効にし、そのアカウントの管理者セッションだけを削除する（今は全員分を削除している）。管理者には管理画面の上部で警告を出し、該当アカウントのパスキー一覧で確認・削除できるようにする。

## 5. 他の機能への口（`features.Admin`）の変更

- `AdminSession` に `AccountID() int64`（ログ・機能のデータへの記録用。呼び名は返さない）と `Role() string`（`"admin"` / `"member"`）を足す。
- `Admin` に `AdminPage`・`AdminForm` を足す。管理者ロールでなければ403を返す（未ログインはログイン画面へ）。
- 既存の `Page`・`Form` は、両ロールとも通す（CMSの記事の管理画面は今までどおり）。
- 管理画面のナビは、ロールに応じて「アカウントの管理」を出し分ける（`PageData` の中で判定）。

## 6. 画面と経路（すべて独立経路・JSなし。パスキーの操作だけ既存の `webauthn.js`）

| 経路 | ロール | 内容 |
|---|---|---|
| `GET /admin/accounts` | 管理者 | アカウントの一覧（呼び名・ロール・状態・パスキー数・最終ログイン日時） |
| `GET/POST /admin/accounts/new` | 管理者 | 作成。作成後に登録URLを1回だけ表示する画面へ |
| `GET /admin/accounts/{id}` | 管理者 | 詳細。ロール変更・停止/再開・登録URLの再発行・パスキーの一覧と削除 |
| `POST /admin/accounts/{id}/role`・`/disable`・`/enable`・`/setup-url`・`/delete` | 管理者 | 各操作（削除は確認ページを経る） |
| `GET /admin/passkeys` | 両方 | 自分のパスキーの管理（今の画面を自分のアカウントに限定） |

登録URLの表示画面は `Cache-Control: no-store` のまま、`Referrer-Policy: no-referrer` を維持する。URLはフラグメントに入れるため、サーバーのログにも残らない。

## 7. 保存データ（承認境界2）

| 変更 | 列 | 保持期間 |
|---|---|---|
| 新規 `auth_accounts` | `id`（INTEGER、AUTOINCREMENT）、`name`（呼び名、1〜50字）、`role`（`admin`/`member`）、`webauthn_user_id`（ランダム16バイト）、`created_at`、`disabled_at`、`last_login_at` | 管理者が削除するまで |
| `auth_credentials` | `account_id` を追加（`auth_accounts.id` への外部キー、ON DELETE CASCADE） | アカウントと同じ |
| `auth_sessions` | `account_id` を追加（同上、CASCADE） | 今と同じ（無操作2時間・発行から12時間） |
| `auth_setup_tokens` | `account_id` を追加（同上、CASCADE）、`expires_at` は用途により15分または24時間 | 発行から有効期限まで。使用済み・失効分はGCで削除 |
| `auth_settings` | 廃止（`webauthn_user_id` は `auth_accounts` へ移す） | ― |

- 呼び名は自由入力のため、実名を入れられる余地がある。入力欄に「実名・メールアドレスは入れないでください（例: 編集担当A）」と表示し、台帳に記載する（未決定C）。
- 操作の記録（誰が誰を追加・停止したか）はDBに持たない。サーバーのログに、固定のイベント名とアカウントIDだけを出す（未決定D）。

### 7.1 既存のデータからの移行
- 管理者認証の中に、スキーマの版を持つ表（`auth_meta`、`schema_version`）を作り、Goで順番に移行する。CMS等の他の機能の表には触れない。
- 版1→2: `auth_accounts` を作り、既存の `auth_settings.webauthn_user_id` を持つ管理者アカウント（呼び名「管理者」）を1件作る。既存のパスキー・セッション・登録トークンの `account_id` をそのアカウントにする。`auth_settings` を削除する。1つのトランザクションで行う。
- 移行に失敗した場合は起動を止め、ロールバックする。

## 8. WebAuthnの変更点

- 登録: `user.id` は登録URLのアカウントの `webauthn_user_id`。`user.name` はアカウントIDから作る固定の文字列（例: `account-12`）、`displayName` は呼び名。認証器に呼び名が保存されるため、画面でその旨を案内する。
- `excludeCredentials` は、そのアカウントのパスキーだけ。
- ログイン: `allowCredentials` は空のまま（アカウントを選ばない）。返ってきた `rawId` でパスキーを引き、そのアカウントの `webauthn_user_id` と `userHandle` の一致を確かめる。アカウントが停止中ならログインを拒否する。
- 登録トークンは「どのアカウントのパスキーとして登録するか」を持つ。トークンの消費とパスキーの保存は今と同じく1つのトランザクションで行う。

## 9. ログ

- 固定のイベント名とアカウントIDだけを出す（例: `auth account created`、`account_id`、`role`）。呼び名・トークン・credential IDは出さない。
- カナリアテストに、呼び名と登録トークンを加える。

## 10. テスト

- ロールごとの可否（3節の表の全行）。メンバーがアカウント管理の経路を開く・送ると403になる。
- 最後の管理者を降格・停止・削除できない。並行に2人を降格しても管理者が0人にならない。
- 自分のロール変更・停止・削除の拒否。
- ロール変更・停止・削除で、そのアカウントのセッションが無効になる。停止中はログインも登録URLも使えない。
- 登録URLが別のアカウントのパスキーを登録できない。再発行で古いURLが無効になる。期限（15分・24時間）。
- 複製の疑いで、そのアカウントのセッションだけが消える。
- 移行（版1→2）でパスキー・セッションが引き継がれ、既存の管理者でそのままログインできる。失敗時のロールバック。
- `auth-recover` の動き。
- 見本の機能（テスト用）で、`AdminPage`・`AdminForm` が管理者だけを通す。
- 検査がわざと外したときに失敗すること（ロールの判定、最後の管理者の判定）。

## 11. 進め方

1. 本計画のレビューと、未決定A〜Dの確定。
2. スキーマの版と移行、アカウントの保存処理（ロール・最後の管理者の判定）。
3. WebAuthnの登録・ログインのアカウント対応、`auth-setup`・`auth-recover`。
4. アカウント管理の画面、`Admin` の口の拡張（`AdminPage`・`AdminForm`・`Role`）。
5. 台帳・README・スキル・カナリアテストの更新、監査。

各段階で全テスト・`make verify` を通してからコミットする。

## 13. 守る範囲・守らない範囲

- 管理者ロールのアカウントが乗っ取られると、他のアカウントの追加・削除ができる。管理者ロールのアカウントは最小限にし、パスキーを2つ以上登録することを推奨する。
- 登録URLの受け渡し経路（チャット等）の安全は、キットの範囲外。URLは1回限り・期限付きで、使用後は無効になる。
- 業務の細かい権限は各機能が設計する。
