# 管理画面のUI標準と自動検査 実装計画

状態: 2026-10-29、計画の段階。利用者の依頼「機能を足すたびにUIがぶれないよう、統一的なUI/UX標準を作る」による。外部レビュー前。
きっかけは、カタログのカテゴリ・タグ管理画面のぶれ（`24cd2df` で修正）。共通の入力欄の部品（`field`）があっても使わずに書けてしまい、テストも通ったため、見出し・エラー文・一覧の形・削除の見た目が他の画面とずれた。

## 1. 目的と範囲

管理画面（`/admin` 以下）の作りを「部品・画面の型・自動検査・スキル」の4層でそろえ、新しい機能を足した人が何もしなくても、標準から外れたら `go test ./...` が落ちるようにする。

- 対象は管理画面。公開ページ（Site・お知らせ・カタログの公開側）は、画面ごとの作りが違うため、今回は静的な検査（6.1）だけを当て、描画しての検査は後で広げる。
- 見た目の良し悪し（余白・配置）と文の言い回しは、テストで判定しない。画面の型の文書と用語集、見本の画面の撮影（7節）で防ぐ。
- 新しいCSS・JSのファイル、保存データ、外部通信、`go.mod` の変更は無い（承認境界1〜5に当たらない）。CSSは `style.css` にクラスを足す範囲。CIの導入は10節で決める。

## 2. 今のぶれ（2026-10-29 時点の棚卸し）

| 種類 | 箇所 |
|---|---|
| 入力欄を手書き（共通の `field` を使っていない） | カタログ項目のカテゴリ（`<select>`）・新規タグ（`<textarea>`）、アカウント作成後の登録URL |
| 削除の確認画面の形が2通り | お知らせ・アカウント・パスキーは「`btn-danger` の削除」＋「`btn-secondary` の削除せずに戻る」を `action-bar` に並べる。カタログの項目・分類は、ボタンだけで、戻るのは文中のリンク |
| 表の中の削除 | パスキーの一覧は文字のリンク「削除」、アカウントの画面は `btn-danger` のボタン「削除」 |
| 選択肢（ラジオ・チェックボックス） | `fieldset`・`legend` で囲む画面と、`<p><label>` を並べるだけの画面がある |

## 3. 画面の型

管理画面は、次のどれかの型で作る。型ごとに要素の順番を決め、文書（`docs/ui-patterns.md`、新規）に見本のテンプレートを載せる。

| 型 | 構成（上から） | 例 |
|---|---|---|
| 一覧 | `h1`（「〜の管理」）→ 完了メッセージ → 操作の並び（主操作は `btn-primary` 1つ、他はリンク）→ 表（`caption`・`th scope`、最後の列が「操作」）か、空のときの1文（「〜はまだありません。」）→ ページ送り | お知らせの管理、カテゴリの管理 |
| 作成・編集 | `h1`（「〜の作成」「〜の編集」）→ 画面全体のエラー（一時的な失敗など）→ フォーム（`card`、入力欄は部品、送信は `btn-primary`）→ 公開などの別操作の並び → 削除（`btn-danger` のリンク、編集のときだけ）→ 一覧へ戻るリンク | お知らせの作成・編集 |
| 削除の確認 | `h1`（「〜の削除」）→ 対象と影響の説明（何が消え、何が残り、元に戻せないか）→ 操作の並び（`btn-danger` の「削除する」＋ `btn-secondary` の「削除せずに戻る」） | お知らせの削除 |
| 一覧＋追加 | 一覧の型の後に、`h2`（「〜の追加」）とフォーム。追加の失敗は、この画面のまま入力欄にエラーを出す | カテゴリ・タグの管理 |

- ログイン・初回登録・登録URLの表示など、認証の画面は型の外とし、6.2の共通の検査だけを当てる。
- 入力の失敗は、送る前と同じ型・同じ `h1` の画面で、入力した値を残して返す。原因が入力欄にあるときは、その欄にエラー（`aria-invalid`）、ないとき（一時的な失敗等）は画面全体のエラー（`role="alert"`）。

## 4. 用語集とメッセージ

`docs/ui-patterns.md` に置く。

- 操作の名前: 「〜を作成する」（新しく作る主操作）、「保存する」、「追加する」（一覧の画面で足す）、「削除する」、「削除せずに戻る」、「〜の一覧へ戻る」、「公開する」「非公開（下書き）に戻す」。表の操作列は「編集」「削除」の短い形で、読み上げ用に対象の名前を `visually-hidden` で添える。
- 件数: 「○件」。0件を特別に言う文（「使っている項目はありません。」）は、0件のときに言い換える。
- エラー文: 何が問題か＋どうすればよいか（例:「同じ名前のタグがあります。別の名前にしてください。」）。その画面に関係しない条件を並べた汎用の文を使わない。
- 完了メッセージ: Coreの `notice`（「変更を保存しました。」等）を使い、機能ごとに作らない。

## 5. 部品

`internal/web/views/components.html` と `internal/web/form` に足す・広げる。部品の追加は `docs/components.md` の手順に従う。

| 部品 | 内容 |
|---|---|
| `field` を広げる | `<select>`（`form.Field` に選択肢 `Options` を足す）。複数行は今の `Rows` |
| `choices`（新規） | ラジオ・チェックボックスの選択肢。必ず `fieldset`・`legend` で囲み、説明・エラーを `field` と同じ形で出す |
| `confirm-actions`（新規） | 削除の確認の操作の並び（削除する／削除せずに戻る）。送信先と戻り先を渡す |
| `empty`（新規） | 空のときの1文。`<p>` で出し、箇条書きにしない |
| 表の操作列 | 部品にせず、文書の見本と6.2の検査で形をそろえる（列の中身が画面ごとに違うため） |

部品を足したら、2節のぶれを部品に寄せて直す（6節の検査を厳しくする前に行う）。

## 6. 自動検査（`go test ./...` で走る。Chrome不要）

### 6.1 テンプレートの静的な検査（`test/template_test.go` に足す）

- 機能の `views/` の中で、`<label` `<input` `<select` `<textarea` を直接書かない（`type="hidden"` のCSRFトークン、`components.html`、許可リストに書いた例外を除く）。例外は理由つきで許可リストに書く（例: 公開一覧の検索欄）。
- `<table>` には `<caption>` と `th scope` がある。
- 「削除」へのリンク・ボタンは `btn-danger`、または表の操作列の短い形。

### 6.2 全管理画面を描画しての検査（`test/admin_ui_test.go`、新規）

1. **経路を集める**: `web.IsolatedMux` に、登録された経路を返す読み取り専用の `Patterns()` を足す。全機能を登録した構成で、`GET` かつ `/admin` で始まる経路を集める（静的ファイルを除く）。
2. **URLを埋める**: テストの最初に、各機能の見本のデータ（お知らせ・項目・カテゴリ・タグ・アカウント・パスキー）を作り、「経路の型 → 開くURL」の表を書く。`{…}` を含む経路が表に無ければ、テストを落とす（「見本のURLを登録してください」）。新しい画面が検査から漏れない。
3. **開く**: `authtest` で管理者とメンバーのセッションを作り、実際の経路（認証・CSRF・CSP）を通して開く。データが空の状態と入っている状態の2回。メンバーで開けない画面は、メンバーの検査から外す（権限の検査は既存のテストが受け持つ）。
4. **解析**: 標準の `encoding/xml` を、HTML向けの緩い設定（`Strict=false`、`AutoClose=xml.HTMLAutoClose`、`Entity=xml.HTMLEntity`）で使う。依存は足さない。
5. **検査項目**（全画面）:
   - `h1` がちょうど1つで、`<title>` の先頭と一致する。
   - 同じ `id` が無い。`aria-describedby`・`label for`・`aria-controls` の参照先が存在する。
   - 見える入力欄（`hidden` 以外の `input`・`select`・`textarea`）には、`label for` か、囲む `label`、または `aria-label` がある。ラジオ・チェックボックスの組は `fieldset`・`legend` の中にある。
   - `POST` のフォームには `csrf_token` がある。
   - `main` の中の `ul`・`ol` にはクラスがある（素の箇条書きを出さない）。
   - `table` に `caption` と `th scope` がある。
   - 経路が `/delete` で終わる画面（削除の確認）は、`btn-danger` の送信ボタンと「削除せずに戻る」がある。
6. **失敗の画面**: 各機能が「わざと失敗する送信の見本」（経路・送る値・期待する `h1`）を表に書く。送った結果が400で、`aria-invalid="true"` か `role="alert"` があり、`h1` が期待どおりであることを確かめる。例: カテゴリの重複・空の名前、お知らせの空のタイトル、アカウントの空の呼び名。

検査が効くことを、2節のぶれと `24cd2df` で直したぶれをわざと戻して、落ちることで確かめる。

## 7. 見本の画面の撮影（`make test-ui` の中、Chromeがあるときだけ）

`test/browser/` に、6.2と同じ見本のデータで主な管理画面（各型・空の状態・失敗の画面、幅1100pxと360px）を撮るテストを足す。画像は `test/browser/shots/`（`.gitignore`）に書き出し、人かAIが見て確かめる。画像の自動比較はしない（フォント・環境の差で誤検知が多いため）。

## 8. 文書とスキル

- `docs/ui-patterns.md`（新規）: 画面の型・見本のテンプレート・用語集・メッセージの書き方。
- `docs/components.md`: 足した部品。`docs/ui-guidelines.md` から `ui-patterns.md` へ案内する。
- スキル（150行以内を保つ）: 設計スキルに「画面ごとに型を選ぶ」、実装スキルに「型の見本と部品で組み、失敗の見本を6.2の表に足す」、監査スキルに「見本の画面を撮って確かめる」を、それぞれ1〜2行。
- `AGENTS.md` のコア原則3に、`ui-patterns.md` への1行の案内。

## 9. 進め方

1. この計画の外部レビュー（Fable）と、10節の決定。
2. 部品（5節）と `IsolatedMux.Patterns()`。
3. 2節のぶれを部品に寄せて直す。
4. 検査（6節）を入れ、わざと崩して落ちることを確かめる。
5. 撮影（7節）、文書とスキル（8節）。
6. 紹介サイトに取り込み、VPSの実行ファイルを置き換える。

## 10. 決めること

| # | 事項 | 提案 |
|---|---|---|
| 1 | CI（GitHub Actions）でプッシュ・プルリクエストのたびに `go test ./...` と `make verify` を走らせるか | 入れる。公開リポジトリのため無料枠で動く見込み（採用前に公式で確認）。外部のサービスでテストが動くことになる（実行するのはテストだけで、秘密は渡さない）。`make test-ui` はChromeが要るため、最初は入れない |
| 2 | 表の中の削除の形 | 操作列は文字のリンク「削除」（確認画面へ移る）にそろえる。ボタンを表の中に並べない |
| 3 | 公開ページへの描画検査の拡大 | 今回はしない。管理画面で運用してから決める |

## 11. 守らない範囲・残るリスク

- 検査は構造だけを見る。余白・色・文の自然さは、撮影と文書で人が確かめる。
- 見本のURLと失敗の見本の表は、機能を足した人が書く必要がある。書かなければテストが落ちるが、表の中身（失敗の見本の網羅）までは強制できない。
- `encoding/xml` の緩い解析は、壊れたHTMLを黙って直して読むことがある。HTMLの文法の検査器ではない。
