# 管理画面のUI標準と自動検査 実装計画

状態: 2026-10-29、利用者が10節の4項目を提案どおり承認し、実装した。外部レビュー（Fable）の指摘は本文に反映済み（要点は12節）。結果は13節。
きっかけは、カタログのカテゴリ・タグ管理画面のぶれ（`24cd2df` で修正）。共通の入力欄の部品（`field`）があっても使わずに書けてしまい、テストも通ったため、見出し・エラー文・一覧の形・削除の見た目が他の画面とずれた。

## 1. 目的と範囲

管理画面（`/admin` 以下）の作りを「部品・画面の型・自動検査・スキル」の4層でそろえ、新しい機能を足した人が何もしなくても、標準から外れたら `go test ./...` が落ちるようにする。

- 対象は管理画面。公開ページ（Site・お知らせ・カタログの公開側）は、画面ごとの作りが違うため、今回は静的な検査（6.1）だけを当て、描画しての検査は後で広げる。
- 見た目の良し悪し（余白・配置）と文の言い回しは、テストで判定しない。画面の型の文書と用語集、見本の画面の撮影（7節）で防ぐ。
- 新しいCSS・JSのファイル、保存データ、外部通信、`go.mod` の変更は無い（承認境界1〜5に当たらない）。CSSは `style.css` にクラスを足す範囲。CIの導入は10節で決める。

## 2. 今のぶれ（2026-10-29 時点の棚卸し）

| 種類 | 箇所 |
|---|---|
| 入力欄を手書き（共通の `field` を使っていない） | カタログ項目のカテゴリ（`<select>`）・新規タグ（`<textarea>`）、登録URLの表示（`readonly` の入力欄）、パスキー一覧の表の中の名前変更 |
| 削除の確認画面の形が2通り | お知らせ・アカウント・パスキーは「`btn-danger` の削除」＋「`btn-secondary` の削除せずに戻る」を `action-bar` に並べる。カタログの項目・分類は、ボタンだけで、戻るのは素のリンク |
| 表の中の削除 | パスキーの一覧は文字のリンク「削除」（確認画面へ）、アカウントの画面のパスキーの表は `btn-danger` のボタン（確認画面なし） |
| `<title>` と `h1` のずれ | 分類の削除確認（`<title>` が「〜の編集」のまま）、登録URLの表示（`<title>`「登録URLの発行」、`h1`「アカウントを作成しました」等） |
| 一覧の形 | お知らせ・アカウントは表、カタログの項目はカードの並び |

ラジオの組は、すでにどの画面も `fieldset`・`legend` の中にある。外にあるのは単独のチェックボックス（登録URLの再発行の `reset_keys`）だけで、これは正しい形。

## 3. 画面の型

管理画面は、次のどれかの型で作る。型ごとに要素の順番を決め、`docs/components.md` に「画面の型」の節を足して見本のテンプレートを載せる（UIの文書を増やさない）。

| 型 | 構成（上から） | 例 |
|---|---|---|
| 一覧 | `h1`（「〜の管理」）→ 完了メッセージ → 操作の並び（主操作は `btn-primary` 1つ、他はリンク）→ 表（`caption`・`th scope`、最後の列が「操作」）か、空のときの1文（「〜はまだありません。」の `<p>`）→ ページ送り | お知らせの管理 |
| 一覧＋追加 | 一覧の型の後に、`h2`（「〜の追加」）とフォーム。追加の失敗は、この画面のまま入力欄にエラーを出す | カテゴリ・タグの管理 |
| 作成・編集 | `h1`（「〜の作成」「〜の編集」）→ 画面全体のエラー → フォーム（`card`、入力欄は部品、送信は `btn-primary`）→ 公開などの別操作の並び → 削除（`btn-danger` のリンク、編集のときだけ）→ 一覧へ戻るリンク | お知らせの作成・編集 |
| 詳細（状態と操作） | `h1`（「〜: 名前」）→ 完了メッセージ・エラー → 状態（表か定義リスト）→ 操作ごとの `h2` とフォーム → 削除（`btn-danger` のリンク）→ 一覧へ戻るリンク | アカウントの詳細 |
| 削除の確認 | `h1`（「〜の削除」）→ 対象と影響の説明（何が消え、何が残り、元に戻せないか）→ 操作の並び（`btn-danger` の「削除する」＋ `btn-secondary` の「削除せずに戻る」） | お知らせの削除 |

- 型の外（6.2の共通の検査だけを当てる）: ログイン・初回登録の画面、登録URLの表示、パスキーの管理の追加（JSで開くフォームで、失敗はJS側で `role="status"` に出すため）。
- `<title>` は `h1` と同じか、`h1` がそれで始まる（例: `h1`「アカウント: 名前（自分）」と `<title>`「アカウント: 名前」）。
- 入力の失敗は、送る前と同じ型・同じ `h1` の画面で、入力した値を残して返す。原因が入力欄にあるときは、その欄にエラー（`aria-invalid`）、ないとき（一時的な失敗・状態の衝突）は画面全体のエラー（`role="alert"`）。状態コードは、入力の誤り400、状態の衝突（最後の管理者を消す等）409、一時的な失敗503。

## 4. 用語集とメッセージ

`docs/components.md` の「用語とメッセージ」の節に置く。

- 操作の名前: 「〜を作成する」（新しく作る主操作）、「保存する」、「追加する」（一覧の画面で足す）、「削除する」、「削除せずに戻る」、「〜の一覧へ戻る」、「公開する」「非公開（下書き）に戻す」。表の操作列は「編集」「削除」の短い形のリンクで、読み上げ用に対象の名前を `visually-hidden` で添える。
- 件数: 「○件」。0件を特別に言う文（「使っている項目はありません。」）は、0件のときに言い換える。
- エラー文: 何が問題か＋どうすればよいか（例:「同じ名前のタグがあります。別の名前にしてください。」）。その画面に関係しない条件を並べた汎用の文を使わない。
- 完了メッセージ: Coreの `notice`（「変更を保存しました。」等）を使い、機能ごとに作らない。

## 5. 部品

`internal/web/views/components.html` と `internal/web/form` に足す・広げる。部品の追加は `docs/components.md` の手順に従う。

| 部品 | 内容 |
|---|---|
| `field` を広げる | `<select>`（`form.Field` に選択肢 `Options`）、ラベルを見えなくする `LabelHidden`（表の中の入力欄）、読み取り専用の `Readonly`（登録URLの表示） |
| `choices`（新規） | 同じ名前のラジオ・チェックボックスの組。必ず `fieldset`・`legend` で囲み、説明・エラーを `field` と同じ形で出す |
| `confirm-actions`（新規） | 削除の確認の操作の並び（`btn-danger` の削除する／`btn-secondary` の削除せずに戻る）。送信先・戻り先・CSRFトークンを渡す |

- 空のときの1文と表の操作列は、部品にしない。文書の見本と6節の検査で形をそろえる。
- 部品を足したら、2節のぶれを部品に寄せて直す（6節の検査を厳しくする前に行う）。

## 6. 自動検査（`go test ./...` で走る。Chrome不要）

### 6.1 テンプレートの静的な検査（`test/template_test.go` に足す）

- 機能の `views/` の中で、`<label` `<input` `<select` `<textarea` を直接書かない（`type="hidden"` の値、`components.html`、許可リストに書いた例外を除く）。例外は理由つきで許可リストに書く。最初の例外は、カタログの公開一覧の検索欄（`list.html`）。
- `<table>` には `<caption>` と `th scope` がある。
- `<td>` の中に `btn-danger` を置かない（表の削除は確認画面へのリンクにする）。
- `features/*/views/admin_*.html` の全ファイルが、6.2の見本の表のどれかに対応づけられている。新しい画面のテンプレートを足して見本を書かなければ落ちる。
- `features/**/*.go` の中の `"GET /admin` で始まる文字列リテラルを集め、6.2で集めた経路に全部含まれることを確かめる（`IsolatedMux` 以外への管理画面の登録を見つける）。経路は文字列リテラルで書く決まりにし、カタログの分類の経路を、文字列の連結から `{kind}` を使ったリテラルに直す。

### 6.2 全管理画面を描画しての検査（`test/admin_ui_test.go`、新規）

1. **構成**: テストで site・news・auth・catalog を登録して `app.BuildRoutes` を呼ぶ（`cmd/server/features.go` に頼らない）。
2. **経路を集める**: `web.IsolatedMux` に、登録された経路を返す読み取り専用の `Patterns()` を足す。`BuildRoutes` の後に、テスト側で別の `IsolatedMux` を作って各機能の `RegisterIsolatedRoutes` をもう一度呼び、`Patterns()` を読む。`GET` かつ `/admin` で始まる経路を対象にし、静的ファイルを除く。
3. **見本の表**: 経路の型ごとに、開くURLを1つ以上書く（状態で中身が変わる画面は複数。例: 自分と他人のアカウント、停止中のアカウント、公開中・下書き・予約のお知らせ、使用中・未使用の分類）。各行に、使うセッション（管理者・メンバー・なし）と、描かれるテンプレート名を書く。`{…}` を含む経路が表に無ければ落とす。見本のデータは各機能の公開の関数（`news.NewPostStore`、`catalog.NewStore` 等）で作る。パスキーは `authtest` に `NewCredential(t, db, accountID, label) string`（URL用の `Param` を返す）を足し、`NewSession` がアカウントIDも返す形の関数を足す。
4. **POSTで描かれる画面**: 成功のときに画面を返す送信（登録URLの表示: `POST /admin/accounts`、`POST /admin/accounts/{id}/setup-url`）も、送る値と描かれるテンプレート名を表に書いて検査する。
5. **開く**: 実際の経路（認証・CSRF・CSP）を通して開く。データが空の状態と入っている状態の2回。3xx と `text/html` 以外の応答は、状態コードだけ確かめて検査から外す（例: `GET /admin` の転送、セッションありの `/admin/login`）。メンバーで403になる画面は、メンバーの検査から外す。
6. **解析**: 標準の `encoding/xml` を、HTML向けの緩い設定（`Strict=false`、`AutoClose=xml.HTMLAutoClose`、`Entity=xml.HTMLEntity`）で使う。依存は足さない（レビューで、今の全管理画面44応答を解析エラーなしで読めることを確認済み）。
7. **検査項目**（全画面）:
   - `h1` がちょうど1つで、`<title>` の本体（サイト名を除く部分）は `h1` と同じか、`h1` がそれで始まる。
   - 同じ `id` が無い。`aria-describedby`・`label for`・`aria-controls`・`aria-labelledby` の参照先が存在する。
   - 見える入力欄（`hidden` 以外の `input`・`select`・`textarea`）には、`label for` か、囲む `label`、または `aria-label` がある。同じ `name` のラジオ・チェックボックスが2つ以上あれば、`fieldset`・`legend` の中にある。
   - `POST` のフォームには `csrf_token` がある。
   - `main` の中の `ul`・`ol` にはクラスがある（素の箇条書きを出さない）。
   - `table` に `caption` と `th scope` がある。`td` の中に `btn-danger` が無い。
   - 経路が `/delete` で終わる画面（削除の確認）は、同じ `action-bar` の中に、`btn-danger` の送信ボタン1つと、`btn-secondary` の「削除せずに戻る」のリンク1つがある。
   - 一覧の型の画面（見本の表で型を書く）は、`table` か、`main` 直下の `p` の空の1文がある。
8. **失敗の画面**: 各機能が「わざと失敗する送信の見本」を表に書く。列は、経路・送る値・期待する状態コード（400／409／503）・期待する `h1`・エラーの場所（入力欄の `id` か「画面全体」）。応答が、状態コード・`h1`・エラーの場所（欄なら `aria-invalid="true"` と `-error` の文、画面全体なら `role="alert"`）に合い、送った値が入力欄に残っていることを確かめる。例: カテゴリの重複・空の名前（追加と改名）、お知らせの空のタイトル、アカウントの空の呼び名、最後の管理者の停止（409）。

検査が効くことを、2節のぶれを直す前の状態と、`24cd2df` で直したぶれ（追加の失敗で見出しが「編集」になる、重複を画面全体のエラーで出す、素の箇条書き）をわざと戻して、落ちることで確かめる。

## 11. 守らない範囲・残るリスク

- 検査は構造だけを見る。余白・色・文の自然さは、撮影と文書で人が確かめる。
- 見本の表は、機能を足した人が書く必要がある。書かなければ落ちるが、状態ごとの見本や失敗の見本の網羅までは強制できない。
- `encoding/xml` の緩い解析は、壊れたHTMLを黙って直して読むことがある。HTMLの文法の検査器ではない。`<template>` の中身も通常の要素として読むため、そこに `id` を置くと重複として扱われる。
- `"GET /admin` の文字列の突合は、文字列を組み立てて登録する経路を見つけられない。決まり（リテラルで書く）で補う。

## 13. 実装の結果（2026-10-29）

- 部品: `field` に選択・単独のチェックボックス・読み上げ専用のラベル・読み取り専用、新しく `choices`・`confirm-actions`（テンプレートの `confirm` 関数）。`IsolatedMux.Patterns()`、`authtest.NewAccountSession`・`NewCredential`。
- 今のぶれの修正: 削除の確認を全画面で `confirm-actions` に、アカウントの画面のパスキーの削除に確認画面を新設、表の中の削除をリンクに、カタログの項目の一覧を表に、手書きの入力欄を部品に、分類の削除確認と登録URLの表示の題名を見出しに合わせた。カタログの項目とお知らせの入力の誤りを、汎用の文から欄ごとの文（`InputError`）にした。
- 検査: `test/admin_ui_test.go`（全管理画面の描画検査、成功・失敗の送信の見本、テンプレートと経路の突き合わせ）、`test/template_test.go`（入力欄の直書き、表の `caption`・`scope`）。プライバシーポリシーの表に読み上げ用の `caption` を足した。わざと崩して落ちることを17通りで確かめた（コミット `3645b5b` の本文）。
- 撮影: `test/browser/shots_test.go` が主な管理画面11種を幅1100px・360pxで撮る。撮った画面で、カタログの項目の公開・削除のボタンの高さのずれと、パスキーの表の名前の欄が狭い画面で潰れることを見つけて直した。
- 文書: `docs/components.md` に部品・画面の型・用語とメッセージ・検査の節、`ui-guidelines.md`・`AGENTS.md`・README・3つのスキルに案内。
- CI: `.github/workflows/test.yml`（`make verify` と `go test -race ./...`、アクションはコミットのハッシュで固定、権限は読み取りだけ）。公開リポジトリの標準ランナーは無料（GitHubの公式の料金の説明で確認）。
- 6.1の「`td` の中の `btn-danger` の禁止」は、テンプレートの静的な検査ではなく、描画しての検査（6.2）で行う。
