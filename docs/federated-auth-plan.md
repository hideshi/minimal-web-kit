# アプリ間の共通認証 計画案

状態: 計画案。方式の試作検証は実施済み（末尾参照）。本書には比較途中の案を含む。現時点の提案は[詳細設計案](federated-auth-detail-plan.md)を優先し、採用済みの仕様とは区別する。実装・依存追加・データ追加・配備は未実施。本書は将来の設計であり、現行仕様の正本 `docs/domain/auth.md` は変更しない。

## 1. 目的と合意した要件

- 自社が管理するアプリAが、既存のアカウント管理・パスキー認証を提供する。
- アプリBは独自のアカウント作成・パスキー管理を持たず、Aで本人確認する。Bはキット以外で実装されていてもよい。
- Aでアカウントを停止したら、Bの既存セッションも次の保護された要求から利用不可にする。
- Bは保護された要求ごとにAへ有効性を問い合わせ、正常な確認が取れない間はアクセスを許可しない。肯定結果を要求間でキャッシュしない。
- 停止前に確認が済んだ処理の取り消し、表示済み画面の消去、既に取得されたデータの回収は保証しない。

## 2. 現状と構成案

既存の `features/auth` は、パスキー、アカウント停止、ロール、ハッシュ保存のセッションを持つ。Cookieは `/admin` 用で、外部連携は現行ドメインモデルの対象外。AのCookie・DBをBと共有しない。

| 担当 | A（認証提供側） | B（認証利用側） |
|---|---|---|
| 本人確認 | 既存のパスキー認証を利用 | Aへブラウザを誘導 |
| アカウント | 作成・停止・削除・回復 | 不変の外部識別子で利用者を識別 |
| セッション | A用セッションと連携の有効性を管理 | B用のランダムCookieとサーバー側セッション |
| 権限 | 連携先の登録・利用許可 | Bの業務権限を判定 |

Aのadmin/memberをBの管理者権限に自動変換しない。利用許可は初期状態では拒否し、登録した連携先と許可した利用者だけを対象にする。

提供側は `features/auth` 内の明示的な設定で有効化し、利用側だけを別の任意機能にする案を推奨する。停止と失効を同じDBトランザクションで行い、CLIによる復旧・全体リセット・GCも同じ管理範囲に入れるためである。別機能にする代替案では、authがトランザクションに参加できる口を公開し、失敗時は全体をロールバックする設計が必要になる。単なる更新後の通知では代替できない。Coreに必須のネットワーク依存を入れない。別リポジトリで拡張する案とも、依存数・既存authとの結合・更新のしやすさを比較して確定する。機能名・コマンド名は未定。

## 3. ログインと有効性確認

標準のログイン連携はOpenID Connect（OIDC）のAuthorization Code FlowとPKCE（S256）を候補とする。対象はまずサーバー側でセッションを持つWebアプリ。ログインの独自プロトコルは作らない。有効性照会には標準利用案と独自契約案があるため、下記の比較後に確定する。

1. Bで短命・一回限りのログイン試行を作る（state、nonce、PKCEをブラウザの試行に結び付ける）。元のページはstateに直接入れずサーバー側に保存し、B内部の許可した相対パスだけに制限する。`//`、バックスラッシュ、制御文字、符号化した迂回も拒否する。
2. 登録済みAの認証経路へ移動する。Aは未ログインならパスキー認証し、連携先・利用者の許可を確認する。
3. Aは進行中の認可要求を期限付きで保存し、認証後に安全に復帰する。登録した完全一致の戻り先に短命・一回限りのコードを返す。コードはclient_id・redirect_uri・S256のchallengeに結び付け、challengeなしは拒否する。
4. Bはサーバー側のconfidential clientとして、PKCEに加えてクライアント認証を行う。Bのサーバーがコードを交換し、署名、issuer、audience、期限、nonce等を検証する。検証前にBセッションを作らない。成功後はセッションIDを新しくする。
5. Bは利用者を `(issuer, sub)` で識別する。呼び名・メール・Aの内部連番を識別の根拠にしない。subは再利用せず、パスキーのリセットでも変えない。
6. Bは以降の保護された要求ごとに、登録したBの資格情報でAへ問い合わせる。照会対象は後述の方式選定で決める。IDトークンの署名検証だけで継続利用を許さない。

有効性確認の方式は未決。いずれもAが最新のDBで停止・利用許可・失効を判定し、認証されたBが許可された対象だけを照会できるようにする。

| 案 | 長所 | 追加の責務 |
|---|---|---|
| RFC 7662による連携トークンの照会 | 標準の応答と個別の連携失効を利用できる | Bで復元可能なトークンを保護する必要がある |
| Bの資格情報でsubとログイン時の世代を照会 | Bに利用者ごとの復元可能トークンを保存せずに済む | 独自API契約と失効世代が必要。標準OIDCクライアントだけでは対応できない |

要件を小さく満たす後者を比較の第一候補とするが、採用は承認前に確定する。単なる「現在有効なsubか」だけでは停止・再開後に古いセッションが復活するため不十分。世代はAがログイン時に発行する署名済みの結果と結び付け、Bの各セッションが保存する。Aの停止・鍵リセット等で単調に更新し、古い認可要求・コードも拒否する。連携許可の取り消し・再付与には連携先単位の世代も必要になる。Bが照会結果の新しい世代で古いセッションを更新することは禁止する。

OIDCログインと毎要求照会は別の契約であり、キット外のBにも保護処理の組み込みを要する。参照IDにクライアント認証を加えても、復元可能な資格情報の保管問題が自動で消えるわけではない。

### Cookieの往復案

SameSiteはオリジンとは別の区分であり、別サイトからの遷移に既存のStrict Cookieが付く前提を置かない。Bの試行用Cookie・BセッションはSecure・HttpOnly・ホスト限定・SameSite=Laxを推奨し、コールバックはトップレベルGETに限定する。BのPOSTは従来どおり同一オリジン検査とCSRFで守る。既存のAのadmin CookieはStrictのままとする。

Aでは外部からの到着時に200の継続ページを表示し、利用者のリンク操作で同一サイトの認可継続経路へ進む案を第一候補とする。継続先は保存済み認可要求に限定し、要求は到着時点で特定の利用者に結び付けず、継続後にセッションを検証する。これによりAでログイン済みの場合も利用可能かをブラウザで実証する。自動リダイレクトだけでStrict Cookieが復元されるとは保証しない。代替はAの連携用Cookieを別途Laxにする案で、保存データ・守りの変更として承認を要する。新規JSで解決しない。

## 4. 失効・障害時の契約案

| 状態 | Bの動作 |
|---|---|
| 有効・Bでの利用許可あり | Bの権限を確認して実行 |
| 正常な200応答が明示する無効・世代不一致 | Bセッションを破棄し、保護された操作を拒否。Bのログイン画面を案内し、Aへ自動転送しない |
| 401/403・5xx・タイムアウト・TLSエラー・不正本文・照会結果の識別不一致 | 操作せず503。既存セッションは即削除せず、回復後に再確認。認証画面への無限転送をしない |
| 期限切れ | Bセッションを失効させ、必要に応じて再認証 |

コード交換時にも最新のアカウント・利用許可を確認する。停止とコード交換・トークン発行を直列化するか、失効世代を照合し、停止前のコードは再開後も使えない契約とする。具体方式は詳細設計で決める。

停止・再開だけで過去のBセッションが復活しないよう、停止時は未消費コード・進行中の認可要求・連携状態を同じトランザクションで無効化する。世代方式では同じトランザクションで世代も更新する。コード消費の条件付き単文だけでなく、消費からトークン発行までを含む全体の原子性を保証する。コードの再利用を検知した場合は、そのコードから発行した連携も取り消す方針とし、検知用の消費済み記録の保持期限を設計する。アカウント削除・鍵のリセット・重大な認証異常にも連携失効を適用する案。Aの通常ログアウトを全Bのログアウトにするかは未決で、初版では混同しない。BのログアウトはBのセッションを消す。

毎要求確認は、Aの判定後からBの処理実行までの競合をなくす分散トランザクションではない。「停止のコミット後にAが行う確認は拒否する」を保証境界とする。長時間接続・WebSocket・ジョブは初版の対象外とし、再確認の周期や実行時の確認を別途設計する。

タイムアウトの初期案は2秒（実測で決定）、認証が必要な操作だけ照会する。再試行で負荷を増幅しない。Aの負荷・停止がBへ波及することを運用上の制約とする。同時照会数を制限する。障害側だけの短い遮断（初期案5秒）は許すが、成功結果をキャッシュして通過させない。画面には再試行を案内する503を表示する。

## 5. 保存・通信・安全策の候補

以下は追加の承認対象。列と保持期限は詳細設計で台帳に確定する。

| 保存先 | 候補データ | 保持・削除の案 |
|---|---|---|
| A | 安定したsub、連携先ID・戻り先・利用許可、連携先の資格情報 | 連携終了時に削除。subを再利用しない仕組みを含め設計 |
| A | 認可要求・コードのハッシュと発行先・期限、消費記録、世代または連携トークンのハッシュ | コード60秒、認可要求5分、連携最大12時間を初期案とし、再利用検知用の記録も含めGCを設計 |
| B | ログイン試行、Bセッションとissuer/sub・ログイン時の世代（または連携トークン）、局所ID・ロール | 試行は5分、セッションは無操作2時間・最大12時間を初期案とし、ログアウト・失効・期限後に削除。局所ID・ロールはセッションとは別の保持・削除規則を定める |
| A/B | 署名秘密鍵・連携先資格情報 | DB外を含む保管先・権限・更新・廃棄・バックアップを詳細設計で確定 |

RFC 7662案では、Aは照合用のトークンをハッシュ保存する。BはAへ提示する連携トークンの復元が必要であり、ハッシュだけでは足りない。暗号化保存と鍵の分離を候補とし、キットの「セッションはハッシュのみ」の原則との差分・例外承認を実装前に解決する。sub・世代照会方式なら利用者ごとの復元可能トークンは保存せず、この例外は不要になる。B自身のクライアント資格情報はどちらの方式でも必要で、設定ファイル等で保護し更新する。ブラウザにはBのランダムなセッションCookieと短命の試行用Cookieだけを置く。

- OIDC/JWTの仕様適合は、依存削減のために安易に自作しない。標準ライブラリで署名できることとOIDC/JWT全体の仕様適合は別である。保守状況・ライセンス・間接依存を調べ、実績あるライブラリと標準ライブラリによる限定実装の検証負担を比較する。自前実装も規約上は禁止されていないが、自動で採択しない。
- HTTPSを前提とし、Cookieはアプリごとに分離する。クロスサイトからのコールバックとSameSiteの整合をテストし、既存admin Cookieを無条件に緩和しない。
- AのURL・issuer・戻り先を管理者設定で固定する。任意URLへの通信、開放リダイレクト、SSRF、コード再利用を防ぐ。通信先の自動追従・リダイレクトも制限する。
- キー更新時の旧公開鍵の保持期間、未知のkidへの照会制限、時刻ずれ、漏洩時の取り消しを定める。
- コード・トークン・Cookie・秘密鍵をログに出さない。コールバックURLのクエリもアクセスログ・CDN・エラー監視から除外または秘匿する。応答はno-store、Referrer-Policyも確認する。
- AのWebAuthn経路の承認済みJSを再利用する案を優先し、読込画面やCSPの拡大は別途承認する。新しい連携先管理画面は既存の画面の型を使う。

## 6. 保つ契約・変更する契約

| 項目 | 保つこと | 追加・変更案 |
|---|---|---|
| Base・公開閲覧 | 外部認証なしで従来どおり動く | 任意機能を有効化した場合だけ連携 |
| Aの既存管理画面 | 最後の管理者保護・アカウント分離・既存認証 | 連携先管理と失効処理を追加 |
| Bの管理画面 | 同梱機能の権限・CSRF・no-transform等 | `features.Admin` 相当の口を外部認証でも提供。ローカルauthとの多重登録は拒否する案 |
| データ所有者 | 匿名OwnerIDは業務上の本人識別に使わない | issuer/subとBの業務データの対応を別に設計 |

### Bの局所IDと管理者の復旧

Bに `(issuer, sub)` を一意とする局所利用者表を設け、再利用しない整数IDを `AdminSession.AccountID()` に対応させる案を推奨する。Bにアカウント作成・パスキー管理画面は設けないが、権限対応の保存は必要になる。ロールはBが要求ごとに読み、未登録者に管理者権限を与えない。匿名OwnerIDや外部subを無理に整数へ変換しない。

初回のB管理者は、サーバー操作権限のある人がissuer/subを指定するCLIで明示的に割り当てる案とする。Aで唯一のB管理者を停止してもAの操作を妨げない。復旧は別の有効・許可済み利用者へBのCLIで管理者を割り当て、Aの確認を迂回する認証経路は設けない。局所対応表の保持・削除、業務データを残す場合の扱いはデータ台帳で定める。

## 8. 受け入れ条件

- Aで認証しBへログインできる。Bにパスキーやアカウント作成画面を持たせない。
- Aで停止をコミットした後のBのGET・POST・API照会を拒否し、更新されていないことを確認する。別利用者は影響を受けない。
- 停止とコード交換が競合しても認証を復活させない。停止前のコードは再開後も拒否する。
- 停止後の再開でも旧Bセッションは復活しない。削除・連携許可取り消し・鍵リセット・期限切れも検証する。
- A停止・遅延・TLSエラー・不正応答は503で閉じ、回復後に再確認できる。肯定キャッシュで通過しない。
- state/nonce/PKCE、署名・issuer・audience・期限・戻り先の不一致、コード再利用、他のB用トークンを拒否する。
- 同時ログイン、失効との競合、連携先資格情報・署名鍵の更新、未登録の連携先、SSRF・ログ漏洩を検証する。
- Bの管理者権限は明示的に付与し、Aの管理者であることだけでは付与しない。
- 同一サイトの別オリジンと、異なる登録可能ドメインの両方で、未ログイン・Aログイン済み・コールバック直後のCookieと無限転送がないことをブラウザ検証する。BのCSRF・セッション固定対策、元のページへの安全な復帰を確認する。
- 401等の資格情報不良でセッションを一括破棄しない。正常な無効応答のみ破棄し、障害回復・同時照会上限・失敗側の遮断を検証する。
- Bの局所IDの一意性・非再利用、初回管理者設定、唯一の管理者をAで停止した後の復旧を検証する。
- `docs/data-inventory.md`・`PrivacyNotices`・ドメインモデルを更新し、`test/canary_test.go` の照会・コールバック漏洩検査、`test/isolated_routes_test.go`、`test/admin_ui_test.go` の対象を追加する。
- `go test -race ./...`、`make verify`、該当するブラウザ・データ台帳・ドメイン不変条件・カナリアテストを通す。

## 10. Fableレビューの反映（P-62）

読み合わせによるレビューであり、ブラウザ動作・競合の実証は未実施。Cookieの代替案、auth内での原子的失効、世代照会の比較案、Bの局所IDと復旧、障害応答の区別を追記した。

指摘をそのまま採用しなかった点: Strictの問題はクロスサイトで生じ、別オリジンの全構成で必ず失敗するとは限らない。リダイレクト連鎖のブラウザ動作は実証する。条件付きのコード消費だけでは、後続の発行処理の原子性まで保証されない。参照IDも資格情報になり得る。ES256を標準で扱えることだけで、OIDCの自前実装を採択しない。

実装前の未決事項と推奨案:

| 決める事項 | 推奨・比較案 |
|---|---|
| 提供側の配置 | auth内部で明示的に有効化。利用側だけ別機能 |
| 毎要求の照会 | sub＋失効世代の照会をRFC 7662案と比較して確定 |
| Cookie | BはLax、AはStrictと継続ページ。別サイトで先に実証 |
| OIDC実装 | 限定実装とライブラリの仕様適合・依存・検証負担を比較 |
| BのIDと復旧 | 局所ID表とCLIによる初回権限付与・復旧 |
| subの公開範囲 | 自社内のみの初版はランダムなpublic subを候補とする。pairwiseなら相関を減らせる一方、連携先ごとの対応表・復旧手順が必要。WebAuthn user.idはリセットで変わるため流用しない |

追加参照: [CookieのSameSite](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)、[OAuth 2.0 Security BCP（RFC 9700）](https://www.rfc-editor.org/rfc/rfc9700.html)。

## 11. 方式の試作検証

[検証結果と再実行手順](experiments/federated-auth/README.md)に記録した。別サイトでのCookie往復、世代による失効、停止とコード交換の競合、A障害時の拒否とセッション保持を確認した。Goとキットの既存SQLiteドライバでも主要な失効契約を検査した。

この結果から、BのLax Cookie、AのStrict＋継続ページ、sub＋世代照会を詳細設計の第一候補とする。実際のOIDC・パスキーとの統合、他ブラウザ、復旧CLI・GC、ライブラリ選定は未完了。実装前の承認事項は引き続き7節のとおりである。

## 13. FableレビューP-64の反映

方針は採用可能との評価を受けた。実装前の修正として、クライアント認証前のコード再利用による失効を禁止し、confidential clientでもS256をアプリ側で必須にした。discoveryと公開経路は実装済みの範囲だけを構成する。

依存は単一モジュール内のimport境界で分ける。UserInfoとトークン保存表、Bの起動時discovery取得・権限CLIのネットワーク確認、Aのロール変更によるB失効を初版から外す。削除後のsub墓標は12時間＋2分後にGCし、無期限保持をしない。試行上限では最古破棄とメモリの流量制限を組み合わせ、残る可用性の制約を明示した。
