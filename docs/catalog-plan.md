# カタログ機能 実装計画

状態: 設計草案・Fableレビュー反映済み（実装承認待ち）。実装および承認境界2・4・5の変更は未実施。
ドメインモデル草案は [catalog-domain-draft.md](catalog-domain-draft.md)。実装時に `docs/domain/catalog.md` へ移し、不変条件と実際のテストを対応させる。既存の不変条件検査は緩めない。

## 1. 目的と範囲

商品・サービス・事例・作品をテキスト中心で掲載する、独立した同梱機能 `features/catalog` を作る。画面名は当面「カタログ」。Newsの表・経路・仕様は変更しない。

初版は項目の作成・編集・公開・非公開・削除、カテゴリ1つと複数タグ、公開側の絞り込みとページ送りまで。画像は必要性を認識したうえで、容量・形式・メタデータ除去・保存先・バックアップを別途設計する次段階にする。画像URL欄も初版には設けない。
予約公開、価格・在庫・注文、独立したJSON API、静的書き出し、操作履歴、項目ごとの権限は範囲外。

## 2. 経路と連携

- 公開: `GET /catalog`、`GET /catalog/{id}`。一覧のGETパラメータは `q`、`category`（カテゴリID）、繰り返しの `tag`（タグID）、`page`。
- 管理: `/admin/catalog` 配下の一覧・新規・編集・公開・非公開・削除確認。変更はPOSTだけ。カテゴリとタグの管理も同配下に置く。
- `features.Admin` の `Page`・`Form` で保護し、管理者とメンバーの両方に全編集操作を許す。認証の表は直接読まない。
- `make add-catalog` / `remove-catalog` を追加。追加時はAuthも有効化し、Catalog使用中はAuth削除を拒否。`AdminConsumer` を実装し、既存の起動時依存検査を使う。`cmd/kit` のAuth削除拒否をNewsとCatalogの両方に広げる。
- `IsolatedRoutesFeature`・`NavLinkFeature`・`LayoutConsumer`・`SitemapFeature`・`AdminNavFeature` の既存の口で接続。Siteがなくても公開ページは表示可能にする。
- サーバーとSQLiteが必要。静的書き出しは既存のexport処理が非対応機能として拒否することを検証する。新しい拒否機構は作らない。

## 3. 保存データ案（承認境界2）

| 表 | 列案 | 目的・保持 |
|---|---|---|
| catalog_items | id、title、body、status、category_id（NULL可）、created_at、updated_at | 公開内容。明示削除まで |
| catalog_categories | id、name | 単一分類。明示削除まで |
| catalog_tags | id、name | 複数分類。明示削除まで |
| catalog_item_tags | item_id、tag_id（複合主キー） | 項目とタグの関連。どちらかの削除で消える |

IDはAUTOINCREMENTで再利用しない。statusはdraft/publishedのCHECK制約。分類名は前後空白を除去した文字列をUNIQUEにする（大小文字・全半角は区別）。category_idは削除時SET NULL、関連表のFKはCASCADE。分類削除は影響件数を確認画面に示す。
項目・分類・タグ関連の保存は同一トランザクション。管理側で存在しない分類IDの保存は拒否し、SQLはプレースホルダーを使う。新規タグは `INSERT ... ON CONFLICT(name) DO NOTHING` 後にIDを取得し、同名の既存タグがあればそれを使う。専用接続で `BEGIN IMMEDIATE` を開始し、同じ接続で保存・コミット・ロールバックする。競合待ちは既存のbusy_timeoutを使い、時間切れは入力値を含まない再試行案内にする。

索引は `catalog_items(status, id DESC)`、`catalog_items(category_id)`、`catalog_item_tags(tag_id, item_id)`。分類名変更・削除や関連変更は影響する項目のupdated_atも同一トランザクションで更新する。sitemapには絞り込みURLを載せず、公開詳細をNewsと同じ最大49,000件まで載せ、updated_atをlastmodにする。

タイトル1〜200字、本文50,000字以下、分類名1〜50字、1項目20タグ以下。タイトル・分類名は既存の `form.Line` に合わせて前後空白を除去し、改行・制御文字を拒否する。内部の連続空白は保持する。タグ新規作成は入力してEnterだけで保存せず、「新規タグとして追加」を明示して選び、項目の保存と同時に確定する。入力エラー時は部分保存しない。
本文はプレーンテキスト。個人情報を入力しない旨を管理画面に示す。作者ID、閲覧履歴、検索語、IP、追加Cookieは保存しない。公開閲覧で匿名セッションを発行・照合しない。CoreのGCやアカウント削除でも公開内容は消さない。
機能の無効化はデータ削除ではない。削除済みデータはバックアップに残り得るため、運用時の保持方針も台帳に記す。実装時にデータ台帳・プライバシー説明を更新する。

## 4. 公開検索と部分描画

- title/bodyの部分一致、カテゴリ一致、指定したタグすべてに一致（AND）。検索語は200字、タグ条件は20個まで。LIKEは `ESCAPE` を明示し、バックスラッシュ自身と `%`・`_` をエスケープして文字として検索する。SQLiteのLIKEはASCIIの大小文字を区別せず、全Unicodeの大小文字同一視は行わない。タグIDは重複除去し、AND検索は関連表の `GROUP BY item_id HAVING COUNT(DISTINCT tag_id) = ?` で判定する。
- 20件/ページ、id降順で安定させる。pageは1〜5,000（NewsのmaxOffset=100,000と同じ上限の求め方）。構文不正や入力上限超過だけを400とし、範囲内で結果がないページは空の一覧。未公開項目の詳細は404。
- 分類候補も公開項目に付いているものだけ。公開側の分類解決を1つにまとめ、存在しないID・下書き専用のIDとも200の空一覧・同じ文言にする。非公開の分類名は反映しない。件数・検索結果・sitemapを含め、未公開の項目や分類との関連は漏らさない。
- htmxは公開一覧のGET絞り込みとページ送りに限定。管理側の書き込みは通常フォームとし、既存CSRF基盤をそのまま使う。
- 同じURLで通常は全ページ、HX-Request時は一覧断片を返す。履歴復元要求は全ページを優先し、直接表示・戻る・進むを検証する。
- 公開・非公開の反映遅れを避けるため、初版は一覧・詳細・断片ともCore既定の `Cache-Control: no-store` を維持し、PublicCacheを呼ばない。`Vary: HX-Request, HX-History-Restore-Request` を揃え、キャッシュによる混同を避ける。下書きの管理画面はhtmx履歴に保存しない。
- フォーム送信を起点とし、入力ごとの自動通信は初版に入れない。URLに検索条件が残ることを説明し、秘密を入力しないよう案内する。
- 全件数のCOUNTは行わず、既存page部品の21件取得で次ページを判定し、「このページにN件・次ページあり」を通知する。固定したrole=status領域の中身を更新し、領域自体は差し替えない。検索後のフォーカスはフォームに残し、ページ送り後はtabindex=-1の結果見出しへ移す。通信中表示、失敗の通知と通常GETへの再試行リンクを設ける。古い要求が新しい結果を上書きしないよう同期・取消を設定する。

## 5. JavaScriptとCSP案（承認境界4・5）

初版はhtmx本体とカタログ用の自前JSの2本。`features/catalog/static/htmx.min.js` と `features/catalog/static/catalog.js` に置き、独立経路 `/catalog/static/` で配信する。機能を外すと配信も止まる。導入前に公式資料で対応バージョン・ライセンス・CSP制約を検証し、版・取得元・ハッシュ・ライセンスを記録する。現時点では取得・追加しない。npmやCDNの実行時読込は使わない。

Alpine.jsは初版から外す。タグ選択は既存タグのチェックボックスと新規タグ名の入力欄で提供する。タグが増え実際に操作上の問題が確認されたら、まずhtmxによる候補検索を検討する。選択済みタグを検索で失わない設計が必要。Alpineの試作を行う場合も別途範囲を決め、本体への採用・CSP緩和を自動で進めない。

設定はインラインscriptではなく `meta name="htmx-config"` に置く案とし、`allowEval:false`、`allowScriptTags:false`、`includeIndicatorStyles:false`、`selfRequestsOnly:true`、`historyCacheSize:0` を指定する。採用版の公式仕様と照合してから確定する。履歴スナップショットをlocalStorageに保存しない。hx-on、js:値、イベントの式フィルタは使わない。4xx/5xx・通信失敗は自前JSのイベント処理で固定の通知を表示し、元の結果を残して通常GETへの再試行を提供する。応答本文を無条件にHTMLとして挿入しない。インジケーターは既存style.cssのクラスで作る。

公開一覧だけに2本を読み込み、同画面だけscript-src 'self'、他は既定を維持。unsafe-inline/unsafe-evalとstyle-srcの緩和は行わない。AGENTS.md・READMEの「唯一のJS例外」の説明、UI規約、JSファイル許可リストと画面別scriptタグ検査を、この2本の範囲に更新することも承認対象に含める。管理画面にはhtmxを読み込まない。将来広げる場合は、現行Admin.Formがフォームのcsrf_tokenを検証する点と、UI規約のヘッダー送信方針との整合を別途検討する。

## 6. 検証と実装順

1. 計画とモデルのレビュー、保存項目・JS・CSPの具体案の承認。
2. モデルを正本へ移し、SQLite保存処理と通常HTMLの公開・管理機能を実装。テストの番号を対応づける。
3. 公開一覧へのhtmxの強化を実装。
4. 付け外しコマンド、Auth依存、Site連携、台帳・README・スキル・検査の更新。migration.sqlは有効化前でも台帳検査が読むため、台帳と同じコミットに含める。
5. 実SQLiteで公開判定・関連更新のロールバック・FK・削除を検証。未ログイン/停止/CSRF/別オリジン、XSS文字列、ログカナリア、通常/断片/履歴/JSなし、CSP適用範囲を検証。既存News・Authも回帰検証。
6. `go test -race ./...`、`make verify`、`make build`。ブラウザでキーボード・読み上げ・通信失敗・戻る進むを確認。未確認事項は明記し、機械検査だけでアクセシビリティ適合を宣言しない。

紹介サイトへの取り込み・公開は別工程。今回は設計文書のみで、本番の構成は変更しない。

## 7. 実装前の承認事項

- 境界2: 上記4表と管理フォーム項目。カテゴリ1つ＋タグ複数を基本案とする。小さく始める場合はカテゴリを省き、タグのみの3表にもできる。
- 境界4: htmxとcatalog.jsの2本追加、規約・README・許可検査の例外更新。Alpineは含めない。
- 境界5: 公開一覧画面だけscript-srcをselfへ変更。
- ライブラリ取得のための開発時の外部通信も承認範囲に含める。実行時の外部通信は追加しない。go.modの変更なし。

Fableレビューの指摘を反映。no-storeは反映遅れを避けるため維持し、カテゴリは削減可能な選択肢として明記した。仕様・設定の正しさは実装段階の公式資料照合と検証で確定する。
